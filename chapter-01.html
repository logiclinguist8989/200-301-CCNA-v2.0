1A.2 Introduction: what a network actually does

A network moves data from one program on one device to another program on another device. When you open a website on your laptop in Birgunj, your browser hands a request to your laptop's network software. That software wraps the request in addressing information, turns it into electrical signals or radio waves, and sends it to the next device. Every device on the path reads only the information it needs, then passes the data on.

Networking models exist so that this job is split into layers. Each layer solves one problem and trusts the layers below it. Cable makers do not need to know about web browsers, and browser developers do not need to know about cables.

1A.3 The OSI and TCP/IP models

The OSI model has seven layers and is used to talk about problems ("it's a Layer 1 issue"). The TCP/IP model is the one the Internet actually runs on. You need to map between them quickly.

7 Application Application Data Network services for programs HTTP, HTTPS, DNS, DHCP, SSH, SNMP Hosts, servers
6 Presentation Application Data Formatting, encryption, compression TLS, JPEG, ASCII Hosts
5 Session Application Data Opening and closing conversations Session setup in apps Hosts
4 Transport Transport Segment (TCP) / datagram (UDP) Process-to-process delivery using port numbers TCP, UDP Hosts, firewalls
3 Network Internet Packet Logical addressing and routing between networks IPv4, IPv6, ICMP, OSPF Routers, Layer 3 switches
2 Data Link Link (Network Access) Frame Delivery on one local link using MAC addresses Ethernet, 802.11 Wi-Fi Switches, access points

1A.4 How encapsulation works

Encapsulation means each layer adds its own header (and Ethernet also adds a trailer) in front of the data it receives from the layer above. Decapsulation is the reverse on the receiving side. Figure 1.1 shows PC1 sending a web request; Figure 1.2 then follows the frame across the switch and the router.

The data block (highlighted) never changes on the way down; each layer only adds its header, and Data Link also adds the FCS trailer. The receiver reads the same picture bottom to top, removing one header per layer.

Sending (PC1 → web server at 203.0.113.80):

  1. The browser creates an HTTP request (Application data).
  2. Transport adds a TCP header: source port 50123 (random, chosen by PC1), destination port 443 (HTTPS). The result is a segment.
  3. Network adds an IPv4 header: source 10.10.10.11, destination 203.0.113.80. The result is a packet.
  4. Data Link adds an Ethernet header and trailer. The destination MAC is the default gateway's MAC (R1), not the web server's, because the server is on another network. The result is a frame.
  5. Physical turns the frame into bits on the wire.

Receiving (R1, the router):

  1. R1 receives bits, rebuilds the frame and checks the FCS (error check). A bad FCS means the frame is dropped and the CRC counter rises — this is why cable faults show up as CRC errors.
  2. R1 sees its own MAC as destination, removes the Ethernet header, and reads the IP destination.
  3. R1 looks up 203.0.113.80 in its routing table, then builds a new Ethernet frame for the next link. The IP addresses stay the same end to end; the MAC addresses change at every hop (unless NAT is used, Chapter 21).

In Figure 1.2 the arrows show the direction of travel. SW1 forwards the frame unchanged because it only reads the destination MAC. R1 strips the old Ethernet header and builds a new one for the next link, while the IP header keeps the same source and destination.

1A.6 Ethernet frames and MAC addresses

A MAC address is 48 bits, written as 12 hexadecimal digits, for example 0050.7966.6801 (Cisco style) or 00-50-79-66-68-01 (Windows style). The first 24 bits are the OUI (Organizationally Unique Identifier), which identifies the manufacturer; the last 24 bits are assigned by that manufacturer.

Type Destination MAC Who receives it
Unicast One device's MAC That device only
Broadcast FFFF.FFFF.FFFF Every device in the VLAN (e.g. ARP requests, DHCP Discover)
Multicast Starts 0100.5E (IPv4) or 3333 (IPv6) Devices that joined that group (e.g. OSPF hellos)

Ethernet II frame layout (sizes in bytes)

Field Size Purpose
Preamble + SFD 7 + 1 Synchronises the receiver's clock; not counted in frame size
Destination MAC 6 Where the frame goes on this link
Source MAC 6 Who sent it on this link
802.1Q tag (only on trunks) 4 VLAN ID and priority (Chapter 5)
Type 2 Payload protocol: 0x0800 IPv4, 0x86DD IPv6, 0x0806 ARP
Payload 46–1500 The packet; 1500 bytes is the standard MTU
FCS 4 CRC checksum; a mismatch = corrupted frame, dropped

A normal Ethernet frame is therefore 64 to 1518 bytes (1522 with an 802.1Q tag). Frames smaller than 64 bytes are runts; frames larger than the maximum are giants. Both counters appear in show interfaces and matter for objective 1.1.

Figure 1.3 shows the same fields as the table above, in transmission order from left to right. The highlighted payload is the IP packet from Figure 1.1; everything from Destination MAC to FCS counts toward the 64–1518-byte frame size.

1A.7 How a switch forwards frames

A switch builds its MAC address table by watching source addresses.

  1. Learn: a frame arrives on Fa0/1 from 0050.7966.6801. The switch records "this MAC is on Fa0/1, VLAN 1" (entries age out after 300 seconds by default).
  2. Forward: if the destination MAC is in the table, the frame goes out only that port.
  3. Flood: if the destination is unknown, broadcast or (by default) multicast, the frame goes out every port in the same VLAN except the one it came in.
  4. Filter: if the destination is on the same port it arrived on, the frame is dropped.

Figure 1.4 runs once for every frame. Learning always uses the source address; the forwarding choice always uses the destination address. Unknown multicast is flooded like a broadcast by default.

SW1
SW1# show mac address-table dynamic
          Mac Address Table
-------------------------------------------
Vlan    Mac Address       Type        Ports
----    -----------       --------    -----
   1    0050.7966.6801    DYNAMIC     Fa0/1
   1    0050.7966.6802    DYNAMIC     Gi0/1

Read it as: PC1's MAC lives behind Fa0/1; the second MAC is reached through the uplink Gi0/1, so that host is on another switch.

Collision domain vs broadcast domain. A collision domain is the set of devices whose transmissions can collide; on a modern switch with full-duplex ports each port is its own, and collisions should be zero. A broadcast domain is the set of devices that receive each other's broadcasts; one VLAN is one broadcast domain, and routers stop broadcasts.

ARP in one paragraph. Before PC1 can send to 10.10.10.1 it needs that IP's MAC address. PC1 broadcasts an ARP Request ("who has 10.10.10.1?"); R1 replies by unicast with its MAC; PC1 caches it (arp -a on Windows shows the cache). If a host's gateway or mask is wrong, ARP is often where the fault first appears.

1A.9 Cisco IOS command line essentials

Every Cisco device you configure in this guide uses the same mode hierarchy. Moving between modes is the first skill to make automatic.

Mode Prompt How to enter How to leave What you do there

Privileged EXEC R1# enable disable All show, copy, reload, debug, clear
Global configuration R1(config)# configure terminal end or Ctrl+Z (to #), exit (one level up) Device-wide settings

In Figure 1.5 each arrow is labelled with the command that moves you down a level. The three sub-modes on the bottom row are all entered from global configuration, so you always pass through R1# and R1(config)# first.

Helpers you should use every day: ? lists what can come next; Tab completes a keyword; do show ... runs a show command from any config mode; the up arrow recalls history; show running-config | include hostname filters output (| section, | begin also work).

Two configurations live on every device. The running-config is in RAM and is what the device is doing now. The startup-config is in NVRAM and is loaded at boot. Changes take effect immediately but are lost on reload unless you save.

1A.10 Part A quick check

  • Which address changes at every router hop, MAC or IP? MAC; the IP addresses stay the same unless NAT is in use.
  • A switch receives a frame for an unknown unicast MAC. What does it do? Floods it out all ports in that VLAN except the incoming one.
  • Which mode do you need for show running-config? Privileged EXEC (#).

Chapter 1, Part B — Objective 1.1: Diagnose interface and cable issues

Most "the network is down" tickets start at Layer 1, and the exam expects you to name the cause from interface status and counters. The rule of thumb: status tells you whether the link exists; counters tell you how healthy it is.

1B.1 Learning objectives

After Part B you can:

  1. Choose the correct copper or fiber cable, connector and standard for a link, and state its distance limit.
  2. Explain T568A/T568B pinouts and when straight-through, crossover and rollover cables are used, including auto-MDIX.
  3. Distinguish multimode and single-mode fiber and read optical signal levels in dBm.
  4. Interpret every interface status combination and the main error counters.
  5. Diagnose duplex mismatch, speed mismatch, over-length cables, wrong cable types and bad optics from evidence.
  6. Configure speed and duplex correctly and verify the result.

1B.2 Introduction

A cable fault rarely looks like a cable fault. A duplex mismatch keeps the link up but makes file transfers crawl. A cable that is 130 m long may come up but show CRC errors all day. A fiber patch lead with swapped strands shows no light at all. Your job is to collect evidence — status, counters, logs, optical readings — and match it to a cause.

1B.3 Copper cabling: categories, standards and distance

Ethernet over copper uses UTP (unshielded twisted pair): four twisted pairs in one jacket, ending in RJ-45 connectors. Twisting cancels electromagnetic interference (EMI); untwisting too much at the connector causes crosstalk and errors. STP/FTP (shielded) cable is used near heavy EMI such as motors.

Standard (common name) IEEE Speed Minimum cable Max distance Pairs used
10BASE-T (Ethernet) 802.3i 10 Mb/s Cat3 100 m 2 (pins 1,2 and 3,6)
100BASE-TX (Fast Ethernet) 802.3u 100 Mb/s Cat5 100 m 2 (pins 1,2 and 3,6)
1000BASE-T (Gigabit Ethernet) 802.3ab 1 Gb/s Cat5e 100 m All 4 pairs, both directions
10GBASE-T 802.3an 10 Gb/s Cat6a (Cat6 up to 55 m) 100 m All 4 pairs

The 100 m rule covers the whole channel: typically 90 m of permanent cable plus patch leads. Beyond it, signals weaken and pick up noise, so you see CRC and input errors, a link that flaps up and down, or a link that only negotiates at a lower speed.

1B.4 Pinouts: T568A, T568B, straight-through, crossover, rollover

The two wiring standards differ only by swapping the green and orange pairs.

Pin T568A T568B 10/100 role on a PC/router (MDI)
1 White/green White/orange Transmit +
2 Green Orange Transmit −
3 White/orange White/green Receive +
4 Blue Blue (used by 1000BASE-T)
5 White/blue White/blue (used by 1000BASE-T)
6 Orange Green Receive −
7 White/brown White/brown (used by 1000BASE-T)
8 Brown Brown (used by 1000BASE-T)

Why cable type matters. PCs, routers, servers, firewalls and APs are MDI devices: they transmit on pins 1,2 and receive on 3,6. Switches (and hubs) are MDI-X: they do the opposite. Transmit must meet receive.

Cable Wiring Use between Examples
Straight-through Same standard both ends (B–B) Unlike devices (MDI ↔ MDI-X) PC–switch, router–switch, AP–switch
Crossover A one end, B the other Like devices (MDI ↔ MDI, MDI-X ↔ MDI-X) Switch–switch, PC–PC, router–router, PC–router
Rollover (console) Pins reversed 1↔8 PC serial/USB to device console port Initial setup, password recovery

Figure 1.6, left: a PC sends on pins 1 and 2 and the switch listens on 1 and 2, so the wires run straight. Right: two switches both listen on 1 and 2, so the cable must cross each side's 3/6 transmit pair over to the other side's 1/2 receive pair.

Auto-MDIX lets a port detect the wrong cable and swap its own transmit and receive pairs. Most current Cisco switches enable it by default (mdix auto); on many models it only works when speed and duplex are both set to auto. Gigabit 1000BASE-T ports handle pair swapping as part of the standard. So on real modern gear a "wrong" cable often still works — but the exam still expects you to know the correct cable, and Packet Tracer often does not apply auto-MDIX, so the link stays red.

Memory trickSort devices into two teams: PCs and routers (MDI) and switches and hubs (MDI-X). Same team → crossover; different teams → straight-through. The rollover cable is only for the console port.

1B.5 Fiber optic cabling

Fiber carries light, so it is immune to EMI, can run much further than copper, and is used for uplinks between floors and buildings. A fiber link uses two strands: one to transmit, one to receive. Tx on one end must connect to Rx on the other.

Multimode fiber (MMF) Single-mode fiber (SMF)
Core diameter 50 or 62.5 µm (cladding 125 µm) About 9 µm (cladding 125 µm)
Light source LED or VCSEL laser Laser
Light paths Many modes bounce through the core One mode, straight path
Typical distance Hundreds of metres Kilometres (10 km and beyond)
Cost Cheaper optics More expensive optics
Jacket colour (convention) Orange (OM1/OM2), aqua (OM3/OM4) Yellow

Figure 1.7 shows why reach differs. In the wide multimode core, light takes several zig-zag paths of different lengths, so a pulse spreads out over distance. The narrow single-mode core allows only one path, so the pulse stays sharp for kilometres.

Standard Fiber Typical reach
1000BASE-SX MMF About 220–550 m depending on fiber grade
1000BASE-LX/LH SMF (also MMF with conditioning) 5–10 km depending on optic
10GBASE-SR MMF About 300 m on OM3, 400 m on OM4
10GBASE-LR SMF 10 km

Reach figures vary by optic model; always check the transceiver data sheet. Fiber ports usually take a pluggable transceiver: SFP (1 Gb/s), SFP+ (10 Gb/s), QSFP (40/100 Gb/s). Common connectors are LC (small, duplex, the usual one on SFPs) and SC (larger, square, push-pull).

A mismatched optic is a cable-type fault. An SX optic on one end and an LX optic on the other, or an SR optic plugged into single-mode fiber, gives no link or a very weak signal.

1B.6 Signal levels: reading optical power in dBm

Optical power is measured in dBm (decibels relative to 1 milliwatt). 0 dBm = 1 mW. Every 3 dB lower roughly halves the power, so −3 dBm ≈ 0.5 mW and −10 dBm = 0.1 mW. More negative means weaker. Signal levels are the "signal levels" in objective 1.1.

Transceivers with DOM (digital optical monitoring) report their readings:

SW1
SW1# show interfaces transceiver
                                          Optical   Optical
           Temperature  Voltage  Current  Tx Power  Rx Power
Port       (Celsius)    (Volts)  (mA)     (dBm)     (dBm)
---------  -----------  -------  -------  --------  --------
Gi1/1/1      33.1        3.29     6.2      -5.1      -6.8
Gi1/1/2      34.0        3.28     6.0      -5.3     -24.9 --
  • Gi1/1/1 is healthy: received power (−6.8 dBm) is close to what the far end transmits, so little light is being lost.
  • Gi1/1/2 shows --, meaning Rx power is below the low-alarm threshold. Suspects, in order: dirty or damaged connector, a tight bend or crushed fiber, wrong fiber type, too long a run, a faulty far-end optic.
  • Rx too high (marked ++) happens when a long-range optic is used on a short single-mode run; the receiver is overloaded. The fix is an attenuator or a shorter-reach optic.
  • No light at all on both ends: check that Tx and Rx are not swapped (or not both connected Tx-to-Tx).

show interfaces transceiver detail prints the alarm and warning thresholds for each optic. Output format varies by platform, and not every optic supports DOM. PT note: Packet Tracer does not simulate optical power; learn this from the output above.

Memory trickRead status / protocol as Layer 1 / Layer 2: up/up is healthy, down/down is physical, up/down is a Layer 2 mismatch, and administratively down means someone typed shutdown.

1B.8 Speed and duplex: autonegotiation and mismatches

Duplex is whether a link can send and receive at the same time. Full duplex can; collisions are impossible. Half duplex cannot; the device must listen first (CSMA/CD) and collisions are normal. Modern switched networks should be full duplex everywhere.

Autonegotiation (IEEE 802.3u/802.3ab) lets both ends agree the best common speed and duplex. Problems start when only one side negotiates. What the negotiating side does if the other side is hard-coded:

  1. Speed: it can still detect the speed from the electrical signal, so speed is usually correct.
  2. Duplex: it cannot detect duplex, so it falls back to a default: half duplex at 10 or 100 Mb/s, full duplex at 1000 Mb/s.

That is how a duplex mismatch is born: R1 is hard-coded to speed 100 and duplex full; SW1 is left on auto, senses 100 Mb/s and falls back to half duplex.

Fault Link status Evidence on the full-duplex side Evidence on the half-duplex side Users notice
Duplex mismatch up/up CRC errors, runts, input errors Late collisions, collisions Slow, worse under load; pings may look fine
Speed mismatch (both hard-coded differently) down/down (notconnect) — — No connectivity at all

Figure 1.8 uses the same SW1–SW2 link as Lab 1.2. The highlighted SW2 port is where the problem is born: it negotiates, cannot learn the duplex, and falls back to half. Each side then records a different kind of error, so always compare counters on both ends.

CDP also warns you about duplex mismatches:

%CDP-4-DUPLEX_MISMATCH: duplex mismatch discovered on GigabitEthernet0/1 (not full duplex), with SW2 GigabitEthernet0/1 (full duplex).

Configuring speed and duplex (interface configuration mode):

SW1
SW1(config)# interface gigabitethernet0/1
SW1(config-if)# description Uplink to SW2 Gi0/1
SW1(config-if)# speed 1000            ! options: 10 | 100 | 1000 | auto (platform-dependent)
SW1(config-if)# duplex full           ! options: half | full | auto
SW1(config-if)# end
Command Mode Purpose Common mistake
speed {10\|100\|1000\|auto} Interface config Sets or negotiates speed Hard-coding one end only
duplex {half\|full\|auto} Interface config Sets or negotiates duplex Same — set both ends identically, or leave both on auto

Best practiceLeave both ends on auto, or set both ends to the same speed and duplex. Never mix.

1B.9 Reading show interfaces counters

show interfaces is the most detailed Layer 1/2 command. Annotated example from a link with a duplex problem:

Counters are cumulative since boot or the last clear. To see whether a problem is current, clear and re-check:

1B.10 A systematic diagnostic procedure

Use the same order every time, from Layer 1 upward. Figure 1.9, after this list, draws the same logic as a flowchart.

  1. Check status with show ip interface brief or show interfaces status. Check both ends of the link.
  2. Administratively down? Enter no shutdown.
  3. err-disabled? Read show logging and show interfaces status err-disabled for the reason, fix it, then bounce the port with shutdown / no shutdown.
  4. down/down or notconnect? Check physically: cable seated, link lights, correct cable type (straight vs crossover in labs), cable length, far end enabled, matching speed settings, correct and matching transceivers, fiber Tx/Rx orientation, Rx light level.
  5. up/up but slow or dropping? Compare speed and duplex on both ends. Look at CRC, runts, collisions, late collisions. Clear counters and watch which ones rise.
  6. Counters clean but still failing? The fault is above Layer 1: VLAN, trunk, IP address, mask, gateway or routing — later chapters cover each.
  7. Document the fix and add an interface description.

Work down the left column; the first "yes" tells you what to fix. Only when every check says "no" do you move up to the Layer 2 and Layer 3 checks in later chapters.

1B.11 Real-world scenarios

  • Office printer "randomly offline": the printer NIC is hard-coded 100/full; the switch port is on auto and fell back to 100/half. CDP is not running on the printer, so no log message appears. show interfaces status shows a-half a-100. Fix: set the printer to auto, or hard-code the switch port to match.
  • New building uplink is dead: two switches are joined by MMF but one end has a 1000BASE-LX optic meant for SMF. Both ends show notconnect; DOM on one end reports Rx below threshold. Fix: matching SX optics on both ends.
  • CRC errors on one floor only: cable runs pass beside a lift motor. CRC counters climb steadily, collisions are zero, duplex is correct. Fix: reroute or use shielded cable.

1B.12 Exam-focused revision

  • Straight-through for unlike devices, crossover for like devices, rollover for the console. Auto-MDIX can hide the mistake on real gear.
  • Copper UTP: 100 m. MMF: hundreds of metres. SMF: kilometres. SMF core ≈ 9 µm; MMF core 50/62.5 µm.
  • dBm: more negative = weaker. Low Rx = dirty connector, bend, length, wrong fiber. High Rx on short SMF = needs an attenuator.
  • Duplex mismatch: link up, slow. Full side: CRC/runts. Half side: late collisions.
  • Speed mismatch (both hard-coded): link down.
  • Autonegotiation fallback: 10/100 → half; 1000 → full.
  • Collisions on a full-duplex link should be zero; any late collision is a red flag.
  • administratively down = shutdown; err-disabled = a protection feature shut the port.

Lab 1.2 — Speed and duplex mismatch (Beginner–Intermediate)

Objective: 1.1 (duplex, speed, collisions, errors). Uses the Lab 1.1 topology; only the SW1–SW2 link changes.

Part 1 — Baseline. On both switches run show interfaces status. Gi0/1 should show a-full a-1000: both ends negotiated.

Part 2 — Create a duplex mismatch.

SW1
SW1(config)# interface gigabitethernet0/1
SW1(config-if)# speed 100
SW1(config-if)# duplex full
! SW2 Gi0/1 stays on auto

Expected: the link comes back up. SW2 detects 100 Mb/s but cannot learn the duplex, so show interfaces status on SW2 shows a-half a-100. Within a minute CDP should log %CDP-4-DUPLEX_MISMATCH on the console. Pings between PC1 and PC2 still succeed — exactly why duplex mismatches go unnoticed. PT note: Packet Tracer reproduces the status and the CDP message but does not model real collision and CRC counters reliably; use the annotated output in 1B.9 for those.

Part 3 — Fix it two ways. Either set SW2 Gi0/1 to speed 100 and duplex full (both hard-coded, matching), or return SW1 to speed auto and duplex auto (both negotiating). Verify full on both ends.

Part 4 — Create a speed mismatch. Set SW1 Gi0/1 speed 100 and SW2 Gi0/1 speed 10, both hard-coded. Expected: the link goes down on both ends (notconnect). Restore both to auto.

Part 5 — Broken-configuration challenge. Load this onto a fresh copy of Lab 1.1 and do not read it again until you have diagnosed the fault from show commands only. Ticket: "Users on SW2 say file copies to the server on SW1 are very slow."

The cable exceeds the 100 m limit, so the signal is weak and corrupted, which shows up as CRC errors. Duplex is not the cause because both ends are full and collisions are zero.

Which counter in show interfaces records frames smaller than 64 bytes?

A port shows err-disabled after someone plugged in an unknown device. Which sequence restores it correctly?
