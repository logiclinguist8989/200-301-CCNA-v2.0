Chapter 20IPv4 access control lists

🖼️ 3 figures⏱️ ~21 min read📝 Self-check: 14 questions

Objective covered: 4.6 Configure IPv4 access control lists (standard, extended, numbered, and named ACLs). ACLs are the basic packet filter on every Cisco router and Layer 3 switch, and they reappear in NAT (Chapter 21) and management security.

20.1 Learning objectives

After this chapter you can:

  1. Explain how an ACL is processed: top-down, first match, implicit deny.
  2. Calculate and interpret wildcard masks, including host and any.
  3. Configure standard and extended ACLs, numbered and named, and choose where to apply them.
  4. Edit named ACLs with sequence numbers.
  5. Restrict VTY access with access-class.
  6. Verify ACLs with counters and troubleshoot common mistakes.

Lab itThis chapter is hands-on. Once the theory clicks, jump to Lab 20.1 — Campus security policy with ACLs (Intermediate) and build it yourself — reading about a network is good, breaking and fixing one is better.

20.2 How an ACL works

An access control list is an ordered list of access control entries (ACEs), each a permit or deny with matching conditions. When a packet meets an interface with an ACL (Figure 20.1):

  1. The router compares the packet with the first ACE.
  2. If it matches, the router applies that ACE's action — permit or deny — and stops. Later lines are never checked.
  3. If it does not match, the router tries the next ACE.
  4. If no ACE matches, the packet hits the implicit deny any at the end, which is invisible in the configuration.

In Figure 20.1 a packet walks down the list until a line matches, then leaves to the right with that line's action. The dashed red box is the implicit deny that catches everything else.

Consequences:

  • Order matters. Put specific entries before general ones: deny host 10.10.30.25 after permit 10.10.30.0 0.0.0.255 never matches.
  • An ACL with only deny lines blocks everything; it needs at least one permit.
  • One ACL per interface, per direction, per protocol (one IPv4 inbound, one IPv4 outbound).
  • Inbound ACLs filter packets arriving on the interface, before routing. Outbound ACLs filter packets leaving it, after routing.
  • An outbound ACL does not filter packets the router itself creates (for example its own pings or routing updates).
  • Applying an ACL name that has no entries yet permits everything; once the first entry exists, the implicit deny takes effect.

20.3 Wildcard masks

ACLs match addresses with a wildcard mask: a 32-bit pattern where 0 = this bit must match and 1 = ignore this bit (Figure 20.2). It looks like an inverted subnet mask.

In Figure 20.2 the highlighted wildcard octets are the ones that must match. 10.10.30.25 agrees in all three, so it matches; 10.10.40.11 differs in the third octet (red), so it does not.

Match Address + wildcard Shortcut
One host 10.10.40.11 10.10.40.11 0.0.0.0 host 10.10.40.11
Subnet 10.10.30.0/24 10.10.30.0 0.0.0.255 —
Subnet 10.0.0.4/30 10.0.0.4 0.0.0.3 —
Campus 10.10.0.0/16 10.10.0.0 0.0.255.255 —
Every address 0.0.0.0 255.255.255.255 any

Quick method: wildcard = 255.255.255.255 − subnet mask. For a /26 (255.255.255.192): 255 − 192 = 63 → 0.0.0.63. For a /20 (255.255.240.0): 0.0.15.255.

Wildcards need not match subnet boundaries. 10.10.1.0 0.0.254.255 matches every odd third octet (10.10.1.x, 10.10.3.x …) because the lowest bit of the third octet must be 1 while the other bits there are ignored. You will rarely configure this, but you may be asked to interpret it.

Memory trickWildcard = 255.255.255.255 − mask. In a wildcard, 0 = must match and 1 = don't care — the opposite of a subnet mask.

20.4 Standard and extended, numbered and named

IOS has two ACL types and two ways to identify them. Any combination is allowed.

Standard Extended
Matches on Source IP address only Protocol, source and destination address, source and destination port, and more
Numbered ranges 1–99 and 1300–1999 100–199 and 2000–2699
Named form ip access-list standard NAME ip access-list extended NAME
Typical place Close to the destination Close to the source
Typical use VTY access (access-class), NAT (Chapter 21), SNMP, simple filters Traffic policy between subnets and to services

Numbered standard ACL — each line is a global command that starts with the number:

R1
R1(config)# access-list 10 remark Management sources
R1(config)# access-list 10 permit 10.10.99.0 0.0.0.255
R1(config)# access-list 10 permit host 10.10.10.11

In a standard ACL an address with no wildcard means a single host, so access-list 10 permit 10.10.10.11 is the same as permit host 10.10.10.11.

Numbered extended ACL:

R1
R1(config)# access-list 110 permit tcp 10.10.30.0 0.0.0.255 any eq 443
R1(config)# access-list 110 deny ip 10.10.30.0 0.0.0.255 10.10.99.0 0.0.0.255
R1(config)# access-list 110 permit ip any any

Named ACL — the name is self-documenting, and you enter a sub-mode where each line gets a sequence number (10, 20, 30 … unless you type your own):

DSW1
DSW1(config)# ip access-list extended WIRELESS-IN
DSW1(config-ext-nacl)# remark Wireless users: no management, printer by IPP only
DSW1(config-ext-nacl)# 10 permit udp any any eq bootps
DSW1(config-ext-nacl)# 20 deny ip 10.10.30.0 0.0.0.255 10.10.99.0 0.0.0.255
DSW1(config-ext-nacl)# 30 permit tcp 10.10.30.0 0.0.0.255 host 10.10.40.11 eq 631
DSW1(config-ext-nacl)# 40 deny ip 10.10.30.0 0.0.0.255 10.10.40.0 0.0.0.255
DSW1(config-ext-nacl)# 50 permit icmp 10.10.30.0 0.0.0.255 any
DSW1(config-ext-nacl)# 60 permit ip 10.10.30.0 0.0.0.255 any

Names are case-sensitive: wireless-in and WIRELESS-IN are two different ACLs.

20.5 Extended ACE syntax, protocols and ports

{permit | deny} protocol  source source-wildcard [operator port]  destination dest-wildcard [operator port]  [established] [log]
  • protocol: ip (any IPv4 packet), tcp, udp, icmp, ospf, gre, esp, or an IP protocol number.
  • operator: eq (equal), neq (not equal), lt, gt, range 20 21. Only tcp and udp lines can have ports.
  • Position matters: a port written after the source is a source port; after the destination it is a destination port. permit tcp any eq 80 any matches traffic from web servers, not to them.
  • established matches TCP segments with ACK or RST set (return traffic of a session started from the other side).
  • log sends a syslog message when the line matches (Chapter 25).
Service Protocol and port IOS keyword
FTP TCP 20, 21 ftp-data, ftp
SSH / SCP / SFTP TCP 22 — (use 22)
Telnet TCP 23 telnet
SMTP TCP 25 smtp
DNS UDP 53 (and TCP 53) domain
DHCP UDP 67 server, UDP 68 client bootps, bootpc
TFTP UDP 69 tftp
HTTP TCP 80 www
NTP UDP 123 ntp
SNMP UDP 161, 162 (traps) snmp, snmptrap
HTTPS TCP 443 443
Syslog UDP 514 syslog
IPP printing TCP 631 631
ICMP (ping) IP protocol 1, no ports icmp (echo, echo-reply as types)
OSPF IP protocol 89, no ports ospf

IOS shows a keyword in show access-lists even if you typed the number (for example eq 80 appears as eq www).

20.6 Where to place an ACL and how to apply it

Placement rules:

  • Extended ACL — close to the source. It can match exactly the unwanted traffic, so drop it before it crosses the network.
  • Standard ACL — close to the destination. It only sees the source; placed near the source it would block that source from every destination.
  • Pick the direction from the router's point of view: in = arriving on that interface, out = leaving it.

Applying to an interface (one IPv4 ACL per interface per direction):

DSW1
DSW1(config)# interface vlan 30
DSW1(config-if)# ip access-group WIRELESS-IN in

On a Layer 3 switch an ACL on an SVI filters traffic routed into or out of that VLAN. Traffic between two hosts in the same VLAN is switched and never passes the SVI ACL.

An ACL that does not exist yet can be applied without error; it permits everything until its first line is created. no ip access-group WIRELESS-IN in removes it from the interface; no ip access-list extended WIRELESS-IN deletes the list itself.

Memory trickStandard ACLs go near the Destination; Extended ACLs go near the Source. Standard–Destination, Extended–Source.

20.7 Editing ACLs with sequence numbers

Named ACLs (and numbered ACLs entered with ip access-list standard 10 or ip access-list extended 110) can be edited line by line:

DSW1
DSW1(config)# ip access-list extended WIRELESS-IN
DSW1(config-ext-nacl)# 15 permit udp 10.10.30.0 0.0.0.255 host 10.10.99.53 eq domain
DSW1(config-ext-nacl)# no 50
DSW1(config-ext-nacl)# exit
DSW1(config)# ip access-list resequence WIRELESS-IN 10 10
  • Line 15 is inserted between 10 and 20, so DNS to the future server (Chapter 22) is permitted before line 20 denies VLAN 99.
  • no 50 removes only that line.
  • resequence renumbers to 10, 20, 30 … so you have gaps for later inserts.

TrapIn global mode, no access-list 110 deny ip 10.10.30.0 0.0.0.255 10.10.99.0 0.0.0.255 deletes the whole ACL 110, not one line. If the ACL is applied to an interface, the interface then has no filter at all. Edit numbered ACLs through ip access-list extended 110 instead.

20.8 Protecting VTY lines with access-class

An ACL on an interface filters traffic through the device; it is awkward for filtering management access to the device, which can arrive on any of its addresses. access-class applies a (normally standard) ACL to the VTY lines, so it covers SSH to every IP address of the device:

DSW1
DSW1(config)# ip access-list standard MGMT-ONLY
DSW1(config-std-nacl)# 10 permit 10.10.99.0 0.0.0.255
DSW1(config-std-nacl)# 20 permit host 10.10.10.11
DSW1(config-std-nacl)# exit
DSW1(config)# line vty 0 15
DSW1(config-line)# access-class MGMT-ONLY in
  • access-class … in filters incoming SSH/Telnet sessions by source address. (access-class … out filters sessions started from the device, which is rarely used.)
  • A refused connection is closed immediately; the user sees "connection refused" before any login prompt.
  • Do not lock yourself out: check that the address you are connected from is permitted before you apply it, and keep console access.

20.9 Verification and troubleshooting

The output below is the original six-line ACL from 20.4, before the edits shown in 20.7.

DSW1
DSW1# show access-lists WIRELESS-IN
Extended IP access list WIRELESS-IN
    10 permit udp any any eq bootps (4 matches)
    20 deny ip 10.10.30.0 0.0.0.255 10.10.99.0 0.0.0.255 (3 matches)
    30 permit tcp 10.10.30.0 0.0.0.255 host 10.10.40.11 eq 631
    40 deny ip 10.10.30.0 0.0.0.255 10.10.40.0 0.0.0.255 (4 matches)
    50 permit icmp 10.10.30.0 0.0.0.255 any (8 matches)
    60 permit ip 10.10.30.0 0.0.0.255 any (112 matches)

DSW1# show ip interface vlan 30 | include access list
  Outgoing access list is not set
  Inbound  access list is WIRELESS-IN

Reading it: the match counters show which line each packet stopped at. Line 30 has no matches yet (nobody has printed); line 40 has 4 (the pings to the printer you tested). Counters for the implicit deny are not shown — packets that match no line are dropped silently. To count them, add your own last line deny ip any any log.

Command What it shows
show access-lists [name] All IPv4 (and IPv6) ACLs with sequence numbers and match counters
show ip access-lists [name] IPv4 ACLs only
show ip interface <if> Which ACL is applied, and in which direction
show running-config \| section vty access-class on the VTY lines
clear access-list counters [name] Reset counters before a test
log keyword on an ACE Syslog such as %SEC-6-IPACCESSLOGP: list WIRELESS-IN denied tcp 10.10.30.12(51234) -> 10.10.99.2(22), 1 packet

Troubleshooting method: (1) confirm the ACL is applied to the right interface in the right direction; (2) clear the counters; (3) send the test traffic; (4) see which line's counter rises; (5) if none rises, the packet hit the implicit deny or never reached this interface.

Symptom Likely cause Fix
Everything from the subnet blocked Only deny lines; implicit deny catches the rest Add the needed permit lines (often permit ip any any last)
A deny line never matches A broader permit above it matches first Move the specific line above the general one (sequence numbers)
ACL has no effect at all Not applied, applied to the wrong interface, or wrong direction show ip interface; apply in/out correctly
Hosts lose their DHCP lease after the ACL is applied No permit for UDP 67 before a deny permit udp any any eq bootps near the top
Too much is blocked; output shows a different address Wrong wildcard; IOS stored the address with the wildcard applied (for example 10.10.40.0 0.0.255.255 shows as 10.10.0.0 0.0.255.255) Recalculate the wildcard
Web works one way only, or replies blocked Port written on the wrong side (source vs destination) Put the port after the destination for traffic to a server
Policy disappears after a gateway failover ACL configured on only one HSRP/VRRP router Apply the same ACL on every router that can be the gateway
Whole numbered ACL vanished no access-list <n> … in global mode deleted all of it Re-create; edit numbered ACLs in ip access-list mode
Locked out of SSH access-class does not permit your source Console in and correct the ACL
Routing neighbours drop after an ACL is applied Routing protocol packets hit the implicit deny Permit them (for example permit ospf any any)

20.10 Lab 20.1 — Campus security policy with ACLs (Intermediate)

Objective: 4.6. Start from: your Lab 19.1 file (campus with R1, DSW1/DSW2 running HSRP, SW1/SW2, PC1, PC2, PC3, Printer1, AAA-1, FILES, ISP). Any recent Packet Tracer accepts ip access-group on a 3650 SVI and access-class on VTY lines.

Policy to implement (Figure 20.3):

  1. Wireless users (VLAN 30) must not reach the management VLAN 99 at all.
  2. Wireless users may reach Printer1 only for IPP printing (TCP 631); everything else to VLAN 40 is denied.
  3. Wireless users keep DHCP, ping and everything else (including the internet).
  4. Only VLAN 99 and the admin PC (PC1) may SSH to the switches.

In Figure 20.3 the coloured borders give each destination's result: green permitted, amber limited to one service, red denied. The tinted band at the bottom is the second ACL, which guards the switches themselves.

Step 1 — Check the starting point. From PC2 (VLAN 30): ipconfig (note the address), ping 10.10.40.11, ping 192.0.2.8, and from the Desktop SSH client ssh -l netadmin 10.10.99.2. All should work now. On PC1 run ipconfig and note its address; the steps below assume 10.10.10.11 — use yours if it differs.

Step 2 — WIRELESS-IN on DSW1 and DSW2. Enter the same ACL on both switches (they share the VLAN 30 gateway through HSRP, so either may be routing the traffic):

DSW1
DSW1(config)# ip access-list extended WIRELESS-IN
DSW1(config-ext-nacl)# remark Wireless users: DHCP, no management, printer by IPP only
DSW1(config-ext-nacl)# 10 permit udp any any eq bootps
DSW1(config-ext-nacl)# 20 deny ip 10.10.30.0 0.0.0.255 10.10.99.0 0.0.0.255
DSW1(config-ext-nacl)# 30 permit tcp 10.10.30.0 0.0.0.255 host 10.10.40.11 eq 631
DSW1(config-ext-nacl)# 40 deny ip 10.10.30.0 0.0.0.255 10.10.40.0 0.0.0.255
DSW1(config-ext-nacl)# 50 permit icmp 10.10.30.0 0.0.0.255 any
DSW1(config-ext-nacl)# 60 permit ip 10.10.30.0 0.0.0.255 any
DSW1(config-ext-nacl)# exit
DSW1(config)# interface vlan 30
DSW1(config-if)# ip access-group WIRELESS-IN in

Repeat on DSW2. Why each line: line 10 keeps DHCP working — a client's Discover has source 0.0.0.0, which the later lines would not match. Line 60 also matches the HSRP hellos that DSW2 (10.10.30.3) sends into VLAN 30 towards 224.0.0.102, so HSRP keeps running; without it, both switches would become Active. Line 50 is technically covered by line 60, but it gives ping its own counter for this lab.

Step 3 — MGMT-ONLY on the VTY lines of DSW1, DSW2, SW1 and SW2:

SW1
SW1(config)# ip access-list standard MGMT-ONLY
SW1(config-std-nacl)# 10 permit 10.10.99.0 0.0.0.255
SW1(config-std-nacl)# 20 permit host 10.10.10.11
SW1(config-std-nacl)# exit
SW1(config)# line vty 0 15
SW1(config-line)# access-class MGMT-ONLY in

Step 4 — Test from PC2 (clear the counters first with clear access-list counters on DSW1):

Test from PC2 Expected Line that decides
ping 10.10.40.11 (printer) Fails 40
ping 192.0.2.8 (ISP) Works 50
ssh -l netadmin 10.10.99.2 Fails (no login prompt) 20
ssh -l netadmin 10.10.30.2 (DSW1's own VLAN 30 address) Connection refused Passes WIRELESS-IN line 60, then MGMT-ONLY refuses it
ipconfig /release then ipconfig /renew New lease 10

Then run show access-lists on DSW1 and match each counter to a test. (Packet Tracer has no IPP client, so line 30 stays at zero; that is expected.)

Step 5 — Test management access. From PC1 ssh -l netadmin 10.10.99.2 works; from PC3 (also VLAN 10, different address) it is refused. Explain why the result differs for two PCs in the same VLAN.

Step 6 — Edit with sequence numbers. Chapter 22 adds a DNS server at 10.10.99.53. Prepare for it on both DSW1 and DSW2 without retyping the list:

DSW1
DSW1(config)# ip access-list extended WIRELESS-IN
DSW1(config-ext-nacl)# 15 permit udp 10.10.30.0 0.0.0.255 host 10.10.99.53 eq domain
DSW1(config-ext-nacl)# end
DSW1# show access-lists WIRELESS-IN

Confirm that 15 sits between 10 and 20, then ip access-list resequence WIRELESS-IN 10 10 and look again.

Step 7 — Failover test. On DSW1, interface vlan 30 → shutdown. DSW2 becomes HSRP Active for VLAN 30. Repeat the printer ping from PC2: it must still fail (the ACL on DSW2 now decides). no shutdown afterwards.

Start from: your finished Lab 20.1 file. Introduce one fault at a time (or ask a study partner to), describe the symptom from PC2, find the cause using only show commands, fix it, and restore before the next.

B ip access-list extended WIRELESS-IN → no 10 DSW1 and DSW2

Solutions

Their sources are not in 10.10.30.0/24 and DHCP replies go to port 68, so only the implicit deny matches: PC2 loses everything routed (and cannot renew its lease). Fix: apply it in.
  • B — DHCP permit removed. Existing leases keep working until renewal; ipconfig /renew then fails and PC2 ends up with a 169.254.x.x address. show access-lists shows no line 10. Fix: 10 permit udp any any eq bootps.

  • D — ACL on one gateway only. While DSW1 is Active everything looks correct; after the failover PC2 can ping the printer and VLAN 99 hosts such as AAA-1 (10.10.99.20); SSH to the switches is still refused by MGMT-ONLY. show standby brief on DSW2 shows Active, and show ip interface vlan 30 on DSW2 shows no inbound ACL. Fix: apply the same ACL on both HSRP routers.

20.12 Chapter 20 summary notes (exam revision)

  • Processing: top-down, first match wins, then stop; implicit deny any at the end; one ACL per interface, per direction, per protocol.
  • Wildcard: 0 = must match, 1 = ignore; wildcard = 255.255.255.255 − mask; host = 0.0.0.0, any = 0.0.0.0 255.255.255.255.
  • Standard (1–99, 1300–1999): source only, place near the destination. Extended (100–199, 2000–2699): protocol, source, destination, ports, place near the source.
  • Named: ip access-list {standard | extended} NAME, sequence numbers, insert (15 …), delete (no 15), ip access-list resequence.
  • Apply: ip access-group NAME {in | out} on the interface or SVI; access-class NAME in under line vty.
  • Ports: after the source = source port, after the destination = destination port. SSH 22, Telnet 23, DNS 53, DHCP 67/68, HTTP 80, HTTPS 443, SNMP 161, syslog 514.
  • Verify: show access-lists (counters), show ip interface (direction), clear access-list counters, log keyword.
  • Outbound ACLs do not filter traffic the device itself originates. With HSRP/VRRP, apply the same ACL on every possible gateway.

Common conceptual mistakes

Mistake Correct idea
"An ACL with only deny lines blocks just those hosts" The implicit deny blocks everything else too
"Wildcard masks are the same as subnet masks" They are inverted: 0 = match, 1 = ignore
"Put standard ACLs close to the source" Near the destination, or they block the source from everywhere
"no access-list 110 … removes one line" It deletes all of ACL 110
"An inbound SVI ACL also filters traffic inside the VLAN" Only routed traffic passes the SVI
"permit tcp any eq 80 any allows web browsing to servers" That matches source port 80 (replies from servers)
"Filtering SSH means putting an ACL on every interface" access-class on the VTY lines covers every address of the device

In global mode, no access-list 110 … deletes the whole ACL 110. The interface still references 110, but an applied ACL that does not exist permits everything. Re-create it, and edit numbered ACLs via ip access-list extended 110 → no <seq>.

What is wrong with permit tcp 10.10.30.0 0.0.0.255 eq 443 any if the goal is to let wireless users browse HTTPS sites?

Answer it in your head (or on paper) first.

Port 443 is written after the source, so it matches packets from source port 443. Users browse to port 443: permit tcp 10.10.30.0 0.0.0.255 any eq 443.
