Chapter 19Managing configurations and images with SCP and SFTP

🖼️ 2 figures⏱️ ~13 min read

Objective covered: 4.2 Manage device configuration and software files using secure file transfer operations with SFTP/SCP. You back up and restore configurations, copy software images, check them and boot from them — over encrypted, authenticated transfers.

19.1 Learning objectives

After this chapter you can:

  1. Navigate IOS file systems and use the copy command correctly.
  2. Explain why TFTP and FTP are unsuitable for production and what SCP and SFTP add.
  3. Configure an IOS device as an SCP server and use it as an SCP and SFTP client.
  4. Back up, restore and replace configurations safely.
  5. Upgrade a software image: check space, transfer, verify the hash, set the boot variable, reload.
  6. Troubleshoot failed transfers.

19.2 Files on an IOS device

File system Holds Survives reload?
flash: / bootflash: Software images, saved files, sometimes the configuration Yes
nvram: startup-config Yes
system: running-config (in RAM) No
usbflash0: USB stick, where present Yes 
DSW1# show file systems           ! every file system, size and free space
DSW1# dir flash:                  ! files, sizes, and bytes free at the bottom
DSW1# show version | include System image
System image file is "flash:packages.conf"

The copy command always reads source, then destination: copy <from> <to>. copy running-config startup-config saves; copy startup-config running-config merges the saved file into the running configuration (it does not erase lines that exist only in the running configuration).

On Catalyst 9000 and other IOS XE platforms the switch usually runs in install mode: it boots packages.conf, which points to package files expanded from the .bin image. Older devices run in bundle mode and boot the .bin directly. Both appear in show version.

19.3 Why not TFTP or FTP?

Protocol Transport Authentication Encryption Verdict
TFTP UDP 69 None None Labs, PXE/phone boot only; anyone can read or replace files
FTP TCP 20/21 Username and password in clear text None Avoid on untrusted networks
SCP SSH, TCP 22 SSH login (local or AAA) Yes Recommended; IOS can be server and client
SFTP SSH, TCP 22 SSH login Yes Recommended; IOS XE is an SFTP client only

SCP and SFTP both run inside SSH, so they reuse everything from Chapter 18: RSA keys, SSH version 2, local or AAA users.

19.4 SCP and SFTP: who starts the transfer?

There are two directions to think about (Figure 19.1):

  • The device is the server — an administrator's PC connects to the switch and pushes or pulls files. Only SCP works this way on IOS XE.
  • The device is the client — the switch connects to a file server (a Linux backup server, for example) with the copy command. Both SCP and SFTP work this way.

Figure 19.1 compares the two directions. The arrow shows which side opens the SSH connection; the grey panels hold the commands typed on that side.

IOS as an SCP server. SCP needs SSH (Chapter 18), and IOS must be able to check the user's privilege, so AAA exec authorization is required:

DSW1(config)# username netadmin privilege 15 algorithm-type scrypt secret N3t-Admin-2026
DSW1(config)# aaa new-model
DSW1(config)# aaa authentication login default local          ! or group <AAA servers> local
DSW1(config)# aaa authorization exec default local            ! required for SCP
DSW1(config)# ip scp server enable

From a Linux, macOS or Windows 10/11 PC with OpenSSH:

$ scp -O cat9k_iosxe.17.12.04.SPA.bin netadmin@10.10.99.2:flash:/cat9k_iosxe.17.12.04.SPA.bin   # push an image
$ scp -O netadmin@10.10.99.2:flash:/DSW1-2026-10-15.cfg .                                        # pull a saved file

The -O option matters: OpenSSH 9.0 and later use the SFTP protocol inside scp by default, which the IOS XE SCP server does not accept; -O selects the original SCP protocol. To pull the running configuration, save it to flash first (copy running-config flash:DSW1-2026-10-15.cfg).

IOS as an SCP or SFTP client. Credentials can go in the URL or be prompted for. Set the source address the server sees with ip ssh source-interface:

DSW1(config)# ip ssh source-interface Vlan99
DSW1# copy running-config scp://netadmin@10.10.99.30/backups/DSW1-2026-10-15.cfg
Address or name of remote host [10.10.99.30]?
Destination username [netadmin]?
Destination filename [backups/DSW1-2026-10-15.cfg]?
Password:
!
5124 bytes copied in 1.204 secs (4256 bytes/sec)

DSW1# copy running-config sftp://netadmin@10.10.99.30//backups/DSW1-2026-10-15.cfg
DSW1# copy scp://netadmin@10.10.99.30/images/cat9k_iosxe.17.12.04.SPA.bin flash:

Note the URL forms: scp://user@host/path, and sftp://user@host//path (the double slash marks an absolute path in Cisco's SFTP examples). Exact prompts vary by release. A password typed into a URL (user:password@host) is visible on screen and in history — let IOS prompt for it instead.

Sources: Cisco IOS Secure Copy configuration; Configuring SSH File Transfer Protocol, Catalyst 9300, IOS XE 17.10.

19.5 Backing up and restoring configurations

Goal Command Effect
Back up off the device copy running-config scp://netadmin@10.10.99.30/backups/DSW1-2026-10-15.cfg Encrypted copy on the backup server
Keep a local copy copy running-config flash:DSW1-2026-10-15.cfg File in flash for quick rollback
Add lines from a file copy scp://…/DSW1-snippet.cfg running-config Merges: adds and changes lines, deletes nothing
Return exactly to a saved state configure replace flash:DSW1-2026-10-15.cfg Replaces the running configuration, removing lines not in the file
Automatic versions archive → path flash:archive/$h- → write-memory Saves a numbered copy every time you write memory; list them with show archive

The merge-versus-replace difference is a classic trap: restoring a backup with copy … running-config onto a device that has extra, wrong configuration leaves the wrong lines in place.

19.6 Upgrading a software image

Figure 19.2 shows the full workflow. The steps:

Figure 19.2 runs left to right along the top, then back along the middle row. The highlighted hash check is the gate: the red dashed path sends a mismatched file back to be copied again before anything touches the boot settings.

  1. Choose the image from Cisco's software download site, matching the exact platform, and record its published SHA-512 (or MD5) hash.
  2. Check space: dir flash: — the bytes free must exceed the image size (install mode needs room to expand it too). Delete old images only after checking which one is running.
  3. Copy securely: copy scp://netadmin@10.10.99.30/images/cat9k_iosxe.17.12.04.SPA.bin flash: (or push it from a PC with scp -O).
  4. Verify integrity: verify /sha512 flash:cat9k_iosxe.17.12.04.SPA.bin and compare with Cisco's hash. A mismatch means corruption or tampering — delete and copy again.
  5. Point the device at it: - Bundle mode: boot system flash:cat9k_iosxe.17.12.04.SPA.bin, then copy running-config startup-config. - Install mode (Catalyst 9000): install add file flash:cat9k_iosxe.17.12.04.SPA.bin activate commit — it expands the packages, updates packages.conf and reloads.
  6. Back up the configuration first (19.5), and reload in a maintenance window.
  7. Confirm with show version (new version, uptime minutes) and normal operation; keep the old image until you are sure.

If the device cannot find a valid image at boot it drops to ROMMON (rommon 1 >), from where an image is booted manually — a reason to check show boot before every reload.

19.7 Verifying and troubleshooting transfers

Command Use it to check
show file systems, dir flash: Space and files
verify /sha512 flash:<file> (or /md5) Image integrity against the published hash
show boot / show bootvar Which image the next reload will use
show version Running image and how the device last booted
show ip ssh, show running-config \| include scp SSH version, SCP server enabled
debug ip scp Watch an SCP session (briefly)
Symptom Likely cause Fix
scp from a PC: connection closed or protocol error OpenSSH 9+ using SFTP mode scp -O
SCP to the device refused ip scp server enable missing, SSH not configured Configure SSH and enable the SCP server
"Permission denied" though the password is right User below privilege 15, or no aaa authorization exec Privilege 15 user; add exec authorization
Copy stops part-way Not enough flash dir flash:; delete unused files
Hash mismatch Corrupted or wrong file Copy again; check the filename and platform
Server never sees the connection Routing, ACL blocking TCP 22, wrong source address ip ssh source-interface; check ACLs (Chapter 20)
Restored backup, old wrong lines still present copy merged instead of replacing configure replace
Device boots to ROMMON after upgrade Boot variable points to a deleted or incomplete image Boot the image manually, fix boot system, save

19.8 Lab 19.1 — File management, from Packet Tracer to real SCP and SFTP (Intermediate)

Objective: 4.2. Packet Tracer limitation: Packet Tracer's file server offers TFTP and FTP only, and most versions do not accept SCP or SFTP in the copy command. Part A therefore practises the IOS file workflow with those protocols (and shows why they are insecure); Part B practises SCP and SFTP for real.

Part A — Packet Tracer (start from your Lab 18.1 file)

  1. Add a Server-PT FILES at 10.10.99.30/24, gateway 10.10.99.1, cabled to SW2 Fa0/5 (access VLAN 99). On it, check that TFTP and FTP are on (Services), and add an FTP user netadmin / Ftp-2026 with write permission.
  2. On DSW1, back up by TFTP and by FTP:
DSW1# copy running-config tftp:
Address or name of remote host []? 10.10.99.30
Destination filename [DSW1-confg]? DSW1-2026-10-15-tftp.cfg
DSW1# configure terminal
DSW1(config)# ip ftp username netadmin
DSW1(config)# ip ftp password Ftp-2026
DSW1(config)# end
DSW1# copy running-config ftp:
Address or name of remote host []? 10.10.99.30
Destination filename [DSW1-confg]? DSW1-2026-10-15-ftp.cfg
  1. See why FTP is unsafe: repeat the FTP copy in Simulation mode, filter on FTP and open the packets: the username and password appear readable. TFTP needed no password at all.
  2. Merge, not replace: on DSW1 add interface loopback 99 → ip address 10.255.99.1 255.255.255.255, then copy tftp: running-config from your backup. The loopback is still there — the copy merged. Remove it by hand with no interface loopback 99.
  3. Files and boot variables on SW1 (2960): dir flash:, show version | include image, copy a newer 2960 image from the server (copy tftp: flash: — Packet Tracer's server lists the images it holds), then boot system flash:<new image>, copy running-config startup-config, reload, and confirm with show version.
  4. If your Packet Tracer version accepts ip scp server enable and scp: in copy, repeat step 2 with SCP; otherwise continue with Part B.

Part B — real SCP and SFTP

  1. In your Linux VM (Lab 4.1) install an SSH server (sudo apt install openssh-server on Ubuntu), create ~/backups, and from your host computer:
scp notes.txt student@<vm-ip>:~/backups/          # copy to the VM
sftp student@<vm-ip>                              # interactive: ls, put, get, bye
sha512sum notes.txt                               # compare hashes on both sides
  1. With a real IOS device — a lab switch or router, or an IOS virtual node in Cisco Modeling Labs Free (check Cisco's site for the current free tier) — configure SSH and the SCP server (19.4), then from your computer scp -O a file to flash:, and from the device copy running-config scp://student@<vm-ip>/backups/R1.cfg and the same with sftp://. Verify with dir flash: and verify /sha512.

19.9 Chapter 19 summary notes (exam revision)

  • File systems: flash: (images, files), nvram: (startup-config), system: (running-config). show file systems, dir flash:. copy <source> <destination>.
  • TFTP UDP 69, no authentication; FTP TCP 20/21, clear-text credentials; SCP and SFTP run over SSH, TCP 22, authenticated and encrypted.
  • IOS SCP server: SSH + aaa new-model + aaa authentication login … + aaa authorization exec … + privilege 15 user + ip scp server enable. PC side: scp -O file user@device:flash:/file (OpenSSH 9+ needs -O).
  • IOS as client: copy running-config scp://user@host/path, copy running-config sftp://user@host//path, copy scp://… flash:; ip ssh source-interface. IOS XE is an SFTP client only.
  • Restore: copy … running-config merges; configure replace replaces. archive keeps versions.
  • Upgrade: pick image + hash → dir flash: → copy → verify /sha512 → boot system (bundle) or install add … activate commit (install mode) → back up → reload → show version. Bad boot variable → ROMMON.

Common conceptual mistakes

Mistake Correct idea
"copy tftp: running-config restores the old configuration exactly" It merges; use configure replace
"SCP and SFTP need extra ports opened" Both use SSH on TCP 22
"Any SSH user can SCP files" IOS requires exec authorization and normally privilege 15
"A successful copy means the image is good" Verify the hash against Cisco's published value
"IOS XE can be an SFTP server" It is an SFTP client; use SCP to push files to it

19.11 Answer key with explanations

  1. C and D. TFTP has no authentication or encryption; FTP and HTTP send credentials in clear text.
  2. TCP 22, inside SSH.
  3. aaa new-model, an authentication list (for example aaa authentication login default local), aaa authorization exec default local, and ip scp server enable.
  4. copy running-config scp://netadmin@10.10.99.30/backups/R1.cfg (enter the password when prompted).
  5. Copying a file into the running configuration merges it, so lines not in the file remain. Use configure replace <file> to return exactly to the saved state.
  6. dir flash: → copy the image → verify /sha512 → boot system flash:new.bin → copy running-config startup-config → reload.
  7. Use scp -O: newer OpenSSH uses SFTP inside scp, which the IOS SCP server does not accept.
  8. The user has privilege 1 (or exec authorization is missing). SCP needs aaa authorization exec and a privilege 15 user.
  9. To be sure the device will boot the intended, present and verified image; a wrong boot variable leaves it in ROMMON.
  10. B and C. IOS XE is an SFTP client only; TFTP has no username; FTP sends the password in clear text.
  11. Do not use it: delete the file, download it again from Cisco, copy it again and re-verify. A mismatch means corruption or tampering.
  12. No. TFTP has no authentication or encryption, so the configurations (with password hashes, keys and topology) cross the WAN readable and the server accepts writes from anyone. Use SCP or SFTP.
