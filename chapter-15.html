Chapter 15The troubleshooting toolkit

🖼️ 3 figures⏱️ ~20 min read

Objective covered: 2.4 Troubleshoot basic Layer 2/Layer 3 connectivity and device operations using show commands (including show logs), ping, extended ping, trace route, and packet capture output. This chapter gathers the tools you have used one at a time since Chapter 1 into one method, and adds extended ping, traceroute in depth and reading packet captures.

15.1 Learning objectives

After this chapter you can:

  1. Follow a structured troubleshooting method instead of guessing.
  2. Choose the right show command for each layer and for device health.
  3. Read IOS log messages and know which ones matter.
  4. Interpret ping and extended ping results, including every IOS result symbol.
  5. Explain how traceroute works and read its output, including timeouts and loops.
  6. Read packet capture output for ARP, ICMP, TCP and DHCP.
  7. Work a realistic trouble ticket from symptom to fix.

15.2 A troubleshooting method

Random changes create new faults and hide the original one. Use the same steps every time:

  1. Define the problem precisely. Who is affected, what fails (all traffic, one application, one destination), since when, what changed.
  2. Gather facts with show commands, logs, ping and traceroute — before touching the configuration.
  3. Compare with the baseline: documentation (Chapter 8), saved configurations, how it worked yesterday.
  4. Form a hypothesis that explains all the symptoms.
  5. Change one thing, and record what you changed.
  6. Verify the fix from the user's point of view; if it did not work, undo the change.
  7. Document the cause and the fix.

Approaches to narrowing it down:

Approach How Best when
Bottom-up Physical → data link → network → transport → application Hardware or cabling suspected; new installations
Top-down Application first, then down the stack One application fails, everything else works
Divide and conquer Start at Layer 3 with ping; success → look higher, failure → look lower Most general problems — the usual CCNA choice
Follow the path Check each device hop by hop from source to destination (and back) Multi-hop routing faults
Compare Diff a working device or configuration against the broken one Many similar devices (access switches, branches)

15.4 Reading logs with show logging

IOS records events — interfaces going up or down, neighbors forming, errors — as log messages. On the console you see them as they happen; remotely (SSH) you see them only after terminal monitor; and show logging lists those kept in the logging buffer in RAM.

DSW1# show logging
Syslog logging: enabled (0 messages dropped, 0 flushes, 0 overruns)
    Console logging: level debugging, 212 messages logged
    Buffer logging:  level informational, 188 messages logged
Log Buffer (16384 bytes):
*Oct 15 10:02:13.457: %LINK-3-UPDOWN: Interface GigabitEthernet1/0/2, changed state to down
*Oct 15 10:02:14.461: %LINEPROTO-5-UPDOWN: Line protocol on Interface GigabitEthernet1/0/2, changed state to down
*Oct 15 10:02:14.470: %EC-5-UNBUNDLE: Interface Gi1/0/2 left the port-channel Port-channel2
*Oct 15 10:05:40.112: %SYS-5-CONFIG_I: Configured from console by admin on vty0 (10.10.99.50)

Every message has the same structure (Chapter 25 covers syslog servers and severities in full):

Part Example Meaning
Timestamp *Oct 15 10:02:13.457 When; * means the clock is not synchronised (NTP)
Facility LINEPROTO The part of IOS that raised it
Severity 5 0 (emergency) to 7 (debugging); lower is more serious
Mnemonic UPDOWN Short code for the event
Description Line protocol on Interface … Human-readable detail

Messages worth recognising:

Message Points to Chapter
%LINK-3-UPDOWN / %LINEPROTO-5-UPDOWN Physical link / line protocol changed state 1
%CDP-4-DUPLEX_MISMATCH Duplex mismatch with the neighbor 1, 8
%CDP-4-NATIVE_VLAN_MISMATCH Native VLAN differs on a trunk 5
%PM-4-ERR_DISABLE Port err-disabled (BPDU guard, port security, channel misconfiguration) 6, 9, 23
%SPANTREE-2-BLOCK_BPDUGUARD, %SPANTREE-2-ROOTGUARD_BLOCK STP protection acted 9
%SW_MATM-4-MACFLAP_NOTIF A MAC address moving between ports: likely a loop 9
%IP-4-DUPADDR Duplicate IP address on the segment 2
%OSPF-5-ADJCHG OSPF neighbor state changed 12
%HSRP-5-STATECHANGE HSRP role changed 13
%SYS-5-CONFIG_I Someone changed the configuration — and who 18

Useful logging settings (global configuration): service timestamps log datetime msec (real dates in messages), logging buffered 16384 informational (bigger buffer), and on the console line logging synchronous (messages no longer interrupt your typing).

15.5 Ping

ping sends ICMP Echo Request (type 8) messages and waits for Echo Reply (type 0). A reply proves the whole path works in both directions at Layer 3.

DSW1# ping 10.10.40.11
Type escape sequence to abort.
Sending 5, 100-byte ICMP Echos to 10.10.40.11, timeout is 2 seconds:
.!!!!
Success rate is 80 percent (4/5), round-trip min/avg/max = 1/1/2 ms

The first . is normal: the router was waiting for an ARP reply before it could send the first packet.

IOS symbol Meaning Usual cause
! Echo Reply received Success
. Timed out No route on the way or the way back, a filter dropping silently, host down, ARP pending (first packet)
U ICMP Destination Unreachable received A router on the path has no route, or an ACL rejected it
Q Source quench Congestion (rare today)
M Could not fragment Packet too big with DF set: an MTU problem
? Unknown packet type received Unexpected ICMP reply
& Packet lifetime exceeded TTL expired: a routing loop

Windows prints Reply from …, Request timed out., or Reply from 10.0.0.1: Destination host unreachable. — the last one comes from a router, not the target, and tells you which router gave up.

15.6 Extended ping

A plain ping from a router uses the exit interface's address as the source. That hides return-path problems: the far end may know how to reach the link subnet but not your LANs (Chapter 11). Extended ping lets you choose the source, size, count and other options.

Interactive form (privileged EXEC, type ping with no address):

DSW2# ping
Protocol [ip]:
Target IP address: 10.10.40.11
Repeat count [5]: 20
Datagram size [100]: 1500
Timeout in seconds [2]:
Extended commands [n]: y
Source address or interface: vlan 10
Type of service [0]:
Set DF bit in IP header? [no]: yes
Validate reply data? [no]:
Data pattern [0x0000ABCD]:
Loose, Strict, Record, Timestamp, Verbose[none]:
Sweep range of sizes [n]:
Sending 20, 1500-byte ICMP Echos to 10.10.40.11, timeout is 2 seconds:
Packet sent with a source address of 10.10.10.3
Packet sent with the DF bit set
!!!!!!!!!!!!!!!!!!!!
Success rate is 100 percent (20/20), round-trip min/avg/max = 1/2/4 ms

One-line form (same result): ping 10.10.40.11 source vlan 10 repeat 20 size 1500 df-bit.

Option Why you would change it
Source address or interface Test the return route to a specific LAN — the most important option
Repeat count Catch intermittent loss (100 or 1000 pings)
Datagram size + DF bit Find MTU problems: large DF packets fail with M while small ones succeed
Sweep range of sizes Find the exact largest size that passes
Timeout Slow links (satellite, congested WAN)

Reading a pair of results. From DSW2, ping 10.10.40.11 succeeds but ping 10.10.40.11 source vlan 10 fails: the printer can reach DSW2's VLAN 40 address (same subnet) but cannot answer a VLAN 10 address — so its default gateway is wrong or missing. Lab 15.1 uses exactly this test.

15.7 Traceroute

Ping says whether a destination answers; traceroute shows the path and where it stops. It relies on the TTL field (Figure 15.2):

Figure 15.2 runs top to bottom in time. Each probe travels one router further than the last before its TTL runs out, and the router where it dies reveals itself in the reply.

  1. The source sends probes with TTL 1. The first router decrements TTL to 0, drops the probe and returns ICMP Time Exceeded from its own address — that is hop 1.
  2. Probes with TTL 2 reach the second router, which returns Time Exceeded — hop 2.
  3. TTL keeps rising until a probe reaches the destination, which answers differently (ICMP Port Unreachable for UDP probes, Echo Reply for ICMP probes) and the trace ends.
  4. Each hop is normally probed three times, so you see three round-trip times per line.
Implementation Probe type
Cisco IOS traceroute UDP to high ports (starting at 33434)
Linux / macOS traceroute UDP by default (-I for ICMP)
Windows tracert ICMP Echo Request 
C:\> tracert 192.0.2.8
Tracing route to 192.0.2.8 over a maximum of 30 hops
  1     1 ms    <1 ms    <1 ms  10.10.10.2
  2     1 ms     1 ms     1 ms  10.0.0.1
  3     2 ms     1 ms     1 ms  192.0.2.8
Trace complete.

Note hop 1: the real address of DSW1 (10.10.10.2), not the HSRP virtual IP — the Active router answers from its own interface address.

DSW1# traceroute 10.20.20.1
Type escape sequence to abort.
Tracing the route to 10.20.20.1
  1 10.0.0.1 1 msec 1 msec 0 msec
  2 198.51.100.1 1 msec 1 msec 1 msec
  3 198.51.100.2 2 msec 1 msec 1 msec
  4 198.51.100.1 2 msec 2 msec 1 msec
  5 198.51.100.2 2 msec 2 msec 2 msec
  ...

The same two addresses alternating is a routing loop: R1 sends 10.20.20.0/24 to the ISP by its default route, and the ISP sends it back by its 10.0.0.0/8 route. Neither has a specific route, so the packet bounces until TTL expires.

Traceroute shows Meaning
* No reply within the timeout for that probe
* * * from some hop onward The path stops there: the next router has no route, a filter drops probes, or replies cannot get back
!H / !N / !P Host / network / protocol unreachable returned
!A Administratively prohibited — an ACL rejected it (Chapter 20)
Repeating addresses Routing loop
Final hop never reached, but ping works Probes (UDP high ports) filtered while ICMP Echo is allowed

Traceroute shows the forward path only. The return path may differ (asymmetric routing), so a stop at hop n can also mean hop n cannot route its Time Exceeded back to you.

Figure 15.3 groups the nine frames into conversations, each with its verdict. The amber pair is the one that matters for a "cannot print" ticket: the network works, the printer's raw-print service on port 9100 does not.

Patterns to recognise:

You see It means
ARP request, no reply Target not on this subnet/VLAN, down, or wrong VLAN
ARP reply with 0000.0c9f.fXXX / 0000.0c07.acXX The gateway is an HSRP virtual IP (Chapter 13)
Echo request, no reply Path or return path broken, or ICMP filtered
TTL in a reply lower than expected Count the hops: 255 → 253 means two routers decremented it
TCP SYN → RST Host reachable, but nothing listens on that port: an application issue, not a network one
TCP SYN repeated, no answer Filtered (ACL, firewall) or no route back
SYN, SYN-ACK, ACK Connection established (three-way handshake)
DHCP Discover repeated, no Offer DHCP problem (Chapter 14)
Many identical broadcasts per second Broadcast storm: a loop (Chapter 9)

15.9 Which tool finds which fault

Fault First symptom Tool that proves it
Cable unplugged / bad down/down show ip interface brief, show interfaces status
Port err-disabled err-disabled status show interfaces status err-disabled, show logging
Host in the wrong VLAN Wrong subnet from DHCP, or no address show vlan brief, show mac address-table address <mac>
VLAN missing on a trunk Hosts in one VLAN cannot cross switches show interfaces trunk (allowed / forwarding lists)
Host's gateway wrong Same-subnet pings work, other subnets fail ipconfig /all; extended ping from the far side
Route missing on the return path Ping from the router works, from the LAN fails Extended ping with source; show ip route on each hop
Routing loop & / TTL expired; traceroute repeats hops traceroute, show ip route <dest>
ACL blocking U or !A, or silence for one protocol only show access-lists counters (Chapter 20), capture
Application not listening Ping works, TCP gets RST Packet capture
Loop / broadcast storm High CPU, MAC flapping show processes cpu sorted, show logging (MACFLAP)

15.12 Chapter 15 summary notes (exam revision)

  • Method: define → gather facts → compare with baseline → hypothesis → change one thing → verify → document. Divide and conquer starts with ping at Layer 3.
  • Device health: show version (uptime, reload reason, image), show processes cpu sorted, show environment. Filter with | include, | section, | begin, | exclude.
  • Logs: show logging; format timestamp %FACILITY-SEVERITY-MNEMONIC: text; terminal monitor for SSH sessions. Know UPDOWN, ERR_DISABLE, BPDUGUARD, MACFLAP, DUPADDR, ADJCHG, STATECHANGE, CONFIG_I.
  • Ping symbols: ! reply, . timeout, U unreachable, Q source quench, M cannot fragment, ? unknown, & TTL exceeded. First . = ARP.
  • Extended ping: choose source, repeat, size, DF bit, sweep. One line: ping <dst> source <int|ip> repeat <n> size <n> df-bit. Proves return routes and MTU.
  • Traceroute: TTL 1, 2, 3…; Time Exceeded names each hop; IOS/Linux use UDP high ports, Windows ICMP. * = timeout; repeating hops = loop; !A = ACL; forward path only.
  • Captures: SPAN, Embedded Packet Capture, Wireshark, Packet Tracer Simulation. SYN→RST = nothing listening; SYN with no reply = filtered or no route back.

Common conceptual mistakes

Mistake Correct idea
"A successful ping from the router proves users can reach it" It used the router's link address; test with source the users' subnet
"The first . in a ping means packet loss" Usually the ARP wait
"Traceroute shows the return path" It shows the forward path only
"* * * means that router is down" It may simply not reply to probes, or its replies cannot return
"A TCP RST means the network is broken" The SYN arrived; the host refused the port

15.14 Answer key with explanations

  1. Each probe was answered by an ICMP Destination Unreachable: a router on the path has no route to the destination (or an ACL rejects it).
  2. C. M = could not fragment. ! success, . timeout, & TTL exceeded.
  3. A plain ping uses DSW2's VLAN 40 address, which the printer can answer as a neighbor. Sourcing from VLAN 10 tests whether the printer can return traffic to another subnet — which depends on its default gateway (and on the routes back).
  4. It sends probes with TTL 2. Hop 1 decrements to 1 and forwards; hop 2 decrements to 0, drops the probe and returns ICMP Time Exceeded from its own address.
  5. The next router has no route onward; a firewall or ACL drops the probes or the ICMP replies; the next router cannot route its replies back to the source. (Also: devices configured not to send Time Exceeded.)
  6. A routing loop: each router points to the other for that destination, and the probe bounces until TTL expires.
  7. Facility LINEPROTO, severity 5 (notification). Layer 2 line protocol on Gi1/0/2 went down — check the cable, the far end, or keepalive problems.
  8. Log messages go to the console by default; a VTY session needs terminal monitor (privileged EXEC).
  9. The SYN gets no answer: it is filtered (ACL or firewall) or lost on the way, or the server's reply has no route back. The host may also be down.
  10. The network delivered the SYN and the host replied: the host is reachable but nothing is listening on that port (service stopped, wrong port).
  11. show version (uptime and last reload reason).
  12. A and C. Lower layers clearly work for other applications, so start at the application; comparing with a working client isolates client-specific settings. D and E are random changes.
  13. show running-config | section interface Vlan10.
  14. The ping came from the router's own address, not from the user's subnet, so it proves neither the user's path nor the return route to the user's subnet, nor that the application port is reachable. Test from (or sourced from) the user's subnet, then check the port with a capture or a TCP test.
