# Chapter 3 — IPv6 addressing and prefix sizing

CCNA-style practice questions for [Chapter 3](../CCNA%20200-301%20v2.0%20Study%20Guide.md#chapter-3--ipv6-addressing-and-prefix-sizing) · Domain 1 · Objective 1.4. The format is described in the [question bank README](README.md).

## Questions

### Q1 · Multiple choice
<sub>Source: 3.3</sub>

Which is the shortest valid form of the IPv6 address 2001:0db8:0000:00a0:0000:0000:0000:0100?

- [ ] 2001:db8::a0:0:0:0:100
- [x] 2001:db8:0:a0::100
- [ ] 2001:db8::a0::100
- [ ] 2001:db8:0:a::1

> **Explanation:** First drop the leading zeros in each hextet: 2001:db8:0:a0:0:0:0:100. Then replace one run of zero hextets with `::`, choosing the **longest** run (the three zeros before 100, not the single zero after db8): 2001:db8:0:a0::100. Putting `::` on the single zero hextet gives a valid but longer address. Using `::` twice is invalid because the length becomes ambiguous. Only **leading** zeros may be dropped, so 00a0 becomes a0 (not a) and 0100 becomes 100 (not 1).

### Q2 · Multiple choice
<sub>Source: 3.6, 3.10</sub>

Refer to the exhibit.

```
R2# show running-config interface gigabitethernet0/0/1 | include ipv6
 ipv6 address 2001:DB8:ACAD:20::/64 eui-64
R2# show interfaces gigabitethernet0/0/1 | include bia
  Hardware is ISR4331-3x1GE, address is 5c5a.c7e1.0a21 (bia 5c5a.c7e1.0a21)
```

Which global unicast address does R2 build for GigabitEthernet0/0/1?

- [x] 2001:db8:acad:20:5e5a:c7ff:fee1:a21
- [ ] 2001:db8:acad:20:5c5a:c7ff:fee1:a21
- [ ] 2001:db8:acad:20:5a5a:c7ff:fee1:a21
- [ ] fe80::5e5a:c7ff:fee1:a21

> **Explanation:** Modified EUI-64: split the MAC (5c5a.c7 | e1.0a21), insert FFFE in the middle (5c5a:c7ff:fee1:0a21), then **flip** the 7th bit of the first byte. 5c = 0101 1100; that bit is 0, so it becomes 1: 0101 1110 = 5e (the "add 2" trick). The interface ID 5e5a:c7ff:fee1:a21 is appended to the /64 prefix. Leaving 5c unchanged skips the flip, and subtracting 2 (5a) is only correct when the bit is already 1. The fe80:: address is the automatic EUI-64 link-local address (no `link-local` command appears in the exhibit), not the global unicast address.

### Q3 · Multiple choice — choose two
<sub>Source: 3.8</sub>

R1 sends Router Advertisements on the VLAN 10 link for 2001:db8:acad:10::/64 with the flags A=1, O=1 and M=0. A stateless DHCPv6 server is available. Which two statements describe how PC1 in VLAN 10 gets its IPv6 settings? (Choose two.)

- [x] PC1 builds its own global address from the advertised prefix with SLAAC.
- [x] PC1 learns its DNS server addresses from the DHCPv6 server.
- [ ] PC1 learns its default gateway from the DHCPv6 server.
- [ ] The DHCPv6 server assigns PC1's global address and keeps track of it.
- [ ] PC1 keeps only its link-local address because the O flag turns SLAAC off.

> **Explanation:** A=1, O=1, M=0 is **stateless DHCPv6** (SLAAC + DHCPv6): the host builds its address from the RA's prefix and its own interface ID, and asks the DHCPv6 server only for other information such as DNS. Address assignment by the server is stateful DHCPv6 (M=1). The default gateway always comes from the Router Advertisement — DHCPv6 never gives a gateway. The O flag adds DHCPv6 for other settings; it does not disable SLAAC.

### Q4 · Drag and drop — match
<sub>Source: 3.5</sub>

Drag each IPv6 address to its address type.

| Address | Type |
| --- | --- |
| 2001:db8:acad:40::200 | Global unicast |
| fe80::2d0:97ff:fe12:3401 | Link-local |
| fd7a:91c2:44e0:10::20 | Unique local |
| ff02::1:ff00:200 | Multicast |
| ::1 | Loopback |
| :: | Unspecified |

**Extra targets:** Broadcast

> **Explanation:** Global unicast addresses come from 2000::/3 (they start with 2 or 3). Link-local addresses use fe80::/10 and never leave the link. Unique local addresses use fc00::/7, in practice fd00::/8. Anything starting with ff is multicast; ff02::1:ff00:200 is the solicited-node group for an address ending in ::200. ::1 is the loopback (like 127.0.0.1) and :: is the unspecified address a host uses as a source before it has an address. IPv6 has no broadcast addresses at all.

### Q5 · Drag and drop — match
<sub>Source: 3.4</sub>

Drag the recommended prefix length to each use. Not every prefix length is used.

| Use | Prefix length |
| --- | --- |
| Block an ISP receives from a registry | /32 |
| One enterprise site | /48 |
| Small business or home site from an ISP | /56 |
| Every LAN or VLAN | /64 |
| Point-to-point link between R1 and R2 | /127 |
| Loopback interface | /128 |

**Extra targets:** /80 · /120

> **Explanation:** A /48 site leaves 16 bits of subnet ID, so it holds 2^16 = 65,536 /64 subnets; a /56 leaves 8 bits, or 256 /64s. Every LAN uses a /64 because SLAAC and EUI-64 need a 64-bit interface ID — longer prefixes such as /80 or /120 break SLAAC. Point-to-point router links use /127 (two addresses, recommended by RFC 6164), and loopbacks and host routes use /128 (one address).

### Q6 · Drag and drop — order
<sub>Source: 3.9</sub>

PC1 joins the Staff VLAN and configures itself with SLAAC. R1 is the router on the link. Drag the steps into the order in which they happen.

1. PC1 creates a link-local address and checks it with DAD
2. PC1 sends a Router Solicitation to ff02::2
3. R1 replies with a Router Advertisement for 2001:db8:acad:10::/64 with A=1, M=0 and O=0
4. PC1 combines the /64 prefix with an interface ID
5. PC1 sends a Neighbor Solicitation for its new global address
6. PC1 uses its global address, with fe80::1 as its default gateway

> **Explanation:** A host always builds and tests its link-local address first, because it needs a source address on the link. It then sends an RS to all routers (ff02::2) instead of waiting for the next periodic RA. The RA carries the prefix, the flags and R1's link-local address as the gateway. PC1 adds an interface ID (EUI-64 or random) to the prefix, runs DAD on the new global address (an NS for its own address; no NA means it is unique), and only then uses it — no DHCP server is involved.

<sub>Source: 3.11, 3.12</sub>

   IPv4 Address. . . . . . . . . . . : 172.16.0.150(Preferred)
   Subnet Mask . . . . . . . . . . . : 255.255.255.192
   Default Gateway . . . . . . . . . : 2001:db8:acad:10::1
                                       172.16.0.129
```

A technician configured the IPv6 settings of PC2, in VLAN 30 (2001:db8:acad:30::/64), by hand. Router discovery is disabled on PC2's adapter, so PC2 uses only the gateway typed by hand. PC2 can reach IPv6 hosts in its own subnet but no remote IPv6 address, while IPv4 works. Other hosts in VLAN 30 reach remote IPv6 subnets normally through R1, whose link-local address on VLAN 30 is fe80::1. What fixes the problem?

- [x] Change PC2's IPv6 default gateway to fe80::1
- [ ] Change PC2's IPv6 default gateway to 2001:db8:acad:30::50
- [ ] Enable DHCPv6 on PC2's adapter so that it learns its gateway
- [ ] Enter `ipv6 unicast-routing` on R1

> **Explanation:** 2001:db8:acad:10::1 is R1's address on the VLAN 10 subnet, not on PC2's link, so PC2 cannot use it as a next hop. The gateway must be an address of the router on the host's own link — normally its link-local address fe80::1, which Windows then shows with a zone index (fe80::1%7); R1's global 2001:db8:acad:30::1 would also work. 2001:db8:acad:30::50 is PC2's own address, not a router. DHCPv6 never provides a default gateway; the gateway comes from the RA or is typed by hand. R1 is already routing for the other VLAN 30 hosts, so `ipv6 unicast-routing` is present.

### Q8 · Multiple choice
<sub>Source: 3.5, 3.7</sub>

PC1 must send a packet to SRV1 at 2001:db8:acad:10::a5:3f1e on the same link. SRV1 is not yet in PC1's NDP cache. Which message does PC1 send to learn SRV1's MAC address?

- [x] A Neighbor Solicitation sent to ff02::1:ffa5:3f1e
- [ ] A Neighbor Solicitation sent to ff02::1:ff00:3f1e
- [ ] An ARP request sent to FFFF.FFFF.FFFF
- [ ] A Router Solicitation sent to ff02::2
- [ ] A Neighbor Advertisement sent to ff02::1

> **Explanation:** IPv6 has no ARP and no broadcast. NDP replaces the ARP request with a Neighbor Solicitation (ICMPv6 type 135) sent to the target's **solicited-node** multicast address: ff02::1:ff followed by the last 24 bits of the target address. The last two hextets 00a5:3f1e give the 24 bits a5:3f1e, so the group is ff02::1:ffa5:3f1e (using only the last 16 bits is a common slip). SRV1 answers with a Neighbor Advertisement (type 136). A Router Solicitation looks for routers, not neighbors.

R2# show running-config | include ipv6|interface

 ipv6 address 2001:DB8:ACAD:50::1/64

    inet6 fe80::5a2b:9cff:fe40:1d07/64 scope link
       valid_lft forever preferred_lft forever
pc3:~$ ip -6 route
fe80::/64 dev eth0 proto kernel metric 256 pref medium
```

R2 is newly installed between two LANs that use SLAAC: 2001:db8:acad:50::/64 on G0/0/0 and 2001:db8:acad:60::/64 on G0/0/1. Both interfaces are up/up. PC3 is a Linux host in the first LAN, and hosts in the second LAN show the same result. Enter the command on R2 that fixes the problem.

**Prompt:** `R2(config)#`

**Accepted:** `ipv6 unicast-routing`

> **Explanation:** Without `ipv6 unicast-routing` the router does not act as an IPv6 router: it does not forward IPv6 between interfaces, does not join the all-routers group FF02::2 and sends no Router Advertisements. The exhibit shows correct /64 addresses on both LAN interfaces, but the filtered running-config has no `ipv6 unicast-routing` line. Interfaces still get their addresses, but SLAAC hosts receive no prefix and no gateway, so PC3 keeps only its `scope link` address and has no `default via` route. Once the command is entered, `show ipv6 interface` lists FF02::2 among the joined groups.

### Q10 · Multiple choice
<sub>Source: 3.9, 3.12</sub>

Why do the sensors build no global address?

- [x] The prefix on G0/0/2 is /80, and SLAAC needs a /64 prefix to add a 64-bit interface ID.
- [ ] `ipv6 unicast-routing` is missing, so R1 sends no Router Advertisements.
- [ ] The RA has the O flag set, so the sensors wait for a DHCPv6 server before they use SLAAC.
- [ ] The RA has the M flag set, so the sensors wait for a stateful DHCPv6 server.

> **Explanation:** The exhibit shows `subnet is 2001:DB8:ACAD:40::/80`. A SLAAC host must append a 64-bit interface ID, so a /80 prefix (which leaves only 48 bits) cannot be used for autoconfiguration. FF02::2 is joined, so `ipv6 unicast-routing` is on and R1 sends RAs. The O flag only tells hosts to ask DHCPv6 for other information such as DNS; it does not stop SLAAC. The last line of the output shows that hosts are told to use stateless autoconfig for addresses, not a DHCPv6 server.

### Q11 · CLI
<sub>Source: 3.10, 3.13</sub>

You are in interface configuration mode for G0/0/2, and the address currently shown in the exhibit has already been removed. Enter the interface command that corrects G0/0/2 so that the sensors can autoconfigure, keeping the router address shown in the exhibit. Type the address in its shortest form.

**Prompt:** `R1(config-if)#`

**Accepted:** `ipv6 address 2001:db8:acad:40::1/64`

> **Explanation:** The exhibit shows 2001:DB8:ACAD:40::1 with a /80 prefix; SLAAC needs /64, so the router keeps ::1 and changes only the prefix length. IPv6 addresses are entered with the prefix length after a slash, not with an IPv4-style mask. Using the `eui-64` keyword would build the interface ID from the MAC instead of ::1, so the router would no longer use the address that hosts and documentation expect. Removing the /80 address first (`no ipv6 address 2001:db8:acad:40::1/80`) matters: unlike IPv4, a new `ipv6 address` command adds another address instead of replacing the existing one, so leaving the old address in place is a common mistake when changing a prefix length.

### Q12 · Multiple choice — choose two
<sub>Source: 3.8, 3.9</sub>

After the fix, which two statements describe the SLAAC sensors in VLAN 40? (Choose two.)

- [x] Each sensor builds a global address in 2001:db8:acad:40::/64 by adding its own 64-bit interface ID.
- [x] The sensors use fe80::1, learned from R1's Router Advertisements, as their default gateway.
- [ ] The sensors use 2001:db8:acad:40::1, learned from a DHCPv6 server, as their default gateway.
- [ ] The sensors receive their global addresses from a stateful DHCPv6 server.
- [ ] Each sensor checks its new address with an ARP request before using it.

> **Explanation:** With a /64 prefix and hosts told to use stateless autoconfig for addresses (not DHCPv6), the sensors combine the advertised prefix with their own interface ID. The default gateway always comes from the RA, and hosts normally use the router's link-local address — the source of the RA — as the gateway. No DHCPv6 server is involved here, and DHCPv6 never provides a gateway anyway. Duplicate Address Detection uses a Neighbor Solicitation for the host's own address; IPv6 has no ARP.
