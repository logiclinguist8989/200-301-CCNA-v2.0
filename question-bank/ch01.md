### Q2 · Multiple choice
<sub>Source: 1A.4</sub>

PC1 (10.10.10.11) opens a web page on a server at 203.0.113.80. Which destination MAC address does PC1 put in the Ethernet frame it sends?

- [ ] The web server's MAC address
- [x] The MAC address of PC1's default gateway
- [ ] FFFF.FFFF.FFFF
- [ ] The MAC address of the access switch port

> **Explanation:** The server is on another network, so the frame only has to reach the next hop: the default gateway (R1). The IP destination stays 203.0.113.80 end to end; the MAC addresses are rewritten at every router hop. Switches forward frames without being the destination.

### Q3 · Multiple choice — choose two
<sub>Source: 1A.7</sub>

Which two statements describe how a Layer 2 switch builds and uses its MAC address table? (Choose two.)

- [x] It learns MAC addresses from the source address of received frames.
- [x] It floods a frame with an unknown unicast destination out every port in the VLAN except the one it arrived on.
- [ ] It learns MAC addresses from the destination address of received frames.
- [ ] It drops frames whose destination MAC address is not in the table.
- [ ] Dynamic entries stay in the table until the switch reloads.

> **Explanation:** Learning always uses the **source** MAC; forwarding decisions use the **destination** MAC. Unknown unicast, broadcast and (by default) multicast frames are flooded within the VLAN. Dynamic entries age out after 300 seconds by default.

### Q4 · Drag and drop — order
<sub>Source: 1A.3, 1A.4</sub>

Drag the protocol data units into the order in which a sending host creates them, from the application down to the wire.

1. Data
2. Segment
3. Packet
4. Frame
5. Bits

> **Explanation:** Application data is wrapped by Transport into a **segment**, by Network into a **packet**, by Data Link into a **frame**, and turned into **bits** by the Physical layer. Memory trick from Layer 4 down: *Some People Fear Birthdays*.

### Q5 · Drag and drop — match
<sub>Source: 1B.4</sub>

None of the devices support auto-MDIX. Drag the correct cable type to each connection. A cable type can be used more than once.

| Connection | Cable |
| --- | --- |
| PC to access switch | Straight-through |
| Router Ethernet port to switch | Straight-through |
| Switch to switch | Crossover |
| PC to router Ethernet port | Crossover |
| Laptop to a router's console port | Rollover |

> **Explanation:** PCs and routers are MDI; switches are MDI-X. Unlike devices (PC or router to switch) use straight-through; like devices (switch–switch, PC–router, PC–PC) use crossover. The console port uses a rollover cable.

### Q6 · Drag and drop — match
<sub>Source: 1B.9</sub>

Drag each interface symptom to its most likely cause.

| Symptom | Cause |
| --- | --- |
| Late collisions rising on a half-duplex port | Duplex mismatch |
| CRC errors rising on a full-duplex port with zero collisions | Damaged or over-length cable |
| Giants rising after a jumbo-frame change on one end | MTU mismatch |
| Output drops rising while error counters stay at zero | Congestion |

**Extra targets:** Speed mismatch

> **Explanation:** Late collisions are the classic duplex-mismatch signature. CRC errors with clean collision counters point to the physical path (cable length, damage, EMI). Giants are frames above the maximum size, typically an MTU mismatch. Output drops mean the queue was full, which is congestion, not a cable fault. A speed mismatch leaves the link down, so it would not produce rising counters.

### Q7 · Multiple choice
<sub>Source: 1B.6</sub>

Refer to the exhibit.

```
DSW1# show interfaces transceiver
                                          Optical   Optical
           Temperature  Voltage  Current  Tx Power  Rx Power
Port       (Celsius)    (Volts)  (mA)     (dBm)     (dBm)
---------  -----------  -------  -------  --------  --------
Gi1/1/3      35.2        3.30     40.1      2.1       1.4 ++
```

Gi1/1/3 connects to a switch in the same rack over a 3 m single-mode patch cable, using long-reach optics on both ends. What should the engineer do?

- [ ] Clean the LC connectors on both ends
- [x] Add an attenuator or use shorter-reach optics
- [ ] Replace the single-mode patch cable with multimode fiber
- [ ] Swap the Tx and Rx strands on one end

> **Explanation:** `++` means the received power is above the high-alarm threshold: a long-range optic on a very short run overloads the receiver. An attenuator or a shorter-reach optic fixes it. Dirty connectors and bends cause **low** Rx power; swapped strands give no light at all.

### Q8 · Drag and drop — order
<sub>Source: 1B.7, 1B.10</sub>

A switch port shows `err-disabled` after an unknown device was connected. Drag the recovery steps into the correct order.

1. Read `show logging` to find the reason the port was disabled
2. Remove the cause of the violation
3. Enter `shutdown` on the interface
4. Enter `no shutdown` on the interface

> **Explanation:** An err-disabled port stays down until it is bounced. Find the reason first, fix it, then `shutdown` followed by `no shutdown`. Bouncing the port without removing the cause simply disables it again.

### Q9 · CLI
<sub>Source: 1A.9</sub>

You have finished configuring SW1 and are at the privileged EXEC prompt. Enter the command that saves the running configuration so it survives a reload.

**Prompt:** `SW1#`

**Accepted:** `copy running-config startup-config` · `write memory` · `write`

> **Explanation:** `copy running-config startup-config` (often typed as `copy run start`) copies the configuration in RAM to NVRAM. `write memory` (or just `write`) does the same thing. From a configuration prompt you would need `do` in front.

### Q10 · Multiple choice
<sub>Source: 1B.5</sub>

A new 1 Gb/s fiber uplink stays down. One end has a 1000BASE-SX optic and the other a 1000BASE-LX/LH optic, joined by multimode fiber. What is the most likely cause?

- [ ] Auto-MDIX is disabled on one end
- [ ] The cable is longer than 100 m
- [x] The optics are of different types, so the two ends cannot form a link
- [ ] One end is hard-coded to full duplex

> **Explanation:** A mismatched optic is a cable-type fault: SX and LX/LH use different wavelengths and fiber types, so there is no link or only a very weak signal. Auto-MDIX applies to copper, the 100 m limit is a copper rule, and duplex settings do not stop a fiber link from coming up.

### Q11 · Multiple choice
<sub>Source: 1B.8</sub>

Why is SW2 Gi0/1 running at half duplex?

- [ ] Half duplex is the default for every Gigabit Ethernet port
- [x] SW2 sensed the speed from the signal but could not negotiate duplex, so it fell back to half duplex at 100 Mb/s
- [ ] SW1 told SW2 to use half duplex during autonegotiation
- [ ] The cable is a crossover cable

> **Explanation:** When one side is hard-coded, the auto side can still detect the speed, but it cannot learn the duplex. At 10 or 100 Mb/s it falls back to half duplex — and a duplex mismatch is born.

### Q12 · Multiple choice — choose two
<sub>Source: 1B.8, 1B.9</sub>

Which two symptoms do you expect on this link? (Choose two.)

- [x] Late collisions on SW2 Gi0/1
- [x] CRC errors and runts on SW1 Gi0/1
- [ ] The link on both switches showing down/down
- [ ] Late collisions on SW1 Gi0/1
- [ ] A speed mismatch error in the log

> **Explanation:** The half-duplex side (SW2) counts collisions and **late collisions**; the full-duplex side (SW1) sees damaged frames as **CRC errors and runts**. The link stays up/up — that is why the fault goes unnoticed while pings still work.

### Q13 · CLI
<sub>Source: 1B.8</sub>

The team decides both ends should negotiate. You are in interface configuration mode for SW1 Gi0/1 and have already entered `speed auto`. Enter the command that returns the duplex setting to autonegotiation.

**Prompt:** `SW1(config-if)#`

**Accepted:** `duplex auto`

> **Explanation:** Best practice is to leave **both** ends on `auto`, or to hard-code **both** ends to the same values. With SW1 back on `speed auto` and `duplex auto`, the two ports negotiate 1000 Mb/s full duplex.
