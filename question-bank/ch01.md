### Q1 · Multiple choice
<sub>Source: 1B.7</sub>

Refer to the exhibit.

```
SW1# show interfaces status
Port      Name          Status       Vlan       Duplex  Speed Type
Fa0/1     PC1           connected    10         a-full  a-100 10/100BaseTX
Fa0/3     Printer       connected    40           full    100 10/100BaseTX
Fa0/4                   notconnect   10           auto   auto 10/100BaseTX
Gi0/1     Uplink-SW2    connected    trunk      a-full a-1000 10/100/1000BaseTX
```

Which port has its speed and duplex configured manually?

- [ ] Fa0/1
- [x] Fa0/3
- [ ] Fa0/4
- [ ] Gi0/1

> **Explanation:** In `show interfaces status`, the `a-` prefix means the value was auto-negotiated. Fa0/3 shows `full` and `100` without the prefix, so both were hard-coded. Fa0/1 and Gi0/1 negotiated their values. Fa0/4 is left at `auto` (the default) and shows `notconnect`, meaning no usable link.

### Q2 · Multiple choice
<sub>Source: 1A.4, 1A.7</sub>

PC2 (10.10.10.12/24, default gateway 10.10.10.1) opens a web page on a server at 198.51.100.25. PC2 already has its gateway's MAC address in its ARP cache. Which destination MAC address does PC2 put in the Ethernet frame that carries the HTTP request?

- [ ] The web server's MAC address
- [x] The default gateway's MAC address
- [ ] The broadcast MAC FFFF.FFFF.FFFF
- [ ] The access switch port's MAC address

> **Explanation:** The server is on another network, so the frame only has to reach the next hop: the default gateway. The IP destination stays 198.51.100.25 end to end; the MAC addresses are rewritten at every router hop. The broadcast address is used only for the ARP Request that resolves the gateway's MAC, not for the data frame, and that MAC is already cached. Switches forward frames without being their destination.

### Q3 · Multiple choice — choose two
<sub>Source: 1A.7</sub>

Which two statements describe how a Layer 2 switch builds and uses its MAC address table? (Choose two.)

- [x] It learns MAC addresses from the source address of received frames.
- [x] It floods unknown unicast frames out all other ports in the VLAN.
- [ ] It learns MAC addresses from the destination address of received frames.
- [ ] It drops frames whose destination MAC address is not in the table.
- [ ] Dynamic entries stay in the table until the switch reloads.

> **Explanation:** Learning always uses the **source** MAC; forwarding decisions use the **destination** MAC. Unknown unicast, broadcast and (by default) multicast frames are flooded out every port in the VLAN except the one they arrived on, not dropped. Dynamic entries age out after 300 seconds by default.

### Q4 · Drag and drop — order
<sub>Source: 1A.3, 1A.4</sub>

A browser sends an HTTPS request over TCP. Drag the protocol data units into the order in which the sending host creates them, from the application down to the wire.

1. Data
2. Segment
3. Packet
4. Frame
5. Bits

> **Explanation:** Application data is wrapped by Transport into a **segment** (TCP; UDP would produce a datagram), by Network into a **packet**, by Data Link into a **frame**, and turned into **bits** by the Physical layer.

### Q5 · Drag and drop — match
<sub>Source: 1B.4</sub>

None of the devices support auto-MDIX. Drag the correct cable type to each connection. A cable type can be used more than once.

| Connection | Cable |
| --- | --- |
| PC to access switch | Straight-through |
| Access point to access switch | Straight-through |
| Switch to switch | Crossover |
| Router Ethernet port to router Ethernet port | Crossover |
| Laptop to a router's console port | Rollover |

**Extra targets:** Serial DCE · Multimode fiber

> **Explanation:** PCs, routers and APs are MDI; switches are MDI-X. Unlike devices (PC or AP to switch) use straight-through; like devices (switch–switch, router–router) use crossover. The console port uses a rollover cable. Serial DCE is a WAN cable, and multimode fiber does not connect RJ-45 copper ports.

### Q6 · Drag and drop — match
<sub>Source: 1B.8, 1B.9</sub>

Drag each interface symptom to its most likely cause. Each cause is used once.

| Symptom | Cause |
| --- | --- |
| Late collisions rising on a 100 Mb/s half-duplex port; the far end shows Full-duplex, 100Mb/s | Duplex mismatch |
| CRC errors rising; both ends full duplex at 1000 Mb/s; zero collisions and zero runts | Damaged or over-length cable, or EMI |
| Giants rising after a jumbo-frame change on one end | MTU mismatch |
| Output drops rising while error counters stay at zero | Congestion |

**Extra targets:** Speed mismatch (both ends hard-coded to different speeds)

> **Explanation:** Late collisions on a half-duplex port facing a full-duplex peer are the classic duplex-mismatch signature. With both ends full duplex there is no duplex mismatch, so CRC errors point to the physical path (cable length, damage, EMI). Giants are frames above the maximum size, typically an MTU mismatch. Output drops mean the egress queue was full: congestion, for example traffic from a faster ingress port, not a cable fault. A speed mismatch between two hard-coded ends leaves the link down/down (`notconnect`), so it produces no rising counters.

### Q7 · Multiple choice
<sub>Source: 1B.5, 1B.6</sub>

Refer to the exhibit.

```
DSW1# show interfaces transceiver
                                          Optical   Optical
           Temperature  Voltage  Current  Tx Power  Rx Power
Port       (Celsius)    (Volts)  (mA)     (dBm)     (dBm)
---------  -----------  -------  -------  --------  --------
Gi1/1/3      35.2        3.30     40.1      2.1       1.4 ++
```

Gi1/1/3 connects to a switch in the same rack over a 3 m single-mode patch cable, using extended-reach (long-range) optics on both ends. Which action resolves the problem?

- [ ] Clean the LC connectors on both ends
- [x] Add an attenuator or use shorter-reach optics
- [ ] Replace the single-mode patch cable with multimode fiber
- [ ] Swap the Tx and Rx strands on one end

> **Explanation:** `++` means the received power is above the high-alarm threshold: a long-range optic on a very short single-mode run overloads the receiver. An attenuator or a shorter-reach optic fixes it. Dirty connectors and bends cause **low** Rx power; swapped strands give no light at all. Multimode fiber with these optics would be a mismatched-media fault of its own and does not fix the overload.

### Q8 · Drag and drop — order
<sub>Source: 1B.9, 1B.10</sub>

The uplink between SW1 and SW2 is reported slow. Drag the troubleshooting steps into the order of the systematic procedure, from Layer 1 upward.

1. Check the status of both ends and confirm the link is up/up (`connected`)
2. Compare the speed and duplex settings on both ends
3. Clear the interface counters with `clear counters`
4. Re-check `show interfaces` to see which counters are rising
5. With the counters clean, move on to VLAN, trunk and IP checks

> **Explanation:** Status comes first, on both ends, because it tells you whether the link exists. For an up/up link that is slow, compare speed and duplex, then look at the counters. Counters are cumulative since boot or the last clear, so clear them before re-checking to see which ones are rising now. Only when the counters stay clean is the fault above Layer 1.

### Q9 · CLI
<sub>Source: 1A.9</sub>

You have finished configuring SW1 and are at the privileged EXEC prompt. Enter the command that saves the running configuration so it survives a reload.

**Prompt:** `SW1#`

**Accepted:** `copy running-config startup-config` · `write memory` · `write`

> **Explanation:** `copy running-config startup-config` (often typed as `copy run start`) copies the configuration in RAM to NVRAM. `write memory` does the same thing (the short `write` is also accepted). From a configuration prompt you would need `do` in front.

### Q10 · Multiple choice
<sub>Source: 1B.4, 1B.5, 1B.8</sub>

A new 1 Gb/s fiber uplink between DSW1 and SW1 shows `notconnect` on both ends. DSW1 has a 1000BASE-SX optic and SW1 a 1000BASE-LX/LH optic, joined by multimode fiber. Tx meets Rx at each end. What is the most likely cause?

- [x] The optic types do not match
- [ ] Multimode fiber cannot carry 1 Gb/s
- [ ] There is a duplex mismatch
- [ ] Auto-MDIX is disabled on one end

> **Explanation:** A mismatched optic is a cable-type fault: an SX optic on one end and an LX/LH optic on the other gives no link or a very weak signal (1B.5). Multimode fiber does carry 1 Gb/s, since 1000BASE-SX runs on it. A duplex mismatch leaves the link up/up (1B.8), so it does not explain `notconnect`. Auto-MDIX swaps copper transmit and receive pairs (1B.4) and has nothing to do with this fiber link.

### Q11 · Multiple choice
<sub>Source: 1B.8</sub>

Which statement describes what happened on this link?

- [x] DSW1 was left on auto and fell back to half duplex
- [ ] SW2 was left on auto and fell back to half duplex
- [ ] DSW1 was left on auto and negotiated full duplex
- [ ] Both ends were hard-coded to different speeds

> **Explanation:** A port left on auto facing a hard-coded peer senses the speed but cannot learn the duplex, so at 100 Mb/s it falls back to half. SW2 runs full duplex at 100 Mb/s, so SW2 cannot be the auto side: it was hard-coded, and DSW1 fell back to half. If DSW1 had ended up full duplex, SW2 would not be counting runts and CRC errors with zero collisions. Different hard-coded speeds would leave the link down/down (`notconnect`), not up/up.

### Q12 · Multiple choice — choose two
<sub>Source: 1B.7, 1B.8, 1B.9</sub>

Which two do you expect to see on DSW1? (Choose two.)

- [x] Late collisions rising on Gi1/0/5
- [x] Gi1/0/5 showing `a-half` `a-100` in `show interfaces status`
- [ ] CRC errors and runts with zero collisions on Gi1/0/5
- [ ] Gi1/0/5 showing `notconnect` in `show interfaces status`
- [ ] A log message reporting a speed mismatch

> **Explanation:** DSW1 is the half-duplex side, so it counts collisions and **late collisions**, and `show interfaces status` shows the negotiated `a-half a-100`. CRC errors and runts with zero collisions are what the full-duplex side (SW2, in the exhibit) records. The link is up/up, so it is not `notconnect`. CDP logs a **duplex** mismatch (`%CDP-4-DUPLEX_MISMATCH`), not a speed mismatch.

### Q13 · CLI
<sub>Source: 1B.8</sub>

The team decides both ends should negotiate. You are in interface configuration mode for SW2 Gi0/1 and have already entered `speed auto`. Enter the command that returns the duplex setting to autonegotiation.

**Prompt:** `SW2(config-if)#`

**Accepted:** `duplex auto` · `no duplex` · `default duplex`

> **Explanation:** Best practice is to leave **both** ends on `auto`, or to hard-code **both** ends to the same values. With SW2 back on `speed auto` and `duplex auto`, the two Gigabit ports negotiate a common speed and full duplex, and the late collisions, CRC errors and runts stop.
