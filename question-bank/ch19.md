# Chapter 19 — Managing configurations and images with SCP and SFTP

CCNA-style practice questions for [Chapter 19](../CCNA%20200-301%20v2.0%20Study%20Guide.md#chapter-19--managing-configurations-and-images-with-scp-and-sftp) · Domain 4 · Objective 4.2. The format is described in the [question bank README](README.md).

## Questions

### Q1 · Multiple choice — choose two
<sub>Source: 19.3, 19.4</sub>

An engineer is writing a procedure to back up DSW1's running configuration to the Linux server 10.10.99.30, with DSW1 acting as the client. Which two statements belong in the procedure? (Choose two.)

- [x] In `copy running-config sftp://netadmin@10.10.99.30//backups/DSW1-2026-10-17.cfg`, the double slash marks `/backups` as an absolute path on the server.
- [x] Leaving the password out of the URL lets IOS prompt for it, so the password is not shown on screen or kept in the command history.
- [ ] DSW1 needs `ip scp server enable` before it can copy its configuration to an SCP server.
- [ ] The firewall between DSW1 and the server must allow TCP 20 and 21 for SFTP in addition to TCP 22.
- [ ] Instead of a copy from DSW1, the server could pull the file over SFTP, because IOS XE also acts as an SFTP server.

> **Explanation:** Cisco's SFTP URLs take the form `sftp://user@host//path`, where the double slash marks an absolute path. A password typed into the URL (`user:password@host`) is visible on screen and in the history, so let IOS prompt for it. `ip scp server enable` is only needed when the device is the SCP **server**; for client copies you use `copy` (and optionally `ip ssh source-interface`). SCP and SFTP both run inside SSH on TCP 22 — TCP 20/21 belong to FTP. IOS XE is an SFTP **client** only.

### Q2 · Multiple choice
<sub>Source: 19.4, 19.7</sub>

Refer to the exhibit.

```
DSW1# show running-config | include username|aaa|ssh|scp
aaa new-model
aaa authentication login default local
aaa authorization exec default local
aaa session-id common
username netadmin privilege 15 secret 9 $9$fpzYSLsHnH0PIn$PNczjzo6Xjm1cm2Y4Mu0DnAXyrr/n6a69p9/V2xaFld
ip ssh version 2
 transport input ssh
```

An administrator logs in with `ssh -l netadmin 10.10.99.2` and lands at `DSW1#`. When they push an image from their laptop with `scp -O cat9k_iosxe.17.12.04.SPA.bin netadmin@10.10.99.2:flash:/cat9k_iosxe.17.12.04.SPA.bin`, DSW1 refuses the transfer. Which command fixes the problem?

- [ ] `aaa authorization exec default local`
- [ ] `username netadmin privilege 15 algorithm-type scrypt secret N3t-Admin-2026`
- [ ] `ip ssh version 2`
- [x] `ip scp server enable`

> **Explanation:** An IOS SCP server needs SSH, `aaa new-model`, an authentication list, `aaa authorization exec`, a privilege 15 user and `ip scp server enable`. The exhibit has everything except the last line, which matches the symptom "SCP to the device refused". Exec authorization and a privilege 15 user are already configured — the login landing at `#` confirms it. SSH version 2 is also present, and the laptop already uses `-O`, so the OpenSSH 9 protocol problem does not apply.

### Q3 · Drag and drop — match
<sub>Source: 19.3</sub>

Drag the correct description to each file transfer protocol.

| Protocol | Description |
| --- | --- |
| TFTP | UDP 69; no authentication and no encryption |
| FTP | TCP 20/21; username and password sent in clear text |
| SCP | SSH on TCP 22; IOS can act as server and client |
| SFTP | SSH on TCP 22; IOS XE acts as a client only |

**Extra targets:** UDP 69; username and password required · TCP 22; credentials encrypted but data sent in clear text

> **Explanation:** TFTP (UDP 69) has no authentication at all, which is why it belongs in labs and PXE/phone boot only. FTP (TCP 20/21) asks for a username and password but sends them in clear text. SCP and SFTP both run inside SSH on TCP 22, so credentials and data are encrypted. On IOS XE, SCP works in both directions, while SFTP works only with the device as the client. TFTP never asks for a username, and nothing that runs over SSH leaves the data unencrypted.

### Q4 · Multiple choice
<sub>Source: 19.2</sub>

Which IOS file system holds the running-config?

- [ ] `flash:`
- [ ] `nvram:`
- [x] `system:`
- [ ] `usbflash0:`

> **Explanation:** The running-config lives in RAM and appears as `system:running-config`; it does not survive a reload. The startup-config is kept in `nvram:`. `flash:` (or `bootflash:`) holds software images and saved files, and `usbflash0:` is a USB stick where present — all three survive a reload.

### Q5 · CLI
<sub>Source: 19.4</sub>

Your team's standard says every switch must start its SCP and SFTP client connections from its VLAN 99 management interface, so that the backup server's logs and ACLs always see the management address. On DSW1, enter the global configuration command that makes interface Vlan99 (10.10.99.2) the source of these connections.

**Prompt:** `DSW1(config)#`

**Accepted:** `ip ssh source-interface Vlan99`

> **Explanation:** SCP and SFTP run inside SSH, so `ip ssh source-interface Vlan99` sets the source address that the server sees when DSW1 runs `copy … scp://` or `copy … sftp://`. A wrong source address is one of the reasons a server "never sees" the connection, together with routing problems and ACLs that block TCP 22.

### Q6 · Drag and drop — match
<sub>Source: 19.7</sub>

Drag the correct fix to each file transfer symptom.

| Symptom | Fix |
| --- | --- |
| `scp` from a laptop with OpenSSH 9.6 ends with a protocol error | Add `-O` to the `scp` command |
| `copy scp: flash:` stops part-way through an image | Check `dir flash:` and delete unused files |
| A backup restored with `copy … running-config` leaves old, wrong lines in place | Use `configure replace` |
| `verify /sha512` prints a value that differs from Cisco's published hash | Copy the image again and check the filename and platform |

**Extra targets:** Add `aaa authorization exec default local` · Change the transfer to TFTP

> **Explanation:** OpenSSH 9.0 and later use the SFTP protocol inside `scp`, which the IOS XE SCP server does not accept; `-O` selects the original SCP protocol. A copy that stops part-way points to a full flash. `copy … running-config` merges, so only `configure replace` removes lines that are not in the file. A hash mismatch means a corrupted or wrong file. Exec authorization fixes a "Permission denied" error with a correct password, which is not listed here, and TFTP would only remove authentication and encryption.

### Q7 · Multiple choice
<sub>Source: 19.2, 19.6</sub>

Refer to the exhibit.

```
DSW2# show version | include System image
System image file is "flash:cat9k_iosxe.17.09.05.SPA.bin"
DSW2# dir flash: | include SPA|free
475137  -rw-   1048291715   Mar 3 2026 11:02:41 +00:00  cat9k_iosxe.17.09.05.SPA.bin
475139  -rw-   1250431459  Oct 17 2026 08:47:19 +00:00  cat9k_iosxe.17.12.04.SPA.bin
11353194496 bytes total (8461029376 bytes free)
```

An engineer has copied the new image to DSW2, and `verify /sha512` matches Cisco's published hash. Which statement is correct?

- [x] DSW2 runs in bundle mode, so the upgrade uses `boot system flash:cat9k_iosxe.17.12.04.SPA.bin` followed by `copy running-config startup-config`.
- [ ] DSW2 runs in install mode, so the upgrade uses `install add file flash:cat9k_iosxe.17.12.04.SPA.bin activate commit`.
- [ ] DSW2 does not have enough free flash to hold the new image.
- [ ] The engineer can delete `cat9k_iosxe.17.09.05.SPA.bin` now, because the new image is already in flash.

> **Explanation:** `show version` shows DSW2 booting the `.bin` file directly, which is bundle mode; an install-mode switch boots `flash:packages.conf`. In bundle mode you point the boot variable at the new image and save. The new image (about 1.25 GB) is already in flash with about 8.4 GB still free. The 17.09.05 image is the one running now: keep it until the new version is confirmed, so there is something to fall back to.

### Q8 · Drag and drop — order
<sub>Source: 19.6</sub>

DSW1 is a Catalyst 9000 switch running in install mode. Drag the steps of its software upgrade into the correct order.

1. Download the image for the exact platform and record Cisco's published SHA-512 hash
2. Check the bytes free with `dir flash:`
3. Copy the image with `copy scp://netadmin@10.10.99.30/images/cat9k_iosxe.17.12.04.SPA.bin flash:`
4. Run `verify /sha512 flash:cat9k_iosxe.17.12.04.SPA.bin` and compare the result with the published hash
5. Run `install add file flash:cat9k_iosxe.17.12.04.SPA.bin activate commit`
6. Confirm the new version and a short uptime with `show version`

> **Explanation:** Choose the image and record its hash, make sure flash has room (install mode also needs space to expand the packages), copy it securely, and verify the hash — the gate before anything touches the boot settings. `install add … activate commit` expands the packages, updates `packages.conf` and reloads, so back up the configuration and plan a maintenance window first. `show version` then confirms the new version.

### Q9 · Multiple choice
<sub>Source: 19.6, 19.7</sub>

R1 runs in bundle mode. During a maintenance window an engineer deleted the old image to free space, copied the new image with SCP, entered `boot system` for the new file, saved the configuration and reloaded without running `verify /sha512` or `show boot`. R1 now stops at the `rommon 1 >` prompt. What is the most likely cause?

- [x] The boot variable points to an image that is missing or incomplete, so R1 found no valid image to boot.
- [ ] `copy running-config startup-config` overwrote the new image in flash.
- [ ] An image copied with SCP cannot be booted until it is expanded with `install add`.
- [ ] The startup configuration was merged into the running configuration during the reload, which removed the `boot system` line.

> **Explanation:** A device that cannot find a valid image at boot drops to ROMMON; after an upgrade the usual reason is a boot variable that points to a deleted or incomplete image. Recover by booting an image manually, fixing `boot system` and saving. Saving writes the startup-config, not images; the transfer method does not affect bootability; and `install add` is the install-mode procedure. Verifying the hash, checking `show boot` before reloading, and keeping the old image until the new one is confirmed prevent this.

## Testlet A · Rolling back DSW1's configuration

Refer to the scenario. On 15 October an engineer saved DSW1's configuration to `flash:DSW1-2026-10-15.cfg` and to the backup server with SCP. Two days later a test interface, Loopback99, was added by mistake. To roll back, a colleague ran the commands in the exhibit.

```
DSW1# copy flash:DSW1-2026-10-15.cfg running-config
Destination filename [running-config]?
5124 bytes copied in 0.214 secs (23943 bytes/sec)
DSW1# show running-config interface loopback 99
Building configuration...

Current configuration : 65 bytes
!
interface Loopback99
 ip address 10.255.99.1 255.255.255.255
end
```

### Q10 · Multiple choice
<sub>Source: 19.2, 19.5</sub>

Why is interface Loopback99 still in DSW1's running configuration?

- [x] Copying a file into the running configuration merges it: lines in the file are added or changed, and lines that exist only in the running configuration are kept.
- [ ] The copy wrote the file to the startup-config, so the running configuration changes only after the next reload.
- [ ] The colleague should first have run `copy startup-config running-config` to clear the running configuration.
- [ ] The file in flash was corrupted during the copy, so IOS skipped the interface sections.

> **Explanation:** `copy <source> <destination>` reads source first; here the destination is the running configuration, and the result is a **merge** — it adds and changes lines but deletes nothing. Loopback99 is not in the 15 October file, so nothing removes it. `copy startup-config running-config` is also a merge, so it would not clear anything either.

### Q11 · CLI
<sub>Source: 19.5, 19.7</sub>

Enter the command that makes DSW1's running configuration exactly match `flash:DSW1-2026-10-15.cfg`, removing every line that is not in that file.

**Prompt:** `DSW1#`

**Accepted:** `configure replace flash:DSW1-2026-10-15.cfg`

> **Explanation:** `configure replace` **replaces** the running configuration with the file, so lines that are not in the file — such as interface Loopback99 — are removed. It is the fix for "restored backup, old wrong lines still present". Removing the loopback by hand with `no interface loopback 99` also works, but only for lines you already know about.

### Q12 · Multiple choice
<sub>Source: 19.5</sub>

To make future rollbacks easier, the team wants DSW1 to keep a numbered copy of its configuration in flash every time someone enters `write memory`. What should the engineer configure?

- [x] `archive` with `path flash:archive/$h-` and `write-memory`, then list the copies with `show archive`
- [ ] `boot system flash:archive/$h-`, so that every save is also written to flash
- [ ] `configure replace flash:archive/$h-` after every change
- [ ] `ip scp server enable`, so that the backup server pulls a copy at every save

> **Explanation:** The `archive` feature with a `path` and `write-memory` saves a numbered version every time the configuration is saved, and `show archive` lists them. `boot system` selects the software image to boot, `configure replace` restores a saved file rather than creating one, and `ip scp server enable` only lets clients connect to DSW1 — it does not make anything copy files automatically.
