# Chapter 19 — Managing configurations and images with SCP and SFTP

CCNA-style practice questions for [Chapter 19](../CCNA%20200-301%20v2.0%20Study%20Guide.md#chapter-19--managing-configurations-and-images-with-scp-and-sftp) · Domain 4 · Objective 4.2. The format is described in the [question bank README](README.md).

## Questions

### Q1 · Multiple choice — choose two
<sub>Source: 19.3, 19.4</sub>

R2 must send its configuration backup to the server 10.10.99.30, which it can reach. The server runs TFTP, FTP, SCP and SFTP services, but its host firewall accepts only TCP port 22. SSH is already configured on R2. Which two commands can complete the backup? (Choose two.)

- [x] `copy running-config scp://netadmin@10.10.99.30/backups/R2-2026-10-17.cfg`
- [x] `copy running-config sftp://netadmin@10.10.99.30//backups/R2-2026-10-17.cfg`
- [ ] `copy running-config tftp:`
- [ ] `copy running-config ftp:`, after `ip ftp username netadmin` and `ip ftp password` have been configured

> **Explanation:** SCP and SFTP both run inside SSH on TCP 22, so they pass the firewall, and they authenticate the user and encrypt the data. TFTP uses UDP 69 and has no authentication at all. FTP uses TCP 20/21; configuring an FTP username and password does not change its ports, and those credentials still cross the network in clear text.

### Q2 · Multiple choice
<sub>Source: 19.4, 19.7</sub>

Refer to the exhibit.

```
DSW1# show running-config | include aaa|username|scp|ssh
aaa new-model
aaa authentication login default local
aaa session-id common
username netadmin privilege 15 secret 9 $9$kazPG9ZY1FT/7r$.UNIYDE3O/BuYF2usH3x1scEnXPYC8lTkHG4TDwhLHT
ip scp server enable
ip ssh version 2
 transport input ssh
```

An administrator can log in to DSW1 with `ssh -l netadmin 10.10.99.2`. When they push a file from their laptop with `scp -O DSW1-snippet.cfg netadmin@10.10.99.2:flash:/DSW1-snippet.cfg`, the transfer fails with "Permission denied", although the password is correct. Which command fixes the problem?

- [x] `aaa authorization exec default local`
- [ ] `ip scp server enable`
- [ ] `ip ssh source-interface Vlan99`
- [ ] Run the same `scp` command on the laptop without `-O`

> **Explanation:** An IOS SCP server needs SSH, `aaa new-model`, an authentication list, **exec authorization**, a privilege 15 user and `ip scp server enable`. Everything is present except `aaa authorization exec`, so IOS cannot apply netadmin's privilege 15: the SSH login works but lands at `DSW1>`, and SCP is denied. `ip scp server enable` is already configured. `ip ssh source-interface` only sets the source address for connections that DSW1 starts as a client. Dropping `-O` would make a laptop with OpenSSH 9 or later use the SFTP protocol, which the IOS XE SCP server does not accept.

### Q3 · Multiple choice
<sub>Source: 19.3, 19.4</sub>

An administrator tries to upload a file to DSW1, a Catalyst 9000 switch running IOS XE, with `sftp netadmin@10.10.99.2` from their laptop, but the session fails. SSH logins with the same account work, and DSW1 is configured as an SCP server. What should the administrator do?

- [x] Push the file with `scp -O` instead, because IOS XE can be an SFTP client but not an SFTP server
- [ ] Open TCP ports 20 and 21 between the laptop and DSW1, because SFTP needs a separate data connection
- [ ] Add `-O` to the `sftp` command so that it uses the original protocol
- [ ] Enter `ip ssh source-interface Vlan99` on DSW1 so that it accepts the session on its management address

> **Explanation:** IOS XE acts as an SFTP **client** only: DSW1 can fetch or send files with `copy … sftp://…`, but a PC cannot open an SFTP session to it. To push a file to the switch, use SCP, which IOS can serve, with `scp -O` from a PC running OpenSSH 9 or later. SFTP runs inside SSH on TCP 22, so no FTP ports are involved. `-O` is an `scp` option, and `ip ssh source-interface` only affects connections that DSW1 starts.

### Q4 · Drag and drop — match
<sub>Source: 19.4, 19.6, 19.7</sub>

Drag the most likely cause to each file transfer symptom.

| Symptom | Likely cause |
| --- | --- |
| `scp` without `-O` from a laptop running OpenSSH 9.6 ends with a protocol error | The laptop's scp uses the SFTP protocol, which the IOS XE SCP server does not accept |
| `copy scp: flash:` of a new image stops part-way through the transfer | Not enough free space in flash |
| `verify /sha512` prints a value that differs from Cisco's published hash | A corrupted or wrong image file |
| The backup server never sees a connection from DSW1 | Routing, an ACL blocking TCP 22, or the wrong source address |
| R1 stops at `rommon 1 >` after an upgrade and reload | The boot variable points to a deleted or incomplete image |

**Extra targets:** The user is below privilege 15, or exec authorization is missing · UDP 69 is blocked between the device and the server

> **Explanation:** OpenSSH 9.0 and later use SFTP inside `scp` by default; `scp -O` selects the original SCP protocol. A copy that stops part-way points to a full flash, so check `dir flash:` and delete unused files. A hash mismatch means corruption or the wrong file: copy it again and check the filename and platform. If the server never sees the connection, check routing, ACLs that block TCP 22 and the source address (`ip ssh source-interface`). A device that finds no valid image at boot drops to ROMMON. A missing privilege or exec authorization causes "Permission denied", which is not listed, and UDP 69 is TFTP, which none of these transfers uses.

### Q5 · Drag and drop — match
<sub>Source: 19.5</sub>

Drag the command that achieves each goal on DSW1.

| Goal | Command |
| --- | --- |
| Keep an encrypted copy of the configuration on the backup server | copy running-config scp://netadmin@10.10.99.30/backups/DSW1-2026-10-17.cfg |
| Keep a local copy for a quick rollback | copy running-config flash:DSW1-2026-10-17.cfg |
| Add a few prepared lines without touching the rest of the configuration | copy scp://netadmin@10.10.99.30/backups/DSW1-snippet.cfg running-config |
| Return exactly to the state saved on 15 October, removing everything added since | configure replace flash:DSW1-2026-10-15.cfg |
| Save a numbered copy automatically every time someone enters write memory | archive, then path flash:archive/$h- and write-memory |

**Extra targets:** copy flash:DSW1-2026-10-15.cfg running-config · boot system flash:DSW1-2026-10-15.cfg

> **Explanation:** `copy running-config scp://…` stores an encrypted copy off the device, and `copy running-config flash:…` keeps one locally. Copying a file **into** the running configuration merges it: lines are added or changed and nothing is deleted, which suits a snippet. Only `configure replace` **replaces** the running configuration and removes lines that are not in the file, so `copy flash:DSW1-2026-10-15.cfg running-config` would leave the newer lines in place. The `archive` feature with a `path` and `write-memory` saves a numbered version at every `write memory`; `show archive` lists them. `boot system` selects a software image, not a configuration.

### Q6 · Multiple choice
<sub>Source: 19.2, 19.5</sub>

Refer to the exhibit.

```
R1# show startup-config | include ip route
ip route 10.10.0.0 255.255.0.0 10.0.0.2
R1# show running-config | include ip route
ip route 10.10.0.0 255.255.0.0 10.0.0.2
ip route 10.10.40.0 255.255.255.0 10.0.0.2
R1# copy startup-config running-config
Destination filename [running-config]?
1342 bytes copied in 0.087 secs (15425 bytes/sec)
R1# show running-config | include ip route
ip route 10.10.0.0 255.255.0.0 10.0.0.2
ip route 10.10.40.0 255.255.255.0 10.0.0.2
```

An engineer added a static route to 10.10.40.0/24 on R1 for a test and did not save it. To discard the test, they ran the commands in the exhibit. Why is the 10.10.40.0/24 route still in the running configuration?

- [x] Copying a file into the running configuration merges it: lines from the file are added or changed, and lines that exist only in the running configuration are kept.
- [ ] `copy` names the destination first, so the command saved the running configuration over the startup configuration instead.
- [ ] A copy into the running configuration takes effect only after the next reload.
- [ ] The startup configuration also contains the 10.10.40.0/24 route, so the copy added it back.

> **Explanation:** `copy` always reads **source, then destination**, so this command copied the startup-config into the running configuration — as the `Destination filename [running-config]?` prompt confirms. The result is a **merge**: it adds and changes lines and deletes nothing. The exhibit shows that the 10.10.40.0/24 route is not in the startup-config, and a merge never removes a line, so the route stays. A copy into the running configuration takes effect immediately, not at the next reload. To remove the route, enter `no ip route 10.10.40.0 255.255.255.0 10.0.0.2`, or use `configure replace` with a saved file, which removes every line that is not in that file.

### Q7 · Drag and drop — order
<sub>Source: 19.6</sub>

DSW1 is a Catalyst 9000 switch running in install mode. Drag the steps of its software upgrade into the correct order.

1. Download the image for the exact platform and record Cisco's published SHA-512 hash
2. Check that the bytes free shown by `dir flash:` exceed the image size
3. Run `copy scp://netadmin@10.10.99.30/images/cat9k_iosxe.17.12.04.SPA.bin flash:`
4. Run `verify /sha512 flash:cat9k_iosxe.17.12.04.SPA.bin` and compare the result with the published hash
5. Run `install add file flash:cat9k_iosxe.17.12.04.SPA.bin activate commit`
6. Confirm the new version and a short uptime with `show version`

> **Explanation:** Pick the image and its hash, make sure flash has room (install mode also needs space to expand the packages), copy the image securely and verify the hash. The hash check is the gate: a mismatched file is deleted and copied again before anything touches the boot settings. `install add … activate commit` expands the packages, updates `packages.conf` and reloads, so back up the configuration and plan a maintenance window before running it. `show version` then confirms the result; keep the old image until you are sure.

### Q8 · CLI
<sub>Source: 19.4, 19.5</sub>

R1 must back up its running configuration over **SFTP** to the server 10.10.99.30 as user `netadmin`. The file must be written to the absolute path `/backups/R1-2026-10-17.cfg` on the server. Enter one command that puts the user, server and path in the URL; leave the password out so that IOS prompts for it.

**Prompt:** `R1#`

**Accepted:** `copy running-config sftp://netadmin@10.10.99.30//backups/R1-2026-10-17.cfg` · `copy system:running-config sftp://netadmin@10.10.99.30//backups/R1-2026-10-17.cfg`

> **Explanation:** The `copy` command reads source, then destination. Cisco's SFTP URL form is `sftp://user@host//path`, where the double slash marks an absolute path on the server; SCP uses `scp://user@host/path`. Leaving the password out of the URL keeps it off the screen and out of the command history, because a password typed as `user:password@host` stays visible.

### Q9 · Multiple choice
<sub>Source: 19.2</sub>

Yesterday an engineer changed the configuration of several interfaces on DSW2 and tested them successfully. After a power outage overnight, all of the changes are gone. Which statement explains the loss?

- [x] The changes existed only in the running configuration, which is held in RAM (`system:`); `copy running-config startup-config` would have written them to `nvram:`.
- [ ] The changes existed only in the running configuration; `copy startup-config running-config` would have written them to `nvram:`.
- [ ] The changes were saved to `nvram:`, which loses its contents when the power fails.
- [ ] The changes were saved to `flash:`, which is erased when the switch boots after a power failure.

> **Explanation:** The running-config appears as `system:running-config` and lives in RAM, so it does not survive a reload. The startup-config in `nvram:` and the files in `flash:` both survive one. Because `copy` reads source first, `copy running-config startup-config` saves; `copy startup-config running-config` goes the other way and merges the saved file into the running configuration.

### Q10 · Multiple choice
<sub>Source: 19.2, 19.6</sub>

Which statement about the upgrade is correct?

- [x] DSW2 boots the `.bin` file directly, so it runs in bundle mode and the next step is to point the boot variable at the new image and save the configuration.
- [ ] DSW2 runs in install mode, because every Catalyst 9000 switch boots `packages.conf`, so the next step is `install add file flash:cat9k_iosxe.17.12.04.SPA.bin activate commit`.
- [ ] DSW2 does not have enough free space in flash for the new image.
- [ ] The 17.09.05 image can be deleted now, because the new image has passed the hash check.

> **Explanation:** `show version` shows DSW2 running `flash:cat9k_iosxe.17.09.05.SPA.bin`, so it is in **bundle mode**; an install-mode switch boots `flash:packages.conf`. Catalyst 9000 switches *usually* run in install mode, but not always — the output decides. The new image (about 1.25 GB) is already in flash, with more than 8 GB still free. The 17.09.05 image is the one running now: keep it until the new version is confirmed, so there is something to fall back to.

### Q11 · CLI
<sub>Source: 19.6</sub>

Enter the global configuration command that makes DSW2 boot `cat9k_iosxe.17.12.04.SPA.bin` from `flash:` at the next reload.

**Prompt:** `DSW2(config)#`

**Accepted:** `boot system flash:cat9k_iosxe.17.12.04.SPA.bin`

> **Explanation:** In bundle mode, `boot system flash:<image>` sets the boot variable, and `copy running-config startup-config` saves it so the setting is used at the next reload. Install-mode switches use `install add file … activate commit` instead.

### Q12 · Multiple choice
<sub>Source: 19.6, 19.7</sub>

The engineer has set the boot variable and saved the configuration. Before reloading DSW2 in the maintenance window, which command should they use to confirm the image that the next reload will use?

- [x] `show boot`
- [ ] `show version`
- [ ] `dir flash:`
- [ ] `verify /sha512 flash:cat9k_iosxe.17.12.04.SPA.bin`

> **Explanation:** `show boot` (or `show bootvar`) shows which image the next reload will use. `show version` shows the image running now, which stays 17.09.05 until the reload. `dir flash:` lists files and free space, and `verify /sha512` checks a file's integrity; neither shows the boot setting. If the boot variable points to a missing or incomplete file, the switch drops to ROMMON (`rommon 1 >`) and an image must be booted manually.
