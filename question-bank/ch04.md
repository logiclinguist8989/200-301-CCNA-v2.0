# Chapter 4 — Hypervisors, virtual machines and containers

CCNA-style practice questions for [Chapter 4](../CCNA%20200-301%20v2.0%20Study%20Guide.md#chapter-4--hypervisors-virtual-machines-and-containers) · Domain 1 · Objective 1.2. The format is described in the [question bank README](README.md).

## Questions

### Q1 · Multiple choice
<sub>Source: 4.4</sub>

A college replaces several mostly idle physical servers with one powerful server. The virtualization software is installed directly on the server hardware, with no general-purpose operating system underneath it. Which statement describes this hypervisor?

- [x] It is a Type 1 (bare-metal) hypervisor, such as VMware ESXi.
- [ ] It is a Type 2 (hosted) hypervisor, such as Oracle VirtualBox.
- [ ] It is a container engine, such as Docker.
- [ ] It is a container orchestrator, such as Kubernetes.

> **Explanation:** Software installed directly on the hardware, with no general-purpose OS underneath, is a bare-metal or Type 1 hypervisor, as VMware ESXi, Microsoft Hyper-V, KVM and Xen are. Type 2 (hosted) hypervisors such as Oracle VirtualBox and VMware Workstation run as an application on top of Windows, macOS or Linux. A container engine such as Docker runs containers that share the host OS's kernel, so it also needs an OS underneath. Kubernetes is not a hypervisor either: it runs many containers across many hosts, restarts failed ones and scales them.

### Q3 · Multiple choice — choose two
<sub>Source: 4.7</sub>

A team must decide whether to run new workloads on a Linux server as virtual machines or as containers. Which two requirements favor virtual machines? (Choose two.)

- [x] A legacy application that runs only on Windows Server must be hosted on the Linux server.
- [x] Each workload needs strong isolation, with its own separate kernel rather than a shared host kernel.
- [ ] New instances must start in about a second so the service can scale quickly.
- [ ] Each instance should take megabytes of storage rather than gigabytes.
- [ ] Microservices are rebuilt and redeployed many times a day by a CI/CD pipeline.

> **Explanation:** A VM runs a full guest OS with its own kernel, so it can run a different OS from the host (a Windows VM on a Linux host) and gives strong isolation between separate kernels. Containers share the host's kernel: Linux containers need a Linux kernel, and their process-level isolation is weaker if the kernel is compromised. Fast start-up (about a second), small size (megabytes) and microservices or CI/CD pipelines are the strengths of containers.

### Q4 · Drag and drop — order
<sub>Source: 4.5</sub>

VM-DB runs on an ESXi host. Its vNIC is in the Staff port group (VLAN 10), and the host's uplink vmnic0 is an 802.1Q trunk to SW1. VM-DB pings its default gateway. Drag the events into the order in which the request and its reply travel.

1. VM-DB's guest OS sends an ordinary Ethernet frame with no VLAN tag out of its vNIC
2. The vSwitch identifies the frame's VLAN from the port group the vNIC belongs to and inserts a VLAN 10 tag
3. The tagged frame leaves the host on vmnic0 and enters SW1 on a trunk port
4. SW1 reads VLAN 10 from the tag and delivers the frame to the VLAN 10 gateway (an SVI or router)
5. SW1 sends the gateway's reply down the trunk to the host with a VLAN 10 tag
6. The vSwitch strips the tag and passes the untagged reply to VM-DB's vNIC

> **Explanation:** The guest OS knows nothing about VLANs: it sends an untagged frame, and the port group decides the VLAN. Because the uplink carries several VLANs as an 802.1Q trunk, the vSwitch tags the frame with the port group's VLAN (10) before it leaves on vmnic0. SW1 uses the tag to keep the frame in VLAN 10 and reaches the gateway. The reply returns over the trunk tagged with VLAN 10, and the vSwitch removes the tag, so the VM again sees an ordinary untagged frame.

### Q6 · Multiple choice
<sub>Source: 4.5, 4.11</sub>

VM-Web and VM-DB run on the same ESXi host, and both vNICs are in the Staff port group (VLAN 10). The host's uplinks are an 802.1Q trunk to SW1. How does a frame from VM-Web to VM-DB travel?

- [x] The vSwitch forwards it directly to VM-DB's vNIC, and the frame never leaves the host.
- [ ] The vSwitch tags it with VLAN 10 and sends it to SW1, which sends it back down the same trunk.
- [ ] The vSwitch sends it to the VLAN 10 gateway on SW1, which routes it back to the host.
- [ ] The vSwitch floods it to every vNIC on the host, in every port group.

> **Explanation:** A vSwitch is a Layer 2 switch inside the hypervisor. It forwards frames between VMs on the same host without them ever reaching the physical network, and sends everything else out an uplink. "VMs on the same host always talk through the physical switch" is a common misconception. Routing through a gateway is needed only between different VLANs. Flooding to every port group would ignore the VLAN boundaries that port groups create: like a physical Layer 2 switch, the vSwitch forwards the frame to the destination VM's vNIC and keeps each port group's traffic in its own VLAN.

### Q7 · Multiple choice
<sub>Source: 4.6, 4.9</sub>

Refer to the exhibit.

```
$ sudo docker ps
CONTAINER ID   IMAGE        COMMAND                  CREATED       STATUS       PORTS                  NAMES
c41e7a9b2f10   my-app:1.2   "python app.py"          5 hours ago   Up 5 hours   5000/tcp                 app
3f9c2a1b7d4e   nginx        "/docker-entrypoint.…"   5 hours ago   Up 5 hours   0.0.0.0:8443->443/tcp    web
```

The Docker host's address is 10.10.10.15. A laptop on the LAN opens https://10.10.10.15:8443 successfully, but http://10.10.10.15:5000 fails. On the Docker host itself, the app container answers normally at http://172.17.0.3:5000. What is the cause?

- [x] Port 5000 of the app container is not published to a port on the host.
- [ ] The host firewall blocks inbound TCP port 5000.
- [ ] The host's NAT translates only outbound traffic, so the app container cannot accept connections from the LAN.
- [ ] The laptop must use http://172.17.0.3:5000, because the host's address reaches only the web container.

> **Explanation:** The PORTS column shows `0.0.0.0:8443->443/tcp` for web: host port 8443 is published to the container's port 443. For app it shows only `5000/tcp`, so no host port maps to it. A container on the docker0 bridge is reachable from outside the host only through the host's address and a published port; 172.17.0.3 is private to the host's bridge, so the laptop cannot use it. A host firewall is the other common cause of "works from the host, not from the LAN", but here the PORTS column already shows that host port 5000 leads nowhere, so publishing the port is needed whatever the firewall does. The fix is to run the container again with a published port, for example `-p 5000:5000` (and then open the firewall if it also blocks the port). NAT does not prevent inbound access in general: the web container is reached from the LAN through its published port.

### Q8 · Multiple choice
<sub>Source: 4.6, 4.10</sub>

A Linux server runs Docker with its default settings. An engineer starts a container without any network options. Which statement describes the container's networking?

- [x] It gets an address such as 172.17.0.2 on the docker0 bridge, and its outbound traffic is translated by NAT to the host's IP address.
- [ ] It gets an address from the LAN's DHCP server and appears on the LAN as a separate host.
- [ ] It uses the host's network interfaces directly and shares the host's IP address.
- [ ] It has no network interface until a port is published with `-p`.

> **Explanation:** By default Docker on Linux creates the docker0 Linux bridge (normally 172.17.0.1/16), gives each container a virtual interface on that bridge with an address such as 172.17.0.2, and uses NAT (masquerading) so containers reach outside networks with the host's IP address. Sharing the host's interfaces is the separate host networking mode. Appearing on the LAN as a separate host is what a VirtualBox VM does in Bridged mode. Publishing a port is needed only to make the container reachable from outside the host.

### Q9 · Drag and drop — match
<sub>Source: 4.9</sub>

Drag each symptom seen on a network with virtualized hosts to its most likely cause.

| Symptom | Cause |
| --- | --- |
| A VM in a tagged port group gets an address in the Wireless subnet 10.10.30.0/24 instead of the Staff subnet 10.10.10.0/24 | Wrong VLAN ID on the VM's port group |
| Users report intermittent loss to several VMs, and the switch log shows their MAC addresses moving back and forth between the host's two switch ports | NIC teaming and switch bundling do not match |
| Two VMs report an address conflict shortly after a new VM is deployed from an existing one | The new VM kept the original's static IP or MAC address |
| VMs in VLAN 40 have no network, while other VMs on the same host work normally | VLAN missing from the trunk's allowed list |

**Extra targets:** Native VLAN mismatch between the vSwitch and the switch · Container port not published

> **Explanation:** A VM in the wrong subnet still has a working network, just in the wrong VLAN; because its frames are tagged, the switch puts them in the VLAN the port group sets, so check the port group's VLAN ID. A native VLAN mismatch affects only untagged traffic, so it does not explain a VM whose frames are tagged. MAC addresses moving between two ports to the same host (`%SW_MATM-4-MACFLAP_NOTIF`) mean the teaming and the switch disagree; make both LACP or both independent ports. A VM copied from another can keep its static IP or MAC address and conflict with the original; regenerate the MAC and re-address the copy. When only one VLAN's VMs on a host fail, that VLAN is not allowed on the trunk (or not created on the switch); check `show interfaces trunk` and add it. An unpublished container port affects only a container that works from its host but not from the LAN; none of the symptoms involves a container.

### Q10 · Multiple choice — choose two
<sub>Source: 4.8</sub>

Which two are examples of network functions virtualization (NFV)? (Choose two.)

- [x] A Secure Firewall Threat Defense Virtual (FTDv) firewall running on a server
- [x] Wireless controller software running as a VM on a server
- [ ] A Catalyst 9300 access switch that powers IP phones with PoE
- [ ] An ISR 4331 router installed at a branch office
- [ ] A web server application running as a VM on an ESXi host
- [ ] A VLAN trunk that carries several virtual LANs over one link

> **Explanation:** NFV runs network devices as software on standard servers instead of dedicated hardware. Cisco examples are the Catalyst 8000V virtual router, the FTDv and ASAv virtual firewalls, and virtual wireless controllers running as VMs. A Catalyst 9300 switch and an ISR 4331 router are dedicated network hardware. A web server VM is server virtualization: the workload is an application, not a network device. A VLAN trunk is "virtual" only in name: it is an ordinary link that carries several VLANs, not a network device running as software on a server.

## Testlet A · VM unreachable after live migration

Refer to the scenario. ESXi-01 and ESXi-02 form a VMware cluster. Each host carries its VM traffic over one 802.1Q trunk to SW1, without LACP: ESXi-01 connects to Gi1/0/11 and ESXi-02 to Gi1/0/12. Before patching ESXi-01, an administrator live-migrates all of its VMs to ESXi-02. Afterwards PrintSrv, a VM in the Printers/IoT port group (VLAN 40) that had been running on ESXi-01 and worked there, cannot reach its gateway. The VMs in VLANs 10 and 99 keep working.

```
SW1# show interfaces trunk

Port        Mode             Encapsulation  Status        Native vlan
Gi1/0/11    on               802.1q         trunking      999
Gi1/0/12    on               802.1q         trunking      999

Port        Vlans allowed on trunk
Gi1/0/11    10,40,99
Gi1/0/12    10,99

Port        Vlans allowed and active in management domain
Gi1/0/11    10,40,99
Gi1/0/12    10,99

Port        Vlans in spanning tree forwarding state and not pruned
Gi1/0/11    10,40,99
Gi1/0/12    10,99
```

### Q11 · Multiple choice
<sub>Source: 4.5, 4.9</sub>

What is the cause of the problem?

- [x] VLAN 40 is not allowed on the trunk to ESXi-02.
- [ ] VLAN 40 does not exist on SW1.
- [ ] There is a native VLAN mismatch between Gi1/0/12 and ESXi-02's vSwitch.
- [ ] PrintSrv's port group on ESXi-02 uses the wrong VLAN ID.

> **Explanation:** Both ports are trunking with native VLAN 999, but Gi1/0/12 allows only VLANs 10 and 99. ESXi-02's vSwitch tags PrintSrv's frames with VLAN 40, and SW1 does not accept that VLAN on Gi1/0/12, so the VM is cut off. VLAN 40 exists on SW1: it is allowed and active on Gi1/0/11. A native VLAN mismatch concerns untagged traffic and shows up as `%CDP-4-NATIVE_VLAN_MISMATCH` messages; PrintSrv's frames are tagged. A wrong port group VLAN ID is worth checking on the hypervisor, but the exhibit already proves that Gi1/0/12 cannot carry VLAN 40 at all, so even a correct port group could not reach the gateway; a wrong port group VLAN typically shows up as a VM in the wrong subnet. PrintSrv worked before the migration because ESXi-01's port, Gi1/0/11, allows VLAN 40. Live migration can move a VM to any host in the cluster at any moment, so every host's uplinks need the same VLANs.

### Q12 · CLI
<sub>Source: 4.9, 4.13</sub>

You are in interface configuration mode on the SW1 port that causes the problem. Enter the single command that makes this port allow exactly the same VLANs as Gi1/0/11, without removing any VLAN it already carries.

**Prompt:** `SW1(config-if)#`

**Accepted:** `switchport trunk allowed vlan add 40` · `switchport trunk allowed vlan 10,40,99` · `switchport trunk allowed vlan 10,99,40` · `switchport trunk allowed vlan 40,10,99` · `switchport trunk allowed vlan 40,99,10` · `switchport trunk allowed vlan 99,10,40` · `switchport trunk allowed vlan 99,40,10`

> **Explanation:** The exhibit shows that Gi1/0/12, ESXi-02's port, lacks VLAN 40, which PrintSrv uses. The `add` keyword appends VLAN 40 and keeps VLANs 10 and 99, so Gi1/0/12 matches Gi1/0/11; typing the full list of VLANs 10, 40 and 99 (in any order) has the same result. Allowing all VLANs would also restore PrintSrv, but the trunk would then differ from Gi1/0/11 and carry VLANs that no VM on the host needs. Typing `switchport trunk allowed vlan 40` alone would replace the list and cut off the VMs in VLANs 10 and 99. Keep the trunks to all hosts in a cluster identical, so that a migrated VM finds its VLAN on whichever host it lands on.
