## Questions

### Q1 · Multiple choice
<sub>Source: 4.4</sub>

A college replaces several mostly idle physical servers with one powerful server. The virtualization software is installed directly on the server hardware, with no general-purpose operating system underneath it. Which statement describes this hypervisor?

- [x] It is a Type 1 (bare-metal) hypervisor, such as VMware ESXi.
- [ ] It is a Type 2 (hosted) hypervisor, such as VMware ESXi.
- [ ] It is a Type 1 (bare-metal) hypervisor, such as Oracle VirtualBox.
- [ ] It is a Type 2 hypervisor, because Type 2 is the newer generation that needs no host OS.

> **Explanation:** "Bare-metal" always means Type 1: the hypervisor runs directly on the hardware, as VMware ESXi, Microsoft Hyper-V, KVM and Xen do. Type 2 (hosted) hypervisors such as Oracle VirtualBox, VMware Workstation and Parallels Desktop run as an application on top of Windows, macOS or Linux. "Type 2" describes where the hypervisor runs, not a second generation of hypervisors.

<sub>Source: 4.4, 4.6</sub>

Drag each product to its category. A category can be used more than once, and not every category is used.

| Product | Category |
| --- | --- |
| Microsoft Hyper-V | Type 1 hypervisor |
| KVM | Type 1 hypervisor |
| Parallels Desktop | Type 2 hypervisor |
| VMware Workstation | Type 2 hypervisor |
| Docker | Container engine |
| Kubernetes | Container orchestrator |

**Extra targets:** Container registry · Virtual switch

> **Explanation:** Hyper-V and KVM (part of the Linux kernel) are Type 1 hypervisors, like ESXi and Xen. Parallels Desktop and VMware Workstation are Type 2: they run as desktop applications on a host OS, like VirtualBox and VMware Fusion. Docker is a container engine that pulls images and runs containers. Kubernetes is an orchestrator: it runs many containers across many hosts, restarts failed ones and scales them. A registry (such as Docker Hub) stores images, and a virtual switch (such as Open vSwitch) connects VMs; none of the listed products is either.

### Q3 · Multiple choice — choose two
<sub>Source: 4.7</sub>

A team must decide whether to run new workloads on a Linux server as virtual machines or as containers. Which two requirements favor virtual machines? (Choose two.)

- [x] A legacy application that runs only on Windows Server must be hosted on the Linux server.
- [x] Each workload needs strong isolation, with its own kernel, so that a kernel compromise affects only that workload.
- [ ] New instances must start in about a second so the service can scale quickly.
- [ ] Each instance should take megabytes of storage rather than gigabytes.
- [ ] Microservices are rebuilt and redeployed many times a day by a CI/CD pipeline.

> **Explanation:** A VM runs a full guest OS with its own kernel, so it can run a different OS from the host (a Windows VM on a Linux host) and gives strong isolation between separate kernels. Containers share the host's kernel: Linux containers need a Linux kernel, and their process-level isolation is weaker if the kernel is compromised. Fast start-up (about a second), small size (megabytes) and microservices or CI/CD pipelines are the strengths of containers.

### Q4 · Drag and drop — order
<sub>Source: 4.5</sub>

VM-DB runs on an ESXi host. Its vNIC is in the Staff port group (VLAN 10), and the host's uplink vmnic0 is an 802.1Q trunk to SW1. Drag the steps into the order in which VM-DB's frame reaches its default gateway and the reply returns.

1. VM-DB's vNIC sends an untagged frame into the Staff port group
2. The vSwitch adds an 802.1Q tag for VLAN 10 and sends the frame out vmnic0
3. SW1 receives the tagged frame on its trunk port and forwards it in VLAN 10 toward the gateway
4. The reply arrives back at the host on vmnic0, tagged with VLAN 10
5. The vSwitch removes the tag and delivers the frame to VM-DB

> **Explanation:** The VM itself sends an ordinary untagged frame; the port group decides its VLAN. The vSwitch knows the Staff port group is VLAN 10, so it adds the 802.1Q tag as the frame leaves on the uplink. SW1 receives the tagged frame on its trunk and forwards it in VLAN 10 toward the gateway (an SVI or router). Replies come back tagged with VLAN 10, and the vSwitch removes the tag before delivering the frame to the VM.

Which interface most likely connects to a server running Microsoft Hyper-V?

- [ ] Po1

### Q6 · Multiple choice
<sub>Source: 4.5, 4.11</sub>

VM-Web and VM-DB run on the same ESXi host, and both vNICs are in the Staff port group (VLAN 10). The host's uplinks are an 802.1Q trunk to SW1. How does a frame from VM-Web to VM-DB travel?

- [x] The vSwitch forwards it directly to VM-DB's vNIC, and the frame never leaves the host.
- [ ] The vSwitch tags it with VLAN 10 and sends it to SW1, which sends it back down the same trunk.
- [ ] The vSwitch sends it to the VLAN 10 gateway on SW1, which routes it back to the host.
- [ ] The vSwitch sends it untagged in the native VLAN to SW1, which forwards it back to the host.

> **Explanation:** A vSwitch is a Layer 2 switch inside the hypervisor. It forwards frames between VMs on the same host without them ever reaching the physical network, and sends everything else out an uplink. "VMs on the same host always talk through the physical switch" is a common misconception. Routing through a gateway is needed only between different VLANs, and frames from the Staff port group are tagged with VLAN 10, not sent in the native VLAN.

### Q7 · Multiple choice
<sub>Source: 4.6, 4.9</sub>

Refer to the exhibit.

```
$ sudo docker ps
CONTAINER ID   IMAGE        COMMAND                  CREATED       STATUS       PORTS                  NAMES
c41e7a9b2f10   my-app:1.2   "python app.py"          5 hours ago   Up 5 hours   5000/tcp               app
3f9c2a1b7d4e   nginx        "/docker-entrypoint.…"   5 hours ago   Up 5 hours   0.0.0.0:8080->80/tcp   web
```

The Docker host's address is 192.168.1.50. A laptop on the LAN opens http://192.168.1.50:8080 successfully, but http://192.168.1.50:5000 fails. On the Docker host itself, the app container answers normally at http://172.17.0.3:5000. What is the cause?

- [x] Port 5000 of the app container is not published to a port on the host.
- [ ] The app container is stopped.
- [ ] The app container uses the none network mode, so it has no network interface.
- [ ] The laptop must use http://172.17.0.3:5000, because the host's address reaches only the web container.

> **Explanation:** The PORTS column shows `0.0.0.0:8080->80/tcp` for web: host port 8080 is published to the container's port 80. For app it shows only `5000/tcp`, so nothing on the host maps to it. A container on the docker0 bridge is reachable from outside the host only through the host's address and a published port; 172.17.0.3 is private to the host's bridge. The fix is to run the container again with a published port, for example `-p 5000:5000` (and open the host firewall if it blocks the port). The container is running (`Up 5 hours`) and has an address on docker0, so it is neither stopped nor in none mode.

### Q8 · Multiple choice
<sub>Source: 4.6</sub>

A Linux server runs Docker with its default settings. An engineer starts a container without any network options. Which statement describes the container's networking?

- [x] It gets an address such as 172.17.0.2 on the docker0 bridge, and its outbound traffic is translated by NAT to the host's IP address.
- [ ] It gets an address from the LAN's DHCP server and appears on the LAN as a separate host.
- [ ] It uses the host's network interfaces directly and shares the host's IP address.
- [ ] It has no network interface until a port is published with `-p`.

> **Explanation:** By default Docker on Linux creates the docker0 Linux bridge (normally 172.17.0.1/16), gives each container a virtual interface on that bridge with an address such as 172.17.0.2, and uses NAT (masquerading) so containers reach outside networks with the host's IP address. Sharing the host's interfaces is the separate host networking mode. Appearing on the LAN as a separate host is what a VirtualBox VM does in Bridged mode. Publishing a port is needed only to make the container reachable from outside the host.

### Q9 · Drag and drop — match
<sub>Source: 4.9</sub>

Drag each symptom seen on a network with virtualized hosts to its most likely cause.

| Symptom | Cause |
| --- | --- |
| A VM gets an address in the Wireless subnet 10.10.30.0/24 instead of the Staff subnet 10.10.10.0/24 | Wrong VLAN ID on the VM's port group |
| `%SW_MATM-4-MACFLAP_NOTIF` messages show VM MAC addresses moving between the host's two switch ports | NIC teaming and switch bundling do not match |
| Two VMs report a duplicate address after one was cloned from the other | The clone kept the same static IP or MAC address |
| `%CDP-4-NATIVE_VLAN_MISMATCH` is logged for the host's trunk port | vSwitch untagged traffic and the switch native VLAN differ |

**Extra targets:** VLAN missing from the trunk's allowed list · Duplex mismatch on the uplink

> **Explanation:** A VM in the wrong subnet still has a working network, just in the wrong VLAN, so check the port group's VLAN ID. MAC flapping between two ports to the same host means the teaming and the switch disagree; make both LACP or both independent ports. Clones that keep the static IP or MAC conflict with the original; regenerate the MAC and re-address the clone. A native VLAN mismatch means the untagged traffic is in different VLANs on the two sides; align the native VLANs or tag everything. A VLAN missing from the trunk would leave the VMs in that VLAN with no network at all.

### Q10 · Multiple choice — choose two
<sub>Source: 4.8</sub>

Which two are examples of network functions virtualization (NFV)? (Choose two.)

- [x] A Secure Firewall Threat Defense Virtual (FTDv) firewall running as a VM on a data-centre server
- [x] Wireless controller software running as a VM instead of on a dedicated appliance
- [ ] A physical Catalyst access switch that powers IP phones with PoE
- [ ] A physical ISR 4331 router installed at a branch office
- [ ] A Kubernetes cluster that restarts failed web-application containers

> **Explanation:** NFV runs network devices as software on standard servers instead of dedicated hardware. Cisco examples are the Catalyst 8000V virtual router, the FTDv and ASAv virtual firewalls, and virtual wireless controllers running as VMs. A physical switch and a physical router are dedicated network hardware. Kubernetes orchestrates application containers; it is not a virtual network device.

## Testlet A · VM unreachable after live migration

Refer to the scenario. ESXi-01 and ESXi-02 form a VMware cluster. Each host carries its VM traffic over one 802.1Q trunk to SW1, without LACP: ESXi-01 connects to Gi1/0/11 and ESXi-02 to Gi1/0/12. Before patching ESXi-01, an administrator live-migrates all of its VMs to ESXi-02. Afterwards PrintSrv, a VM in the Printers/IoT port group (VLAN 40), cannot reach its gateway. The VMs in VLANs 10 and 99 keep working.

```
SW1# show interfaces trunk

Port        Mode             Encapsulation  Status        Native vlan
Gi1/0/11    on               802.1q         trunking      999
Gi1/0/12    on               802.1q         trunking      999

Port        Vlans allowed on trunk
Gi1/0/11    10,40,99
Gi1/0/12    10,99

Port        Vlans allowed and active in management domain
Gi1/0/11    10,40,99
Gi1/0/12    10,99

Port        Vlans in spanning tree forwarding state and not pruned
Gi1/0/11    10,40,99
Gi1/0/12    10,99
```

### Q11 · Multiple choice
<sub>Source: 4.5, 4.9</sub>

What is the cause of the problem?

- [x] VLAN 40 is not allowed on Gi1/0/12, so SW1 does not carry the VLAN 40 frames that ESXi-02's vSwitch sends.
- [ ] VLAN 40 does not exist on SW1.
- [ ] There is a native VLAN mismatch between Gi1/0/12 and ESXi-02's vSwitch.
- [ ] Gi1/0/12 is an access port, so it carries only one VLAN.

> **Explanation:** Both ports are trunking with native VLAN 999, but Gi1/0/12 allows only VLANs 10 and 99. ESXi-02's vSwitch tags PrintSrv's frames with VLAN 40, and SW1 does not accept that VLAN on Gi1/0/12, so the VM is cut off. VLAN 40 exists on SW1: it is allowed and active on Gi1/0/11. A native VLAN mismatch concerns untagged traffic and shows up as `%CDP-4-NATIVE_VLAN_MISMATCH` messages; PrintSrv's frames are tagged. PrintSrv worked only because it ran on ESXi-01. Live migration can move a VM to any host in the cluster at any moment, so every host's uplinks need the same VLANs.

### Q12 · CLI
<sub>Source: 4.9, 4.13</sub>

You are in interface configuration mode for SW1 Gi1/0/12. Enter the command that adds VLAN 40 to the trunk's allowed VLAN list without retyping the VLANs that are already allowed.

**Prompt:** `SW1(config-if)#`

**Accepted:** `switchport trunk allowed vlan add 40`

> **Explanation:** The `add` keyword appends VLAN 40 and keeps VLANs 10 and 99, so Gi1/0/12 matches Gi1/0/11. Typing `switchport trunk allowed vlan 40` without `add` would replace the list and cut off the VMs in VLANs 10 and 99. Keep the trunks to all hosts in a cluster identical, so that a migrated VM finds its VLAN on whichever host it lands on.
