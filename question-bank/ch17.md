## Questions

### Q1 · Multiple choice
<sub>Source: 17.4, 17.8</sub>

Refer to the exhibit.

```
$ ifconfig en0
en0: flags=8863<UP,BROADCAST,SMART,RUNNING,SIMPLEX,MULTICAST> mtu 1500
	ether 8c:85:90:ab:cd:ef
	inet 10.10.30.27 netmask 0xffff0000 broadcast 10.10.255.255
	status: active
$ arp -a
? (10.10.30.1) at c4:72:95:a7:3e:41 on en0 ifscope [ethernet]
? (10.10.40.11) at c4:72:95:a7:3e:41 on en0 ifscope [ethernet]
```

A MacBook is on the Wireless VLAN 30 (10.10.30.0/24, gateway 10.10.30.1). Its user prints to the printer at 10.10.40.11 without any problem. Why does the printer's ARP entry show the same MAC address as the default gateway?

- [x] The mask is /16, so the Mac treats 10.10.40.11 as local and ARPs for it directly; the gateway answers with proxy ARP using its own MAC address
- [ ] The printer and the gateway use a duplicate MAC address, which must be removed from one of them
- [ ] macOS lists the gateway's MAC address for every remote host, because all off-subnet traffic goes to the gateway
- [ ] The ARP cache is stale; the printer was recently moved into VLAN 30

> **Explanation:** macOS shows the mask in hexadecimal: 0xffff0000 is 255.255.0.0 (/16), not 0xffffff00 (/24). With /16, 10.10.40.11 falls inside the Mac's own network 10.10.0.0/16, so the Mac sends an ARP request for the printer instead of sending the packet to its gateway. The gateway answers with proxy ARP, so printing works and the wrong mask stays hidden. With the correct /24 mask, the ARP cache would hold only the gateway, because a host never ARPs for remote addresses. Nothing points to a duplicate MAC address or a stale entry. The fix is the mask: correct the static setting or the DHCP pool.

### Q2 · Multiple choice — choose two
<sub>Source: 17.4, 17.7, 17.8</sub>

Refer to the exhibit.

```
C:\> ipconfig /all
Wireless LAN adapter Wi-Fi:
   Connection-specific DNS Suffix  . :
   Physical Address. . . . . . . . . : 3C-A9-F4-12-34-56
   DHCP Enabled. . . . . . . . . . . : No
   IPv4 Address. . . . . . . . . . . : 10.10.30.25(Preferred)
   Subnet Mask . . . . . . . . . . . : 255.255.255.0
   Default Gateway . . . . . . . . . : 10.10.31.1
   DNS Servers . . . . . . . . . . . : 10.10.99.53
```

A user typed static IPv4 settings on a Windows laptop in VLAN 30 (10.10.30.0/24). Which two results will the user see? (Choose two.)

- [x] Pings to other hosts in 10.10.30.0/24 succeed
- [x] Pings to the DNS server 10.10.99.53 fail
- [ ] Pings to the gateway 10.10.31.1 succeed, so remote networks are reachable
- [ ] Windows replaces the address with a 169.254.x.x address because the gateway cannot be reached
- [ ] Pings by IP address to remote networks succeed, but names do not resolve

> **Explanation:** The gateway 10.10.31.1 is outside the client's subnet 10.10.30.0/24 (10.10.30.0–10.10.30.255), so the client cannot reach it. Hosts in its own subnet are delivered directly and still answer; everything off the subnet fails, including the DNS server in 10.10.99.0/24, so names fail too. A 169.254.x.x address appears only when DHCP gets no answer, and this laptop is not using DHCP. The fix is the gateway 10.10.30.1, or switching the adapter back to DHCP.

### Q3 · Drag and drop — order
<sub>Source: 17.2, 17.5</sub>

A user says "the website is down". Drag the tests into the order in which you run them from the user's Windows PC, following the reachability ladder.

1. `ping 127.0.0.1`
2. Ping the PC's own IPv4 address
3. Ping the default gateway
4. Ping a remote IP address, such as 192.0.2.8
5. Ping a name, such as www.campus.example
6. Test the service itself, for example `Test-NetConnection server -Port 443`

> **Explanation:** Work outward from the client and stop at the first failure, because every later step depends on it. The loopback ping proves the TCP/IP stack; the own address proves the adapter has it; the gateway proves Layers 1–3 to the first hop (link, VLAN, mask, ARP); a remote IP proves routing beyond the gateway and back; a name proves DNS; only then is the application itself tested.

### Q4 · Multiple choice
<sub>Source: 17.5, 17.7</sub>

From PC1 (10.10.10.11), an engineer pings a Windows laptop at 10.10.30.25. PC1 gets replies from its gateway 10.10.10.1 and from other hosts in 10.10.30.0/24, but not from 10.10.30.25. The laptop's user is browsing the web and opening files on SRV1 without any problem. What is the most likely explanation?

- [x] The laptop's host firewall drops incoming ICMP echo requests
- [ ] The laptop is powered off or disconnected from Wi-Fi
- [ ] Routing between VLAN 10 and VLAN 30 is broken
- [ ] The laptop has a 169.254.x.x address because DHCP failed

> **Explanation:** Firewalls can lie: Windows Defender Firewall blocks incoming ICMP by default on public networks, so a PC that does not answer ping may still be fine. Other hosts in VLAN 30 answer, so routing between the VLANs works, and a laptop that was off or had an APIPA address could not be browsing and using SRV1. Test from the laptop outward, use an application-level test such as `Test-NetConnection` with a port, or allow ICMP.

### Q5 · Drag and drop — match
<sub>Source: 17.4, 17.6, 17.7</sub>

Drag each client observation to its most likely meaning. Not every meaning is used.

| Observation | Meaning |
| --- | --- |
| 169.254.x.x with mask 255.255.0.0 and no default gateway | No DHCP server answered |
| `(Duplicate)` after the IPv4 address in `ipconfig /all` | Another device uses the same address |
| Only an `fe80::` IPv6 address on the adapter | No Router Advertisements received |
| A 192.168.1.x address on a laptop plugged into the campus network | Static settings left over from home |
| One phone is blocked by a MAC-based rule while other phones work | Private (random) MAC address in use |
| On the guest SSID: valid address and DNS, but web traffic is blocked until the user accepts the terms | Captive portal |

**Extra targets:** Host firewall blocking ICMP · Wrong subnet mask hidden by proxy ARP

> **Explanation:** 169.254.x.x/16 without a gateway is APIPA: no DHCP server answered, so check the link and VLAN first. `(Duplicate)` means an address conflict; find the other device through ARP and MAC tables. An adapter with only an `fe80::` address gets no Router Advertisements, so it has no global IPv6 address. A 192.168.1.x address on campus is a static setting from home; switch the adapter back to DHCP. Windows, macOS, iOS and Android can use a random MAC per network, which breaks MAC-based rules and reservations. A captive portal blocks everything until the portal page is completed. The extra targets fit none of the rows: a host firewall only makes a working client ignore pings, and a wrong mask shows up as an unusual mask on an otherwise correct address.

### Q6 · Multiple choice — choose two
<sub>Source: 17.3</sub>

You need to see which DNS servers an Ubuntu desktop is using. Which two commands show this? (Choose two.)

- [x] `resolvectl status`
- [x] `cat /etc/resolv.conf`
- [ ] `ip route show`
- [ ] `ip neigh`
- [ ] `scutil --dns`

> **Explanation:** On Linux the DNS servers are shown by `resolvectl status`, or by reading `/etc/resolv.conf`. `ip route show` displays the routing table and the default gateway, and `ip neigh` the neighbor (ARP) cache. `scutil --dns` is the macOS command; Windows uses `ipconfig /all`.

### Q7 · Drag and drop — match
<sub>Source: 17.3, 17.6</sub>

Drag each task to the command that performs it. Not every command is used.

| Task | Command |
| --- | --- |
| Renew the DHCP lease on a Mac whose interface is en0 | sudo ipconfig set en0 DHCP |
| Display the routing table on Windows | route print |
| Display the neighbor (ARP) cache on Linux | ip neigh |
| Flush the DNS cache on Windows | ipconfig /flushdns |
| Display the Wi-Fi RSSI and noise level on macOS | sudo wdutil info |

**Extra targets:** ipconfig /renew · resolvectl flush-caches

> **Explanation:** macOS renews a lease with `sudo ipconfig set en0 DHCP` (or Renew DHCP Lease in Settings); `ipconfig /renew` is the Windows form. Windows shows its routing table with `route print` and flushes its DNS cache with `ipconfig /flushdns`; `resolvectl flush-caches` does that on Linux. Linux shows the neighbor cache with `ip neigh`. `sudo wdutil info` shows the RSSI and the noise floor on macOS, which gives the SNR directly.

### Q8 · Multiple choice
<sub>Source: 17.6</sub>

Staff-WiFi has been changed from WPA2-Enterprise to WPA3-Enterprise. Newer laptops reconnect without problems. One older laptop, whose wireless driver is several years old, no longer connects, although the SSID, the user's credentials and the trust in the RADIUS server's certificate are all correct. Which missing client capability is the most likely cause?

- [x] Protected management frames (PMF)
- [ ] The TKIP cipher
- [ ] Private (random) MAC addresses
- [ ] Automatic private IP addressing (APIPA)

> **Explanation:** A client connects only when every security setting matches the WLAN, including its capabilities. WPA3 requires protected management frames, and an old driver without PMF cannot join a WPA3 network. TKIP is not needed: a client forced to TKIP is itself a typical mistake, because WPA2 and WPA3 use AES (CCMP), or GCMP for WPA3 192-bit. Private MAC addresses affect MAC-based rules and reservations, not association, and APIPA only matters after association, when DHCP gets no answer.

### Q9 · CLI
<sub>Source: 17.3, 17.6</sub>

A user says Staff-WiFi is slow on their Windows laptop. At the Command Prompt, enter the command that shows the SSID, the BSSID of the AP radio, the authentication type, the cipher, the channel and the signal strength of the current Wi-Fi connection.

**Prompt:** `C:\>`

**Accepted:** `netsh wlan show interfaces`

> **Explanation:** `netsh wlan show interfaces` shows the state, SSID, BSSID, radio type, authentication, cipher, band, channel, receive rate and signal of the connection Windows actually negotiated. Windows reports the signal as a percentage; `iw` on Linux and `wdutil` on macOS report it in dBm.

## Testlet A · Slow Wi-Fi on a Linux laptop

Refer to the scenario. A user carried a Linux laptop (Wi-Fi interface wlp2s0) from an office next to AP1 to a meeting room next to AP2, at the other end of the floor. Since then, Staff-WiFi has been slow and keeps dropping on the laptop, while colleagues in the meeting room have no problems. AP1's radios use the BSSIDs 70:7D:B9:AA:BB:01 (5 GHz) and 70:7D:B9:AA:BB:11 (2.4 GHz); AP2's radios use 70:7D:B9:AA:CC:01 (5 GHz) and 70:7D:B9:AA:CC:11 (2.4 GHz). The engineer runs this command on the laptop in the meeting room.

```
$ nmcli -f IN-USE,BSSID,SSID,CHAN,SIGNAL,SECURITY device wifi list
IN-USE  BSSID              SSID        CHAN  SIGNAL  SECURITY
*       70:7D:B9:AA:BB:11  Staff-WiFi  1     27      WPA2 802.1X
        70:7D:B9:AA:CC:01  Staff-WiFi  44    86      WPA2 802.1X
        70:7D:B9:AA:CC:11  Staff-WiFi  6     79      WPA2 802.1X
        A4:2B:B0:11:22:33  Guest       11    66      --
```

### Q10 · Multiple choice
<sub>Source: 17.6, 17.7</sub>

What is the most likely cause of the problem?

- [x] The laptop is a sticky client: it stays associated with AP1's distant 2.4 GHz radio although AP2's radios for the same SSID are much stronger
- [ ] The laptop's security settings do not match Staff-WiFi, so it keeps failing authentication
- [ ] Staff-WiFi appears on three BSSIDs, which shows that a rogue AP is copying the SSID
- [ ] The laptop is connected to the Guest SSID instead of Staff-WiFi

> **Explanation:** The `*` in the IN-USE column marks the radio the laptop is using: 70:7D:B9:AA:BB:11, AP1's 2.4 GHz radio on channel 1, with a far weaker signal (27) than AP2's radios (86 on channel 44, 79 on channel 6). A sticky client on a distant BSSID is a classic cause of slow, dropping Wi-Fi. The laptop is associated, and every Staff-WiFi BSSID shows the same WPA2 802.1X security, so security is not the problem. One SSID served by several AP radios is a normal ESS — each radio has its own BSSID, and all three belong to AP1 and AP2. The Guest SSID is not marked as in use.

### Q11 · Multiple choice
<sub>Source: 17.6, 17.7</sub>

The user asks for "the Wi-Fi password" so they can reconnect. Based on the SECURITY column, what does the laptop need to join Staff-WiFi?

- [x] WPA2-Enterprise settings with an EAP method such as PEAP or EAP-TLS, the user's own credentials or certificate, and trust in the RADIUS server's certificate
- [ ] The shared WPA2-Personal passphrase that all staff use
- [ ] No credentials, because Staff-WiFi is open and relies on a captive portal
- [ ] A profile forced to the TKIP cipher

> **Explanation:** `WPA2 802.1X` means WPA2 in Enterprise mode: each user authenticates with an EAP method (PEAP or EAP-TLS) and their own username and password or certificate, and the client must trust the RADIUS server's certificate. A profile set to WPA2-Personal with a passphrase is the classic security-type mismatch after a WLAN moves to Enterprise. Staff-WiFi is not open, and a client forced to TKIP is a typical mistake, because WPA2 uses AES (CCMP).

### Q12 · CLI
<sub>Source: 17.3, 17.6</sub>

After the user turns Wi-Fi off and on, the laptop joins AP2's 5 GHz radio. Using the `iw` tool, enter the command that confirms the current link of interface wlp2s0: the BSSID, the SSID, the frequency and the signal in dBm.

**Prompt:** `$`

**Accepted:** `iw dev wlp2s0 link` · `sudo iw dev wlp2s0 link`

> **Explanation:** `iw dev wlp2s0 link` shows the BSSID the client is connected to, the SSID, the frequency and the signal in dBm. `nmcli device wifi list` gives the wider view of every visible BSSID with its channel, signal and security, which is how the sticky association was spotted.
