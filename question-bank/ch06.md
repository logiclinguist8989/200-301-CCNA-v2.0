# Chapter 6 — EtherChannel with LACP

CCNA-style practice questions for [Chapter 6](../CCNA%20200-301%20v2.0%20Study%20Guide.md#chapter-6--etherchannel-with-lacp) · Domain 2 · Objective 2.1.c. The format is described in the [question bank README](README.md).

## Questions

### Q1 · Multiple choice
<sub>Source: 6.2, 6.3, 6.4</sub>

SW1 has one 1 Gb/s trunk uplink to DSW1. To add bandwidth, an engineer connects a second cable from SW1 Gi0/2 to DSW1 Gi1/0/3 and configures both new ports as trunks with the same settings as the first link. No EtherChannel commands are entered. What is the result?

- [ ] Both links forward, and the switches balance the traffic across them per flow
- [x] Spanning Tree Protocol sees a loop and blocks one of the links, so only one link carries traffic
- [ ] The switches detect the parallel links and bundle them automatically with LACP
- [ ] Both links forward, and frames are sent across them alternately, one frame per link

> **Explanation:** Two parallel Layer 2 links form a loop, so STP blocks one of them: you pay for two links but use one. Nothing bundles by itself — ports join a bundle only when you add them to a channel group with `channel-group <n> mode <mode>`. Once they are bundled, STP sees the port-channel as one interface and every member forwards. Even then, load balancing is per flow, never frame by frame.

### Q2 · Multiple choice — choose two
<sub>Source: 6.3, 6.5, 6.9</sub>

DSW1 uses LACP for all of its bundles. Which two statements about LACP are true? (Choose two.)

- [x] One LACP bundle can include up to 16 links: 8 active and up to 8 in hot-standby
- [x] The switch with the lower LACP system priority decides which links are active
- [ ] The default LACP system priority and port priority are both 1
- [ ] LACP is Cisco proprietary, so it cannot bundle links to a server or to another vendor's switch
- [ ] A port in passive mode starts LACP negotiation as soon as its link comes up

> **Explanation:** LACP manages up to 16 links per bundle, of which 8 are active and the rest are held in hot-standby (flag `H`). Lower system priority wins and decides which links are active; the default system and port priorities are 32768. LACP is the open standard IEEE 802.3ad (now 802.1AX), which is why it works with servers, hypervisors and other vendors — PAgP is the Cisco-proprietary protocol. A passive port only answers LACP; it never starts the negotiation.

### Q3 · Drag and drop — match
<sub>Source: 6.5, 6.10</sub>

Two switches are cabled together, and each side's member ports use the channel-group mode shown. Drag the correct result to each mode pair. A result can be used more than once.

| Side A / Side B | Result |
| --- | --- |
| `active` / `passive` | Bundle forms using LACP |
| `desirable` / `auto` | Bundle forms using PAgP |
| `on` / `on` | Bundle forms without negotiation |
| `passive` / `passive` | No bundle forms |
| `active` / `desirable` | No bundle forms |
| `on` / `active` | No bundle forms |

> **Explanation:** In each protocol, at least one side must start the negotiation: `active` for LACP, `desirable` for PAgP. `passive` + `passive` (like `auto` + `auto`) never bundles because both sides wait. LACP and PAgP cannot negotiate with each other, and `on` sends no negotiation at all, so it bundles only with `on`. A side set to `on` facing a side that does not bundle can create a loop, which is why the misconfiguration guard may err-disable the ports with `channel-misconfig`. Best practice is LACP `active` on both ends.

### Q4 · Multiple choice
<sub>Source: 6.4, 6.6, 6.7, 6.15</sub>

On DSW1, Po1 to SW1 is a healthy LACP trunk bundle with members Gi1/0/1 and Gi1/0/3, native VLAN 999 and allowed VLANs 10,30,40,99. Which change causes Gi1/0/3 to be suspended from Po1?

- [ ] Changing the description on Gi1/0/3 to `Spare uplink to SW1`
- [x] Entering `switchport trunk native vlan 1` on Gi1/0/3 only
- [ ] Using channel group 5 (Po5) on SW1 for its end of the bundle
- [ ] Setting `port-channel load-balance src-dst-ip` on DSW1 while SW1 keeps a different method

> **Explanation:** All members must match each other and the far end in speed, duplex, switchport type and mode, and (for trunk bundles) native VLAN and allowed VLAN list; a member that differs is suspended (`s`). Descriptions do not affect bundling. Channel-group numbers are local, so Po1 on DSW1 can connect to Po5 on SW1. Each end chooses its own load-balance method; the methods do not have to match. To avoid this fault, make Layer 2 changes on interface port-channel 1 so that every member inherits them.

### Q5 · Multiple choice — choose two
<sub>Source: 6.2, 6.9, 6.11</sub>

Refer to the exhibit.

```
DSW1# show etherchannel summary
Flags:  D - down        P - bundled in port-channel
        I - stand-alone s - suspended
        H - Hot-standby (LACP only)
        R - Layer3      S - Layer2
        U - in use      f - failed to allocate aggregator
...
Number of channel-groups in use: 3
Number of aggregators:           3

Group  Port-channel  Protocol    Ports
------+-------------+-----------+-----------------------------------------
1      Po1(SU)         LACP      Gi1/0/1(D)   Gi1/0/3(P)
2      Po2(SU)         LACP      Gi1/0/2(P)   Gi1/0/4(s)
3      Po3(RU)         LACP      Gi1/0/21(P)  Gi1/0/22(P)
```

Which two statements are true? (Choose two.)

- [x] Po1 is still in use and forwards traffic over Gi1/0/3
- [x] Gi1/0/4 is suspended because its configuration differs from Gi1/0/2 or the far end
- [ ] Gi1/0/1 was removed from Po1 because its configuration differs from Gi1/0/3
- [ ] Po3 is a Layer 2 trunk because both of its members show `P`
- [ ] Spanning tree must recalculate before Po1 can forward traffic again

> **Explanation:** `Po1(SU)` is a Layer 2 bundle in use; Gi1/0/1 is `D` (down — a cable fault or a shut-down far end), so traffic simply shifts to the surviving member, Gi1/0/3, in well under a second and without any STP recalculation. `s` on Gi1/0/4 means suspended: members must match each other and the far end, so a difference from Gi1/0/2 or from the far-end port suspends it. A configuration mismatch shows as `s`, not `D`. `R` in `Po3(RU)` means Layer 3 (routed); `P` only says that a member is bundled.

### Q6 · Multiple choice
<sub>Source: 6.9, 6.11</sub>

Refer to the exhibit.

```
SW1# show interfaces trunk

Port        Mode             Encapsulation  Status        Native vlan
Po1         on               802.1q         trunking      999

Port        Vlans allowed on trunk
Po1         10,30,40,99

Port        Vlans allowed and active in management domain
Po1         10,30,40,99

Port        Vlans in spanning tree forwarding state and not pruned
Po1         10,30,40,99
```

SW1's uplinks Gi0/1 and Gi0/2 were just bundled into Po1 with LACP. A colleague notices that Gi0/1 and Gi0/2 no longer appear in this output. What does this mean?

- [x] Nothing is wrong: Gi0/1 and Gi0/2 are members of Po1, and the trunk is listed once, on the port-channel
- [ ] Gi0/1 and Gi0/2 stopped trunking and need `switchport mode trunk` entered on them again
- [ ] Gi0/1 and Gi0/2 are in LACP hot-standby and forward only if an active member fails
- [ ] STP has blocked Gi0/1 and Gi0/2, so the VLANs are carried only by Po1

> **Explanation:** After bundling, the trunk, STP and the MAC table all see the logical interface Po1, so `show interfaces trunk` lists Po1 and not its members — that is the expected result. `show etherchannel summary` would show Gi0/1 and Gi0/2 as `(P)`, bundled. Hot-standby (`H`) only happens when LACP has more than 8 members, and STP treats Po1 as one port instead of blocking its members.

### Q7 · Multiple choice
<sub>Source: 6.4, 6.10, 6.15</sub>

Refer to the exhibit.

```
DSW1# show etherchannel load-balance
EtherChannel Load-Balancing Configuration:
        src-mac

DSW1# show etherchannel summary | include Po3
3      Po3(RU)         LACP      Gi1/0/21(P)  Gi1/0/22(P)

DSW1# show interfaces gigabitethernet1/0/21 | include output rate
  5 minute output rate 936000000 bits/sec, 79100 packets/sec
DSW1# show interfaces gigabitethernet1/0/22 | include output rate
  5 minute output rate 1000 bits/sec, 1 packets/sec
```

DSW1 routes traffic from many hosts in the access VLANs to DSW2 over Po3, a Layer 3 bundle with two 1 Gb/s members. Gi1/0/21 is close to its limit while Gi1/0/22 is almost idle. What should the engineer do to spread the traffic across both members?

- [x] Enter `port-channel load-balance src-dst-ip` in global configuration mode on DSW1
- [ ] Configure the same load-balance method on DSW2, because both ends of a bundle must use the same hash
- [ ] Change both ends to `channel-group 3 mode on` so that frames are sent across the members in turn
- [ ] Enter `port-channel load-balance src-dst-ip` under interface Gi1/0/22 to bring that member into use

> **Explanation:** Both members are bundled (`P`), so this is a load-balancing problem, not a fault. Every frame DSW1 routes onto Po3 carries DSW1's own MAC address as the source, so a `src-mac` hash always gives the same result and picks the same member. A hash on source and destination IP addresses varies per conversation and spreads the flows. `port-channel load-balance` is a global command that applies to all bundles. Each end chooses its own method independently. Load balancing is always per flow, so mode `on` would not send frames across the members in turn; it only skips the checks that LACP performs.

### Q8 · CLI
<sub>Source: 6.5, 6.7, 6.11</sub>

SW2's uplinks Gi0/1 and Gi0/2 to DSW1 are already configured identically as trunks, and you are in interface range configuration mode for both ports. Enter the command that adds them to channel group 2 using LACP, with SW2 starting the negotiation itself.

**Prompt:** `SW2(config-if-range)#`

**Accepted:** `channel-group 2 mode active`

> **Explanation:** `channel-group 2 mode active` adds the ports to group 2, creates interface port-channel 2 if it does not exist yet, and sends LACP packets to start the negotiation. `mode passive` would only answer LACP, and `mode on` would bundle with no negotiation at all. After the bundle is up, make further trunk changes on interface port-channel 2 so that both members inherit them.

### Q9 · Drag and drop — order
<sub>Source: 6.9, 6.10</sub>

A new EtherChannel is not working as expected. Drag the troubleshooting checks into the recommended order.

1. Check the physical state of each member link
2. Confirm that both ends use the same protocol with compatible modes
3. Compare the member configurations (speed, duplex, switchport mode, VLANs)
4. Confirm that the members connect to the expected neighbor
5. Review the load-balance method

> **Explanation:** Start with the physical layer, because a member that is down (`D`) cannot bundle at all. Next, check protocol and modes: LACP on one side only, or `passive` on both, leaves members stand-alone (`I`). Then look for configuration differences that suspend a member (`s`). `show lacp neighbor` shows the far end's system ID and port numbers, which exposes members cabled to the wrong switch. The load-balance method comes last because it affects how evenly traffic spreads, not whether the bundle works.

### Q10 · Multiple choice
<sub>Source: 6.8, 6.9, 6.10</sub>

In the `show etherchannel summary` output, which detail shows that Po3 was created as a Layer 2 bundle?

- [x] The `S` flag in `Po3(SU)`
- [ ] The `U` flag in `Po3(SU)`
- [ ] The `(P)` flag after Gi1/0/21 and Gi1/0/22
- [ ] `LACP` in the Protocol column for group 3

> **Explanation:** On the port-channel, `S` means Layer 2 and `R` means Layer 3, so a routed bundle would show `Po3(RU)`. `U` only means that the bundle is in use, `(P)` only means that a member is bundled, and LACP negotiates Layer 2 and Layer 3 bundles alike — Po1 and Po2 show the same `U`, `P` and `LACP`. A Layer 2 EtherChannel has no addressing, which is why IOS refused the IP address. The members were still Layer 2 when they joined the group, because `no switchport` was never applied before `channel-group 3 mode active`.

### Q11 · Drag and drop — order
<sub>Source: 6.6, 6.8, 6.10</sub>

Drag the steps into the correct order to rebuild Po3 as a routed bundle, starting on DSW1.

1. Remove Gi1/0/21 and Gi1/0/22 from channel group 3
2. Apply `no switchport` to Gi1/0/21, Gi1/0/22 and interface port-channel 3
3. Add the members back with `channel-group 3 mode active`, then configure the IP address on interface port-channel 3
4. Rebuild Po3 on DSW2 the same way, with DSW2's own address
5. Confirm that `show etherchannel summary` on DSW1 lists Po3(RU) with both members (P)

> **Explanation:** A port-channel created from Layer 2 members stays Layer 2, so the members come out of the group first, become routed ports with `no switchport` (and the port-channel is set to `no switchport` as well), and then rejoin the group. The address goes on interface port-channel 3, never on the members. DSW2 made the same mistake, and members must match the far end in switchport type, so DSW2 must be rebuilt too before the check. `Po3(RU)` with both members `(P)` then confirms a Layer 3 bundle in use.

### Q12 · CLI
<sub>Source: 6.8, 6.11</sub>

DSW2's Po3 has been rebuilt as a routed bundle, and you are in interface configuration mode for interface port-channel 3 on DSW2. Enter the command that assigns DSW2's address from the plan in the scenario, using a dotted-decimal mask.

**Prompt:** `DSW2(config-if)#`

**Accepted:** `ip address 10.0.0.6 255.255.255.252`

> **Explanation:** A Layer 3 EtherChannel has one IP address at each end, on the port-channel interface, never on the members. The plan gives DSW2 10.0.0.6/30, and /30 is the mask 255.255.255.252. 10.0.0.4/30 has two usable addresses, 10.0.0.5 (DSW1) and 10.0.0.6 (DSW2). Once Po3 is up with its address, `show ip route` on DSW1 shows `C 10.0.0.4/30 is directly connected, Port-channel3`, and DSW1 can ping 10.0.0.6.
