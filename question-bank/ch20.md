# Chapter 20 — IPv4 access control lists

CCNA-style practice questions for [Chapter 20](../CCNA%20200-301%20v2.0%20Study%20Guide.md#chapter-20--ipv4-access-control-lists) · Domain 4 · Objective 4.6. The format is described in the [question bank README](README.md).

## Questions

### Q1 · Multiple choice
<sub>Source: 20.3</sub>

An engineer needs one ACE that matches exactly the 16 addresses from 10.10.40.16 to 10.10.40.31. Which address and wildcard mask should they use?

- [x] `10.10.40.16 0.0.0.15`
- [ ] `10.10.40.16 0.0.0.16`
- [ ] `10.10.40.16 255.255.255.240`
- [ ] `10.10.40.0 0.0.0.31`

> **Explanation:** 16 addresses starting on a multiple of 16 form a /28 (mask 255.255.255.240). Wildcard = 255.255.255.255 − mask, so 255 − 240 = 15 → **0.0.0.15**, which ignores the last 4 bits and matches .16 to .31. `0.0.0.16` is the block size, not a wildcard: it ignores only one bit. `255.255.255.240` is the subnet mask; as a wildcard it would ignore the first 28 bits instead of the last 4. `10.10.40.0 0.0.0.31` matches 32 addresses, .0 to .31.

### Q2 · Multiple choice — choose two
<sub>Source: 20.2</sub>

Which two statements describe how IOS processes an IPv4 ACL that is applied to an interface? (Choose two.)

- [x] IOS compares the packet with the ACEs from the top and stops at the first ACE that matches.
- [x] A packet that matches no ACE is dropped by an implicit deny that does not appear in the configuration.
- [ ] IOS compares the packet with every ACE and applies the most specific match.
- [ ] An ACL that contains only deny lines blocks the listed sources and permits all other traffic.
- [ ] An outbound ACL also filters the pings and routing updates that the router itself sends.

> **Explanation:** Processing is top-down and the **first match wins**: the router applies that line's action and checks nothing further, so order matters more than specificity. Anything that matches no line hits the invisible **implicit `deny any`** — which is also why an ACL with only deny lines blocks everything and needs at least one `permit`. An outbound ACL does not filter packets the router creates itself, such as its own pings or routing updates.

### Q3 · Drag and drop — match
<sub>Source: 20.4, 20.6, 20.8</sub>

Drag each characteristic to the ACL type it describes. A type can be used more than once.

| Characteristic | ACL type |
| --- | --- |
| Matches on the source IPv4 address only | Standard |
| Can match the protocol, the destination address and the destination port | Extended |
| Configured with `access-list 1450 …` | Standard |
| Configured with `access-list 2100 …` | Extended |
| Normally placed close to the destination | Standard |
| Normally placed close to the source | Extended |
| The usual choice for `access-class` on the VTY lines | Standard |

> **Explanation:** Standard ACLs (1–99 and 1300–1999, so 1450 is standard) match only the source address. Placed near the source they would block that source from every destination, so they go close to the destination; they are also the normal choice for `access-class`, NAT and SNMP. Extended ACLs (100–199 and 2000–2699, so 2100 is extended) match protocol, source and destination addresses and ports, so they can drop exactly the unwanted traffic close to its source.

### Q4 · Multiple choice
<sub>Source: 20.2, 20.7, 20.9</sub>

Refer to the exhibit.

```
DSW1# show access-lists STAFF-IN
Extended IP access list STAFF-IN
    10 permit udp any any eq bootps (12 matches)
    20 permit ip 10.10.10.0 0.0.0.255 any (4471 matches)
    30 deny tcp 10.10.10.0 0.0.0.255 10.10.99.0 0.0.0.255 eq telnet
DSW1# show ip interface vlan 10 | include access list
  Outgoing access list is not set
  Inbound  access list is STAFF-IN
```

The security team wants to stop Staff users (VLAN 10) from opening Telnet sessions to any address in the management VLAN 99, while all their other traffic keeps working. A test shows that Telnet packets from a Staff PC to VLAN 99 still pass DSW1: line 20's counter rises and line 30 stays at zero. Which change fixes the ACL?

- [x] Enter `ip access-list extended STAFF-IN`, remove line 30 with `no 30`, and re-enter the same deny statement with sequence number 15.
- [ ] Rewrite line 30 as `30 deny tcp 10.10.10.0 0.0.0.255 eq telnet 10.10.99.0 0.0.0.255`.
- [ ] Apply STAFF-IN outbound instead of inbound on `interface vlan 10`.
- [ ] Add `40 deny ip any any` so that the end of the ACL denies traffic explicitly.

> **Explanation:** The first match wins. Line 20 permits every packet from 10.10.10.0/24, Telnet to VLAN 99 included, so line 30 is never reached — that is the "a deny line never matches" signature. The specific deny must sit above the general permit, and sequence numbers let you move it without retyping the list. Rewriting line 30 with the port after the source would match source port 23, and the line would still be below line 20. Outbound on VLAN 10 the ACL would check packets heading towards the Staff PCs, whose sources are not in 10.10.10.0/24, so most of them would hit the implicit deny. A final `deny ip any any` changes nothing for Telnet, because line 20 still matches first.

### Q5 · Multiple choice
<sub>Source: 20.6, 20.7</sub>

Refer to the exhibit.

```
R1# show access-lists 110
Extended IP access list 110
    10 permit tcp 10.10.30.0 0.0.0.255 any eq 443 (52 matches)
    20 deny ip 10.10.30.0 0.0.0.255 10.10.99.0 0.0.0.255 (9 matches)
    30 permit ip any any (1377 matches)
```

ACL 110 is applied inbound on one of R1's interfaces. The team wants line 20 removed, while lines 10 and 30 stay in place and the interface stays filtered by ACL 110. Which method does this?

- [x] Enter `ip access-list extended 110`, then `no 20`
- [ ] In global configuration mode, enter `no access-list 110 deny ip 10.10.30.0 0.0.0.255 10.10.99.0 0.0.0.255`
- [ ] On the interface, enter `no ip access-group 110 in`
- [ ] In global configuration mode, enter `no ip access-list extended 110`

> **Explanation:** Numbered ACLs can be edited line by line through `ip access-list extended 110`, where `no 20` removes only that sequence number. The trap: `no access-list 110 …` in global mode deletes the **whole** ACL 110, not one line, and the interface is then left with no filter at all. `no ip access-group 110 in` only removes the ACL from the interface, and `no ip access-list extended 110` deletes the entire list.

### Q6 · CLI
<sub>Source: 20.8</sub>

SW2 already has the standard ACL MGMT-ONLY, which permits 10.10.99.0/24 and PC1 (10.10.10.11). You have entered `line vty 0 15`. Enter the command that lets only the sources permitted by MGMT-ONLY open incoming SSH sessions to SW2.

**Prompt:** `SW2(config-line)#`

**Accepted:** `access-class MGMT-ONLY in`

> **Explanation:** `access-class` applies an ACL to the VTY lines, and with `in` it filters incoming SSH/Telnet sessions by source address — on every IP address of the switch, which an interface ACL (`ip access-group`) cannot do so neatly. A refused source sees "connection refused" before any login prompt. Check that the address you are connected from is permitted before you apply it, and keep console access in case you lock yourself out.

### Q7 · Drag and drop — order
<sub>Source: 20.9</sub>

Since an ACL change on DSW1, a wireless user says one application no longer works. Drag the steps of the ACL troubleshooting method into the correct order.

1. Confirm with `show ip interface` that the ACL is applied to the right interface in the right direction
2. Reset the match counters with `clear access-list counters`
3. Send the test traffic from the user's PC
4. Check with `show access-lists` which line's counter rose
5. If no counter rose, conclude that the packet hit the implicit deny or never reached this interface

> **Explanation:** First make sure the ACL you are looking at is actually filtering this traffic (interface and direction). Clearing the counters before the test makes the next reading meaningful; after the test, the line whose counter rose is the line that decided. The implicit deny has no counter, so "no counter rose" means either the implicit deny dropped the packet or the packet never arrived on this interface.

### Q8 · Multiple choice
<sub>Source: 20.2, 20.5, 20.9</sub>

Refer to the exhibit.

```
R1# show logging | include ADJCHG
*Oct 17 09:15:31.204: %OSPF-5-ADJCHG: Process 1, Nbr 2.2.2.2 on GigabitEthernet0/0/1 from FULL to DOWN, Neighbor Down: Dead timer expired
R1# show access-lists EDGE-IN
Extended IP access list EDGE-IN
    10 permit tcp any any eq 22 (14 matches)
    20 permit tcp any any eq 443 (305 matches)
    30 permit icmp any any (12 matches)
R1# show ip interface gigabitethernet0/0/1 | include access list
  Outgoing access list is not set
  Inbound  access list is EDGE-IN
```

Shortly after an engineer applied EDGE-IN to R1 GigabitEthernet0/0/1, the OSPF adjacency with R2 on that link went down. What is the cause?

- [x] R2's OSPF Hellos match none of the lines, so the implicit deny drops them; a line such as `permit ospf any any` near the top fixes it.
- [ ] OSPF Hellos are ICMP messages, but line 30 cannot match them because they go to a multicast address and `any` matches only unicast addresses.
- [ ] OSPF uses TCP port 89, so the ACL needs a line such as `permit tcp any any eq 89`.
- [ ] EDGE-IN also filters the Hellos that R1 itself sends out of GigabitEthernet0/0/1, so R2 stops hearing them.

> **Explanation:** OSPF runs directly over IP as protocol 89 and uses no ports. EDGE-IN permits only SSH, HTTPS and ICMP, so R2's incoming Hellos match no line and are dropped silently by the implicit deny, which has no counter. When the dead timer expires, R1 drops the neighbor — the classic "routing neighbours drop after an ACL is applied" signature. OSPF is neither ICMP nor TCP, and `any` matches every address, multicast included. EDGE-IN is inbound, so it does not see R1's own Hellos; even an outbound ACL does not filter packets the router itself creates.

### Q9 · Multiple choice — choose two
<sub>Source: 20.2, 20.6, 20.9</sub>

DSW1 and DSW2 share the default gateway for VLAN 30 through HSRP. Which two statements about filtering VLAN 30 traffic with an ACL on the switches' SVIs are true? (Choose two.)

- [x] An ACL applied inbound on `interface vlan 30` does not filter traffic between two hosts in VLAN 30.
- [x] The same ACL must be applied on DSW1 and DSW2, because either switch can be the gateway that routes VLAN 30's traffic.
- [ ] A second inbound IPv4 ACL can be applied to `interface vlan 30`, provided that it has a different name.
- [ ] An ACL name applied with `ip access-group` before any lines are created denies all traffic until lines are added.
- [ ] A standard ACL that denies 10.10.30.0 0.0.0.255 should be applied inbound on `interface vlan 30`, close to the source.

> **Explanation:** An SVI ACL filters only traffic **routed** into or out of the VLAN; traffic between two hosts in the same VLAN is switched and never passes it. With HSRP or VRRP, an ACL on only one gateway disappears from the path after a failover, so it belongs on every possible gateway. Each interface takes one IPv4 ACL per direction. An applied ACL name with no entries permits everything until its first line exists. A standard ACL placed near the source blocks that source from every destination, so it belongs near the destination.

## Testlet A · Protecting the printer and IoT VLAN

Refer to the scenario. VLAN 40 (10.10.40.0/24) holds Printer1 (10.10.40.11) and a group of IoT sensors. The policy says devices in VLAN 40 may obtain addresses with DHCP, use the DNS server 10.10.99.53 and reach the internet, but must not open any other connections into the campus range 10.10.0.0/16. Staff PCs in VLAN 10 print to Printer1 over IPP (TCP 631). An engineer created the extended ACL IOT-IN on DSW1 and DSW2, the HSRP gateways for VLAN 40, and applied it inbound on `interface vlan 40`. The exhibit was captured on DSW1, the HSRP Active switch.

```
DSW1# show access-lists IOT-IN
Extended IP access list IOT-IN
    10 permit udp any any eq bootps (7 matches)
    20 permit udp 10.10.40.0 0.0.0.255 host 10.10.99.53 eq domain (58 matches)
    30 deny ip 10.10.40.0 0.0.0.255 10.10.0.0 0.0.255.255 (36 matches)
    40 permit ip 10.10.40.0 0.0.0.255 any (1214 matches)
DSW1# show ip interface vlan 40 | include access list
  Outgoing access list is not set
  Inbound  access list is IOT-IN
```

### Q10 · Drag and drop — match
<sub>Source: 20.2, 20.3, 20.5</sub>

Drag each packet that arrives on DSW1's `interface vlan 40` to the IOT-IN entry that decides it. An entry can be used more than once.

| Packet arriving on VLAN 40 | Deciding entry |
| --- | --- |
| A new sensor's DHCP Discover (source 0.0.0.0, UDP destination port 67) | Line 10 |
| A DNS query from sensor 10.10.40.25 to 10.10.99.53 | Line 20 |
| A ping from sensor 10.10.40.25 to PC1 (10.10.10.11) | Line 30 |
| An SSH attempt from sensor 10.10.40.25 to DSW1's management address 10.10.99.2 | Line 30 |
| An HTTPS session from sensor 10.10.40.25 to 203.0.113.80 | Line 40 |
| A ping to 203.0.113.80 from a compromised sensor that spoofs the source 198.51.100.7 | Implicit deny |

> **Explanation:** The DHCP Discover has source 0.0.0.0, so only line 10 (`any any eq bootps`) can match it. The DNS query matches line 20 before line 30 can deny it, even though 10.10.99.53 is inside 10.10.0.0/16. The wildcard 0.0.255.255 makes line 30 match every 10.10.x.x destination, so the ping to PC1 and the SSH attempt to 10.10.99.2 are both denied there. 203.0.113.80 is outside 10.10.0.0/16, so the HTTPS session falls through to line 40. A spoofed source outside 10.10.40.0/24 matches none of the lines and is dropped by the implicit deny.

### Q11 · Multiple choice
<sub>Source: 20.2, 20.5, 20.6</sub>

Since IOT-IN was applied, Staff users can no longer print to Printer1, and line 30's counter rises with every attempt. Why?

- [x] Printer1's replies to the Staff PCs arrive on VLAN 40, so IOT-IN checks them and line 30 denies them.
- [ ] The Staff PCs' print jobs leave DSW1 on VLAN 40, and line 30 denies them on the way out.
- [ ] No line permits TCP 631, so the Staff PCs' print jobs hit the implicit deny.
- [ ] Line 40 matches only the `ip` protocol, so it cannot permit TCP traffic such as IPP.

> **Explanation:** IOT-IN is applied **inbound** on VLAN 40, so it checks only packets that arrive from VLAN 40 hosts. The print jobs from 10.10.10.0/24 arrive on VLAN 10 and leave on VLAN 40, where no outbound ACL is applied, so they pass. Printer1's replies (source 10.10.40.11, source port 631, destination 10.10.10.x) arrive on VLAN 40 and match line 30, because their destination is in 10.10.0.0/16 — that is the rising counter. The implicit deny is never reached for them, and `ip` matches every IPv4 packet, TCP included.

### Q12 · CLI
<sub>Source: 20.5, 20.7</sub>

The team decides to permit Printer1's IPP replies to the Staff PCs without letting the sensors open connections into the campus. You have entered `ip access-list extended IOT-IN` on DSW1. Enter the ACE with sequence number 25 that permits TCP traffic from Printer1 (10.10.40.11) with source port 631 to the Staff subnet 10.10.10.0/24.

**Prompt:** `DSW1(config-ext-nacl)#`

**Accepted:** `25 permit tcp host 10.10.40.11 eq 631 10.10.10.0 0.0.0.255` · `25 permit tcp 10.10.40.11 0.0.0.0 eq 631 10.10.10.0 0.0.0.255` · `25 permit tcp host 10.10.40.11 eq 631 10.10.10.0 0.0.0.255 established` · `25 permit tcp 10.10.40.11 0.0.0.0 eq 631 10.10.10.0 0.0.0.255 established`

> **Explanation:** A port written after the **source** is a source port, and Printer1 sends its IPP replies from TCP port 631. Sequence number 25 places the line between 20 and 30, so it is checked before line 30 denies traffic to 10.10.0.0/16. `host 10.10.40.11` and `10.10.40.11 0.0.0.0` mean the same thing. Adding `established` (TCP segments with ACK or RST set) is also correct, and it limits the line to return traffic. Enter the same line on DSW2, the other HSRP gateway, so the fix survives a failover.
