# Chapter 22 — Diagnosing DNS records

CCNA-style practice questions for [Chapter 22](../CCNA%20200-301%20v2.0%20Study%20Guide.md#chapter-22--diagnosing-dns-records) · Domain 4 · Objective 4.4. The format is described in the [question bank README](README.md).

## Questions

### Q1 · Drag and drop — match
<sub>Source: 22.3</sub>

Drag each DNS record type to the data it holds.

| Record | Data it holds |
| --- | --- |
| A | An IPv4 address |
| AAAA | An IPv6 address |
| CNAME | The canonical name that an alias points to |
| MX | A preference value and the host name of a mail server |
| NS | The name of an authoritative server for the zone |
| PTR | The host name that belongs to an address |

**Extra targets:** A preference value and the IPv4 address of a mail server · The primary server, contact and serial number of the zone

> **Explanation:** A and AAAA return addresses (IPv4 and IPv6). CNAME, MX and NS return **names**, so the client must look up that name's A or AAAA record next. PTR maps an address back to a name in the reverse zone. An MX never holds an IP address: it holds a preference and a host name, and that host name's A/AAAA record gives the address. Primary server, contact and serial number are the contents of the SOA record, which is not in the list.

### Q2 · Drag and drop — order
<sub>Source: 22.2</sub>

PC1 needs the address of web1.campus.example. The cache of its recursive resolver is empty. Drag the steps into the order in which they happen.

1. PC1 (the stub resolver) sends one query to its configured recursive resolver
2. The resolver asks a root server and receives a referral to the .example TLD servers
3. The resolver asks a .example TLD server and receives a referral to ns1.campus.example
4. ns1.campus.example returns the A record as an authoritative answer (aa flag set)
5. The resolver caches the record for its TTL and returns the answer to PC1

> **Explanation:** The client sends a single query; the recursive resolver does all the walking: root → TLD → authoritative server. The authoritative server's answer carries the **aa** flag. The resolver then keeps the record for its TTL (in seconds), so the next client that asks gets the answer straight from the cache — and a corrected record can take up to that TTL to reach everyone.

### Q3 · Multiple choice
<sub>Source: 22.4, 22.7</sub>

Refer to the exhibit.

```
$ dig shop.campus.example A
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 51873
;; flags: qr aa rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 1, ADDITIONAL: 1

;; ANSWER SECTION:
shop.campus.example.   3600  IN  CNAME  web3.campus.example.

;; AUTHORITY SECTION:
campus.example.        3600  IN  SOA    ns1.campus.example. admin.campus.example. 2026101601 3600 900 604800 3600

;; SERVER: 10.10.99.53#53(10.10.99.53)
```

Users can open www.campus.example, but shop.campus.example fails. What is the cause?

- [x] shop.campus.example is an alias for web3.campus.example, and that target name has no record.
- [ ] shop.campus.example has no record of any kind in the zone.
- [ ] The DNS server at 10.10.99.53 cannot be reached from the client.
- [ ] The NS records delegate campus.example to a server that does not hold the zone.

> **Explanation:** The ANSWER section shows that the CNAME for shop exists; the NXDOMAIN belongs to its target, web3.campus.example, which does not exist — the "CNAME to a missing target" signature (the query shows the alias, then NXDOMAIN). Fix it by pointing the CNAME at an existing name. A server replied, with the **aa** flag, so the server is reachable and authoritative; a lame delegation would give SERVFAIL, not an answer.

### Q4 · Multiple choice
<sub>Source: 22.3, 22.7</sub>

Refer to the exhibit.

```
C:\> nslookup -type=mx campus.example
Server:  ns1.campus.example
Address:  10.10.99.53

campus.example  MX preference = 10, mail exchanger = smtp.campus.example

C:\> nslookup smtp.campus.example
Server:  ns1.campus.example
Address:  10.10.99.53

Name:    mail.campus.example
Address:  203.0.113.25
Aliases:  smtp.campus.example
```

Some external senders report that mail to users at campus.example bounces. Which change corrects the MX configuration?

- [x] Change the MX record so that it points to mail.campus.example.
- [ ] Change the MX record so that it points to 203.0.113.25.
- [ ] Lower the MX preference from 10 to 0 so that senders try this server first.
- [ ] Add a PTR record for 203.0.113.25 that returns smtp.campus.example.

> **Explanation:** The `Aliases` line shows that smtp.campus.example is a CNAME for mail.campus.example. An MX must point to a host name that has its own A/AAAA record — never to a CNAME and never to an IP address — so it should name mail.campus.example, which has the A record 203.0.113.25. The preference only orders several MX records (lowest first); with a single MX it changes nothing. A PTR record matters when other servers check mail that campus.example **sends**, not for delivery to campus.example.

### Q5 · Multiple choice — choose two
<sub>Source: 22.5</sub>

web1.campus.example moved from 10.10.40.80 to 10.10.40.88, and its A record was updated ten minutes ago. On PC1, `ping web1.campus.example` still sends to 10.10.40.80, while `nslookup web1.campus.example` returns 10.10.40.88. Which two are likely causes? (Choose two.)

- [x] PC1's hosts file contains an entry that maps web1.campus.example to 10.10.40.80.
- [x] PC1's operating system cache still holds the old answer.
- [ ] The A record on the DNS server still contains 10.10.40.80.
- [ ] nslookup reads the hosts file first, but ping always queries the DNS server directly.
- [ ] PC1 has no DNS server configured.

> **Explanation:** The OS resolves names in the order **hosts file → local cache → configured DNS server**, but `nslookup` and `dig` skip the hosts file and the OS cache and ask the server directly. So the server already returns the new address, and the old one comes from a hosts-file entry or a cached answer that has not reached its TTL. Remove the entry and flush the cache (`ipconfig /flushdns`). nslookup got an answer from a server, so PC1 does have a DNS server.

### Q6 · Drag and drop — match
<sub>Source: 22.4</sub>

An engineer queries names with `dig`. Drag each result to its most likely cause.

| Result | Most likely cause |
| --- | --- |
| `status: NXDOMAIN` | The name was mistyped or its record was never created |
| `status: NOERROR` with `ANSWER: 0` for an AAAA query | The name has an A record but no AAAA record |
| `status: SERVFAIL` | The NS records delegate the zone to a server that does not hold it |
| `status: REFUSED` | The resolver does not allow recursion for the client's subnet |
| `connection timed out; no servers could be reached` | An ACL blocks UDP 53 between the client and the DNS server |

**Extra targets:** The A record still holds the server's old address

> **Explanation:** NXDOMAIN means the server answered that the name does not exist. NOERROR with an empty answer ("NODATA") means the name exists but not that record type. SERVFAIL means the resolver could not get a valid answer, for example because of a lame delegation or a down authoritative server. REFUSED means the server will not answer you. A timeout means no DNS server was reached at all: a wrong server address, routing, or UDP 53 blocked. An old address comes back as NOERROR **with** an answer — the data is simply wrong.

### Q7 · Multiple choice
<sub>Source: 22.3, 22.7</sub>

Refer to the exhibit.

```
C:\> nslookup 203.0.113.25
Server:  ns1.campus.example
Address:  10.10.99.53

*** ns1.campus.example can't find 203.0.113.25: Non-existent domain
```

Other mail domains reject or spam-filter mail sent by mail.campus.example, which sends from the public address 203.0.113.25. Which record is missing?

- [x] A PTR record named 25.113.0.203.in-addr.arpa that returns mail.campus.example
- [ ] A PTR record named 203.0.113.25.in-addr.arpa that returns mail.campus.example
- [ ] A PTR record named 25.113.0.203.ip6.arpa that returns mail.campus.example
- [ ] An MX record for campus.example that points to 203.0.113.25

> **Explanation:** `nslookup` with an address performs a PTR lookup, and "Non-existent domain" (NXDOMAIN) shows there is none. Receiving servers often check that the sender's address has a PTR record whose name resolves back to the same address. The PTR name is the address with its **octets reversed** under in-addr.arpa: 203.0.113.25 → 25.113.0.203.in-addr.arpa. ip6.arpa is the IPv6 reverse tree (reversed nibbles), and an MX controls which server **receives** mail and can never hold an IP address. Because the address is public, the address owner (the ISP) usually has to create the PTR.

### Q8 · Multiple choice
<sub>Source: 22.3, 22.7</sub>

Refer to the exhibit.

```
C:\> nslookup web1.campus.example
Server:  ns1.campus.example
Address:  10.10.99.53

Name:    web1.campus.example
Addresses:  2001:db8:10:4::80
          10.10.40.80
```

web1 is configured with 10.10.40.80 and 2001:db8:10:40::80. Users on dual-stack PCs say the intranet on web1 is very slow to open or does not open at all; users on IPv4-only PCs open it normally. What is the cause?

- [x] The AAAA record for web1 holds a wrong IPv6 address, and dual-stack clients try IPv6 first.
- [ ] The A record for web1 holds a wrong IPv4 address.
- [ ] Dual-stack clients use the A record first and time out before they try the AAAA record.
- [ ] web1's address has no PTR record, so every browser waits for a reverse lookup.

> **Explanation:** The AAAA record returns 2001:db8:10:**4**::80 instead of 2001:db8:10:**40**::80 — a different /64. Dual-stack clients prefer IPv6, so they try the wrong address first and access is slow or fails, although the A record (10.10.40.80) is correct; that is why IPv4-only PCs are fine. Check with `nslookup -type=aaaa web1.campus.example` and fix the AAAA record. A missing PTR would affect IPv4-only and dual-stack clients alike, and it typically slows logins such as SSH rather than stopping access.

### Q9 · Multiple choice
<sub>Source: 22.3, 22.7</sub>

ns1 is the primary server and ns2 a secondary server for campus.example. Yesterday web1 moved from 10.10.40.80 to 10.10.40.88, and the A record was changed on ns1. Today some users still reach the old address, even after flushing their caches. Refer to the exhibit.

```
$ dig @ns1.campus.example web1.campus.example A +short
10.10.40.88
$ dig @ns2.campus.example web1.campus.example A +short
10.10.40.80
$ dig @ns1.campus.example campus.example SOA +short
ns1.campus.example. admin.campus.example. 2026101601 3600 900 604800 3600
$ dig @ns2.campus.example campus.example SOA +short
ns1.campus.example. admin.campus.example. 2026101501 3600 900 604800 3600
```

What is the most likely cause?

- [x] ns2 has not received the updated zone from ns1; its older SOA serial number shows it still serves the previous version.
- [ ] The A record on ns1 is wrong and must be changed back to 10.10.40.80.
- [ ] The NS records delegate campus.example to a server that does not hold the zone.
- [ ] The users' recursive resolver cached the old answer and will keep it until the record's TTL expires.

> **Explanation:** Querying both authoritative servers directly removes every cache from the test, and the two servers disagree. ns2's SOA serial (2026101501) is older than ns1's (2026101601), so ns2 is a secondary that was not updated and serves stale data. Check that zone transfers from ns1 to ns2 work (they use TCP 53) and that the serial is increased with every change. A lame delegation produces SERVFAIL, not an old answer, and a resolver's cache cannot explain why ns2 itself, queried directly, returns the old address.

### Q10 · CLI
<sub>Source: 22.6</sub>

R1 has `ip name-server 10.10.99.53`, and `ip domain lookup` is enabled. Refer to the exhibit.

```
R1# ping web1
Translating "web1"...domain server (10.10.99.53)
% Unrecognized host or address, or protocol not running.

R1# ping web1.campus.example
Translating "web1.campus.example"...domain server (10.10.99.53) [OK]

Type escape sequence to abort.
Sending 5, 100-byte ICMP Echos to 10.10.40.80, timeout is 2 seconds:
!!!!!
Success rate is 100 percent (5/5), round-trip min/avg/max = 1/1/1 ms
```

Enter the global configuration command that makes R1 append the domain campus.example to short names such as web1.

**Prompt:** `R1(config)#`

**Accepted:** `ip domain name campus.example` · `ip domain-name campus.example`

> **Explanation:** The name server works — the full name resolves — but R1 sends the short name unchanged. `ip domain name campus.example` (or the equivalent `ip domain-name campus.example`, the form used in Chapter 18) is appended to short names, so web1 becomes web1.campus.example; the same domain name is also needed to generate SSH keys. `ip host` would only add one static name on the device, and `no ip domain lookup` would mean names no longer resolve on R1 at all.

## Testlet A · Staff PCs cannot resolve names

Refer to the scenario. Last night an engineer edited the DHCP pools on R1 (10.0.0.1), the DHCP server for the campus. This morning, users in VLAN 10 (Staff) say that no internal web page opens by name; users in VLAN 30 (Wireless) are not affected. From PC1, `ping 10.10.40.80` succeeds. The campus DNS server, DNS1, is at 10.10.99.53.

```
C:\> ipconfig /all

   Connection-specific DNS Suffix  . : campus.example
   DHCP Enabled. . . . . . . . . . . : Yes
```

```
 domain-name campus.example
```

### Q11 · Multiple choice
<sub>Source: 22.6, 22.7</sub>

What is the cause of the Staff users' problem?

- [x] The STAFF pool hands out 10.10.99.35 as the DNS server, an address where no DNS server answers.
- [ ] An ACL blocks UDP 53 from VLAN 10 to 10.10.99.53.
- [ ] DNS1 has no PTR record for its own address, so nslookup cannot complete the query.
- [ ] www.campus.example has no A record on DNS1.

> **Explanation:** The service works by IP address, so this is a name problem, and the query **times out**: no DNS server was reached. `ipconfig /all` shows why — PC1 uses 10.10.99.35, which came from the STAFF pool's `dns-server` line, while WIRELESS still hands out 10.10.99.53. A wrong DHCP `dns-server` value breaks name resolution for a whole subnet. PC1 never sends its queries to 10.10.99.53, so an ACL on that path is not the cause. `Server: UnKnown` is a side effect here: nslookup could not even look up the server's own name. A missing record would produce NXDOMAIN from a server that answers, not a timeout.

### Q12 · CLI
<sub>Source: 22.6, 22.8, 22.9</sub>

You have entered `ip dhcp pool STAFF` on R1. Enter the command that gives Staff clients the correct DNS server, 10.10.99.53.

**Prompt:** `R1(dhcp-config)#`

**Accepted:** `dns-server 10.10.99.53`

> **Explanation:** `dns-server 10.10.99.53` corrects the value the STAFF pool hands out. The PCs learn the new value only when they renew their lease, so on PC1 run `ipconfig /release` and `ipconfig /renew`, then confirm with `ipconfig /all` that the DNS server is 10.10.99.53. `ipconfig /flushdns` only clears cached answers; it does not change the DNS server the PC uses.
