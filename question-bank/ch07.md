# Chapter 7 — Edge-host ports: VLAN, PoE, port channel and LACP

CCNA-style practice questions for [Chapter 7](../CCNA%20200-301%20v2.0%20Study%20Guide.md#chapter-7--edge-host-ports-vlan-poe-port-channel-and-lacp) · Domain 2 · Objectives 2.2 and 2.2.a–e. The format is described in the [question bank README](README.md).

## Questions

### Q1 · Multiple choice
<sub>Source: 7.2</sub>

New desktops on SW1 access ports often fail to get a DHCP address right after they boot. When the user retries about a minute later, the address arrives. Each port is configured with `description`, `switchport mode access`, `switchport access vlan 10`, `spanning-tree bpduguard enable` and `no shutdown`. Which command from the edge-port baseline would fix the delay?

- [x] `spanning-tree portfast`
- [ ] `switchport nonegotiate`
- [ ] `power inline auto`
- [ ] `switchport voice vlan 20`

> **Explanation:** Without PortFast, spanning tree holds a new link for about 30 seconds before it forwards, so the PC's first DHCP requests time out. With `spanning-tree portfast` the host gets a working link in about a second. `switchport nonegotiate` concerns DTP, which `switchport mode access` already keeps from forming a trunk; it has nothing to do with the delay. Desktops are not powered devices, so PoE is irrelevant, and `switchport voice vlan 20` adds a voice VLAN for an IP phone; it does not change how quickly the desktop's port starts forwarding.

### Q2 · Drag and drop — match
<sub>Source: 7.2, 7.6, 7.7</sub>

Every device below has a single uplink to the switch, except the hypervisor host, which has two. Drag the switch-port configuration that best fits each device. A configuration can be used more than once.

| Device | Switch port |
| --- | --- |
| PoE-powered IP camera in the IoT VLAN | Access port |
| IP phone with a PC plugged into it | Access port with a voice VLAN |
| Standalone AP broadcasting Staff-WiFi and Guest | Trunk |
| Controller-based AP in local mode | Access port |
| FlexConnect AP with local switching at a branch | Trunk |
| Hypervisor host whose NIC teaming uses LACP | Trunk inside an LACP port-channel |

**Extra targets:** Routed port with an IP address

> **Explanation:** Devices that need one VLAN — cameras, printers, desktops — get an access port, with IoT devices in their own VLAN. An IP phone with a PC behind it stays an access port but adds a voice VLAN. A standalone AP maps each SSID to a VLAN itself, so its port is a trunk (native VLAN = AP management); a FlexConnect AP that switches client traffic locally needs a trunk too. A controller-based AP in local mode tunnels client traffic to the WLC, so it needs only an access port in the AP management VLAN. A hypervisor carries VMs in several VLANs, so it needs a trunk, bundled with LACP only because its teaming uses LACP. None of these edge devices needs a routed port.

### Q3 · Multiple choice — choose two
<sub>Source: 7.4</sub>

Which two statements about Power over Ethernet on a Cisco access switch are correct? (Choose two.)

- [x] The switch powers a port only after it detects a powered device's signature resistance, so a PC's NIC never receives power.
- [x] `power inline static max 30000` reserves 30 W for the port in advance, even before a device connects.
- [ ] Most PoE switches default to `power inline never`, so each PoE port must be enabled manually.
- [ ] IEEE 802.3at (PoE+) supplies up to 15.4 W at the switch port.
- [ ] When the remaining power budget cannot cover a new device's request, the switch powers the device anyway and lowers power on other ports.

> **Explanation:** A PoE port goes through detection (a low test voltage looking for a PD's signature resistance), classification, power-up and monitoring. A PC NIC has no signature, so it is never powered. `power inline static max 30000` reserves 30 W (the value is in milliwatts) before anything is plugged in. Most PoE switches default to `power inline auto`. 802.3af supplies 15.4 W and 802.3at (PoE+) 30 W. If the remaining budget cannot cover a request, the switch denies power to the new device and logs it.

<sub>Source: 7.5, 7.9, 7.10</sub>

Refer to the exhibit.

```
SW4# show interfaces gigabitethernet1/0/15 switchport
Name: Gi1/0/15
Switchport: Enabled
Administrative Mode: static access
Operational Mode: static access
Access Mode VLAN: 10 (STAFF)
Voice VLAN: none
...
SW4# show mac address-table interface gigabitethernet1/0/15
          Mac Address Table
-------------------------------------------

Vlan    Mac Address       Type        Ports
----    -----------       --------    -----
  10    0001.c7a1.b2e6    DYNAMIC     Gi1/0/15
  10    0050.56a1.33c0    DYNAMIC     Gi1/0/15
Total Mac Addresses for this criterion: 2
```

SW4 Gi1/0/15 was recently re-patched to a Cisco IP phone (MAC 0001.c7a1.b2e6) with a PC plugged into the phone's PC port. Both devices work, but the call team reports that the phone's traffic is mixed with user traffic. The phone should be in VLAN 20 (VOICE), which already exists on SW4 and is allowed on the uplink trunk, and the PC should stay in VLAN 10. You are in interface configuration mode for Gi1/0/15. Enter the command that fixes the problem.

**Prompt:** `SW4(config-if)#`

**Accepted:** `switchport voice vlan 20`

> **Explanation:** The MAC address table should show the phone's MAC in VLAN 20 and the PC's MAC in VLAN 10 on the same port. Here both MACs are in VLAN 10, and `Voice VLAN: none` explains why: the port has no voice VLAN to advertise, so the phone sends untagged frames that the switch places in access VLAN 10. After `switchport voice vlan 20`, CDP tells the phone to use VLAN 20; the phone tags its own frames with VLAN 20 and CoS 5, while the PC's frames stay untagged in VLAN 10. The port remains `static access` and does not become a trunk.

### Q5 · Multiple choice
<sub>Source: 7.5, 7.9</sub>

Refer to the exhibit.

```
SW1# show interfaces trunk

Port        Mode         Encapsulation  Status        Native vlan
Gi0/1       on           802.1q         trunking      999

Port        Vlans allowed on trunk
Gi0/1       10,30,40,99

Port        Vlans allowed and active in management domain
Gi0/1       10,30,40,99

Port        Vlans in spanning tree forwarding state and not pruned
Gi0/1       10,30,40,99
```

New IP phones are connected to SW1 access ports configured with `switchport access vlan 10` and `switchport voice vlan 20`. The phones power up but never get an IP address, while the PCs plugged into them work normally. VLAN 20 exists on SW1 and DSW1. Gi0/1 is SW1's uplink to DSW1, which is the gateway and DHCP server for every VLAN. What is the cause?

- [x] VLAN 20 is not allowed on the uplink trunk, so the phones' DHCP requests never reach DSW1.
- [ ] The phone ports are not listed in the output; they must be trunks to carry the phones' tagged frames.
- [ ] CDP is disabled on the access ports, so the phones never learn their voice VLAN.
- [ ] The native VLAN must be 20 so that the phones' frames cross the trunk.

> **Explanation:** The voice VLAN must exist on the switch **and** be carried on the uplink trunks. VLAN 20 is missing from the allowed list, so voice traffic stops at SW1; the PCs' VLAN 10 is allowed, which is why they work. The fix is `switchport trunk allowed vlan add 20` on Gi0/1, and the same on DSW1's end of the trunk if it is also pruned. A port with a voice VLAN is an access port and never appears in `show interfaces trunk`, so its absence is normal. If CDP were disabled, the phones would get addresses in the data subnet rather than none. The phones tag voice frames with VLAN 20, so the native VLAN is not involved.

### Q6 · Multiple choice — choose two
<sub>Source: 7.6</sub>

LAP-1 is a controller-based AP in local mode. It is connected to SW4 Gi1/0/5, an access port in AP management VLAN 99, and broadcasts Staff-WiFi (VLAN 30) and Guest (VLAN 35). Which two statements are correct? (Choose two.)

- [x] LAP-1 sends its clients' frames to the WLC inside a CAPWAP tunnel, and the WLC places them on the right VLAN.
- [x] CAPWAP control traffic uses UDP 5246 and is encrypted with DTLS; client data uses UDP 5247.
- [ ] Gi1/0/5 must be a trunk that allows VLANs 30 and 35, or the wireless clients cannot get addresses.
- [ ] LAP-1 discovers the WLC before it requests an IP address, using CDP on Gi1/0/5.
- [ ] LAP-1 maps each SSID to its VLAN itself, in the same way as a standalone AP.

> **Explanation:** A local-mode AP tunnels every client frame to the WLC over CAPWAP (control on UDP 5246, encrypted with DTLS; data on UDP 5247). The WLC maps SSIDs to VLANs on its own trunk, so the AP's port only needs VLAN 99 as an access port. The AP gets its address by DHCP in VLAN 99 first and only then discovers the WLC, through DHCP option 43, DNS or a broadcast — not through CDP. Mapping each SSID to a VLAN on the AP itself, and therefore needing a trunk, is how a standalone AP works.

### Q7 · Drag and drop — order
<sub>Source: 7.6</sub>

A new controller-based AP is plugged into a PoE access port in VLAN 99. Drag the steps of its start-up into the correct order.

1. The AP boots on power from the switch port (PoE)
2. The AP gets an IP address by DHCP in VLAN 99
3. The AP discovers the WLC through DHCP option 43, DNS or a broadcast
4. The AP builds a CAPWAP tunnel to the WLC
5. The AP downloads its configuration from the WLC
6. The AP starts broadcasting its SSIDs

> **Explanation:** The AP needs power first, then an IP address in the AP management VLAN. Only with an address can it find a WLC — by DHCP option 43, the DNS name `CISCO-CAPWAP-CONTROLLER` or a broadcast. It then builds the CAPWAP tunnel, downloads its configuration through it and only then starts its SSIDs. If it never joins, check DHCP and routing in VLAN 99 and whether UDP 5246–5247 is blocked.

### Q8 · Multiple choice
<sub>Source: 7.6, 7.8</sub>

An older wireless LAN controller running AireOS connects to SW4 Gi1/0/23 and Gi1/0/24. Both switch ports are trunks carrying VLANs 30, 35 and 99, and they are to be bundled into Port-channel 23 for redundancy. Which command should be applied to both switch ports?

- [x] `channel-group 23 mode on`
- [ ] `channel-group 23 mode active`
- [ ] `channel-group 23 mode passive`
- [ ] `channel-group 23 mode desirable`

> **Explanation:** Older AireOS controllers bundle their uplinks statically and do not run LACP, so the switch side must use static `mode on`. The LACP modes `active` and `passive` would find no LACP partner, and `desirable` is a PAgP mode. Newer Catalyst 9800 controllers support LACP, so always check the controller platform before choosing the channel mode.

### Q9 · Multiple choice
<sub>Source: 7.7, 7.10</sub>

Hypervisor host ESXi-02 connects two NICs to SW4 Gi1/0/13 and Gi1/0/14. The server team has set the host's NIC teaming to an independent mode that does not use LACP. The switch ports are configured as trunks for VLANs 10, 30 and 99 and with `channel-group 13 mode active`. VMs on the host keep losing connectivity. What should the network engineer do?

- [x] Remove `channel-group` from both ports and keep them as identical trunks, each with `spanning-tree portfast trunk`.
- [ ] Change both ports to `channel-group 13 mode passive`, so the switch waits for the host to start LACP.
- [ ] Change both ports to `channel-group 13 mode on`, so the bundle forms without negotiation.
- [ ] Keep `channel-group 13 mode active` and add `spanning-tree portfast trunk` to Port-channel 13.

> **Explanation:** Bundle a host's ports only when the host's teaming uses LACP. Here the teaming mode and the switch bundling disagree, which makes VMs flap or lose connectivity. The fix is to match the two sides: either the host uses LACP, or the switch drops `channel-group` and keeps both ports as identical trunks with `spanning-tree portfast trunk`. `passive` still expects LACP from a host that never sends it, and `on` still bundles on the switch while the host does not. Adding PortFast to Port-channel 13 changes only how fast the port forwards; the switch still bundles the ports while the host does not.

### Q10 · CLI
<sub>Source: 7.7</sub>

You are configuring Port-channel 11, an LACP trunk to hypervisor host ESXi-01. The host does not run STP or bridge between its NICs, and the trunk settings are already in place. You are in interface configuration mode for Port-channel 11. Enter the PortFast command that makes this trunk start forwarding immediately when it comes up.

**Prompt:** `SW4(config-if)#`

**Accepted:** `spanning-tree portfast trunk` · `spanning-tree portfast edge trunk`

> **Explanation:** A trunk to a host uses the trunk form of PortFast, `spanning-tree portfast trunk`, configured on the port-channel interface. Newer IOS releases write the same command as `spanning-tree portfast edge trunk`. Use PortFast on a host trunk only when the host does not run STP or bridge between its NICs, which is normal for hypervisors. Do not use it on an appliance in transparent (bridging) mode without following the vendor's design.

### Q11 · Drag and drop — match
<sub>Source: 7.10</sub>

Drag each edge-port symptom to its most likely cause.

| Symptom | Likely cause |
| --- | --- |
| The phone works, but the PC behind it has no network | Wrong access VLAN, or data VLAN missing from the uplink trunk |
| Clients on one SSID of a standalone AP get no address | That SSID's VLAN missing from the AP's trunk |
| A lightweight AP never joins the WLC | No DHCP or route to the WLC, or UDP 5246–5247 blocked |
| A port goes err-disabled as soon as a device is connected | BPDU guard received a BPDU from a switch or bridging appliance |
| An AP boots with reduced radios | PoE class higher than the port supplies |
| Users cannot reach a printer in its own VLAN | No inter-VLAN routing, or an ACL blocks it |

**Extra targets:** Speed and duplex left on auto

> **Explanation:** If the phone works but the PC behind it does not, look at the access VLAN and at the data VLAN on the uplink trunk. A standalone AP needs every SSID's VLAN on its trunk. A lightweight AP needs an address, a route to the WLC and open CAPWAP ports. BPDU guard shuts a port that receives BPDUs from a switch or an appliance in bridge mode. An AP that needs more power than the port's PoE class or maximum allows may boot with reduced radios. A printer in its own VLAN needs a gateway SVI for inter-VLAN routing, and no ACL blocking users. Speed and duplex on auto is the recommended edge-port setting and causes none of these symptoms.

### Q12 · Multiple choice
<sub>Source: 7.4, 7.10</sub>

Based on the exhibit, why does the IP phone on Gi1/0/8 have no lights?

- [x] PoE is disabled on Gi1/0/8 with `power inline never`, so the switch never powers the phone.
- [ ] The switch's PoE budget is exhausted, so the switch denied power to the phone.
- [ ] The phone's power class is higher than the 30 W maximum of Gi1/0/8.
- [ ] Gi1/0/8 detected an overcurrent and moved to the `err-disable` state.

> **Explanation:** Admin `off` is how `show power inline` shows a port set to `power inline never`, so Gi1/0/8 does not even try to detect or power a device. The budget is not the problem: 362.0 W of the 390.0 W remains. The other IP phones draw only 6.3 W each, well under the 30 W port maximum. An overcurrent or bad cable would show a state of `faulty` or `err-disable`, not Admin `off`. The fix is `power inline auto` on Gi1/0/8.

Based on the exhibit, which two statements are correct? (Choose two.)

### Q14 · CLI
<sub>Source: 7.4, 7.6, 7.10</sub>

The engineer decides to keep Gi1/0/9 in automatic detection mode but to allow it up to the 30 W that PoE+ supplies, stated in milliwatts. You are in interface configuration mode for Gi1/0/9. Enter the command.

**Prompt:** `SW4(config-if)#`

**Accepted:** `power inline auto max 30000`

> **Explanation:** The Max column shows Gi1/0/9 capped at 15.4 W, which matches `power inline auto max 15400`. An AP that needs PoE+ on a port that supplies only 15.4 W may boot with reduced radios, which is the symptom here. `power inline auto max 30000` keeps automatic detection and raises the cap to 30 W (the value is in milliwatts). `power inline static max 30000` would also give 30 W, but it reserves the power in advance instead of keeping automatic mode.
