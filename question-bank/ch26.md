## Questions

### Q1 · Drag and drop — match
<sub>Source: 26.2</sub>

Drag each set of strengths and limits to the network management approach it describes.

| Strengths and limits | Approach |
| --- | --- |
| Needs no extra systems and works when everything else is down, but is slow and inconsistent at scale | Device-based |
| Nothing to host and quick to deploy at many sites, but needs internet access and a subscription | Cloud-based |
| Central policy, image management and assurance, but the system must be designed, sized and kept available | Controller-based |
| The same change reaches hundreds of devices in minutes, but scripts must be maintained and credentials protected | Automation-based |
| Every change is versioned, reviewed and easy to roll back, but manual changes on the devices break the model | Infrastructure as code |

> **Explanation:** The approaches differ in where the source of truth lives and how a change reaches the devices. **Device-based** management keeps the truth in each running configuration and needs nothing else, which is why it still works in an emergency. **Cloud-based** management (for example Meraki) is a controller run by the vendor, so there is nothing to host, but every site depends on its internet connection. A **controller** (Catalyst Center, a WLC, SD-WAN Manager) is hosted by you and must be designed for availability. **Automation-based** management pushes changes with scripts or tools such as Ansible, which must be written, tested and kept secure. **Infrastructure as code** keeps the desired state in version-controlled files, so a manual change on a device breaks the model.

### Q2 · Multiple choice — choose two
<sub>Source: 26.3</sub>

Catalyst Center manages the campus switches, routers and wireless. Which two statements about the controller's northbound and southbound interfaces are true? (Choose two.)

- [x] Scripts, Ansible and ticketing systems use the northbound interface, which is usually a REST API that carries JSON over HTTPS.
- [x] NETCONF, which carries XML over SSH on port 830, is one of the southbound protocols the controller can use to reach devices.
- [ ] The northbound interface faces the network devices, and the southbound interface faces applications and operators.
- [ ] Lightweight access points use CAPWAP to reach the controller's northbound API.
- [ ] Because the controller centralises management, the switches send every packet to it for a forwarding decision.

> **Explanation:** **Northbound** faces applications: scripts, Ansible, ticketing systems and dashboards call a REST API with JSON over HTTPS. **Southbound** faces devices: NETCONF (XML over SSH, port 830), RESTCONF, SSH CLI, SNMP and, for lightweight APs, CAPWAP, so CAPWAP is a southbound protocol. Swapping the two directions is a common mistake. The controller centralises the management plane (and in some designs parts of the control plane); the devices still forward traffic in their own data plane.

### Q3 · Drag and drop — order
<sub>Source: 26.4</sub>

The campus switches are managed as infrastructure as code, with the playbooks and variables stored in Git. An engineer must add VLAN 50 to the switches. Drag the steps into the order the change follows.

1. Create a branch and add VLAN 50 to `group_vars/switches.yml`
2. Open a pull request so that a colleague reviews the difference
3. Let the automated checks run (lint and an `ansible-playbook --check --diff` dry run)
4. Merge the branch
5. Let the CI/CD pipeline run the playbook against the switches and verify the result

> **Explanation:** In IaC the files in the repository are the source of truth, and a change follows a software-style workflow: branch and edit, pull request and peer review, automated checks (syntax, lint and a dry run that shows what would change), merge, then a pipeline deploys and verifies. Nobody types the change on the switches. If the change has to be undone, the engineer reverts the commit and lets the pipeline deploy the previous state.

### Q4 · Multiple choice
<sub>Source: 26.4</sub>

DSW1 is managed as infrastructure as code, and the Git repository is its source of truth. During an outage, an engineer logged in to DSW1 and changed the name of VLAN 40 by hand. The next dry run with `--check --diff` shows that the pipeline would change the name back. Which term describes the condition that the dry run found?

- [x] Configuration drift
- [ ] Idempotence
- [ ] Imperative configuration
- [ ] Declarative configuration

> **Explanation:** **Configuration drift** means a device differs from the source of truth, usually after a manual change; IaC tools detect and correct it. **Idempotence** means that running the same automation again changes nothing when the device is already in the desired state — here DSW1 is not in that state, so the run would change it. **Declarative** (describe the end state) and **imperative** (list the exact commands in order) describe how automation is written, not a mismatch between a device and its source of truth.

### Q5 · Drag and drop — match
<sub>Source: 26.5</sub>

Drag each item from an Ansible project to the Ansible building block it is.

| Item | Building block |
| --- | --- |
| The Linux VM with Python and Ansible installed, where `ansible-playbook` is run | Control node |
| R1, DSW1 and SW1, reached over SSH | Managed nodes |
| `inventory.ini`, which lists the groups `[routers]` and `[switches]` | Inventory |
| One `hosts: campus` section together with its list of tasks | Play |
| `cisco.ios.ios_config` | Module |
| `cisco.ios` and `ansible.netcommon` | Collection |

**Extra targets:** Agent · Playbook

> **Explanation:** The **control node** runs everything and opens SSH sessions to the **managed nodes**; nothing is installed on the devices, because Ansible is **agentless**. The **inventory** lists the devices and groups with their connection variables. A **playbook** (for example `show.yml`) is the YAML file that holds one or more **plays**; a play names the hosts and the tasks to run on them. Each task is done by a **module**, the code that does the work, and modules for a platform are packaged in a **collection**.

### Q6 · Multiple choice
<sub>Source: 26.5</sub>

An engineer writes a playbook that must make sure `logging trap informational` is in the configuration of every campus device, and it must send the line only to the devices that do not already have it. Which module should the task use?

- [x] `cisco.ios.ios_config`
- [ ] `cisco.ios.ios_command`
- [ ] `ansible.builtin.debug`
- [ ] `ansible.netcommon.network_cli`

> **Explanation:** `cisco.ios.ios_config` compares its `lines` with the running configuration and sends only what is missing, so it is idempotent. `cisco.ios.ios_command` runs commands such as show commands; it is not the module for configuration changes. `ansible.builtin.debug` only prints a variable, such as a result stored with `register`. `ansible.netcommon.network_cli` is the connection type set with `ansible_connection`, not a module that a task runs.

### Q7 · Multiple choice
<sub>Source: 26.5, 26.6</sub>

Refer to the exhibit.

```
- name: Uplink descriptions
  hosts: switches
  gather_facts: false
  tasks:
    - name: Describe Gi0/1
      cisco.ios.ios_config:
        parents: interface GigabitEthernet0/1
        lines:
          - description Uplink-DSW1
        save_when: modified
```

Yesterday this playbook added the description under GigabitEthernet0/1 on lab-sw1, the only host in the `switches` group. Nobody has changed the switch since. What happens when the engineer runs the playbook again today?

- [x] The task reports changed=0 for lab-sw1, and the configuration is not saved again.
- [ ] The task sends the description line again and reports changed=1, because `ios_config` sends all of its lines on every run.
- [ ] The task fails, because the description already exists under the interface.
- [ ] The task reports changed=1, because `save_when: modified` copies the running configuration to the startup configuration on every run.

> **Explanation:** `ios_config` compares the `lines` with the running configuration — under the section named in `parents` — and sends only what is missing. The description is already there, so nothing is sent and the recap shows **changed=0**: idempotence. `save_when: modified` saves to the startup configuration only when something changed, so there is no save either. A line that is already present is not an error.

### Q8 · Multiple choice
<sub>Source: 26.5, 26.6, 26.7</sub>

Refer to the exhibit.

```
$ ansible-playbook show.yml -k
SSH password:

PLAY [Collect version and interface status] ***********************************

TASK [Run show commands] ******************************************************
ok: [lab-r1]
fatal: [lab-sw1]: UNREACHABLE! => {"changed": false, "msg": "ssh connection failed: Failed to connect to 192.168.100.21:22", "unreachable": true}

TASK [Display the results] ****************************************************
ok: [lab-r1] => {
    "output.stdout_lines": [
        [
            "lab-r1 uptime is 2 hours, 14 minutes"
        ],
        [
            "Interface              IP-Address      OK? Method Status                Protocol",
            "GigabitEthernet0/0     192.168.100.11  YES manual up                    up      ",
            "GigabitEthernet0/1     unassigned      YES unset  administratively down down    "
        ]
    ]
}

PLAY RECAP ********************************************************************
lab-r1   : ok=2  changed=0  unreachable=0  failed=0  skipped=0  rescued=0  ignored=0
lab-sw1  : ok=0  changed=0  unreachable=1  failed=0  skipped=0  rescued=0  ignored=0
```

The management address of lab-sw1 is 192.168.100.12. What is the most likely cause of the problem with lab-sw1, and what should the engineer do?

- [x] The `ansible_host` value for lab-sw1 in the inventory is wrong; correct it and test with `ping` and `ssh` from the VM.
- [ ] User ansible has privilege level 1 on lab-sw1; give the user privilege 15.
- [ ] `show ip interface brief` is not valid on lab-sw1; remove it from the task.
- [ ] The playbook has a YAML indentation error; replace the tabs in `show.yml` with spaces.

> **Explanation:** **Unreachable** always means that Ansible could not connect or log in, never that a task returned an error. The message shows an SSH connection attempt to 192.168.100.21 instead of 192.168.100.12, so the `ansible_host` entry is wrong; fix it, then test with `ping` and `ssh` from the VM. A privilege problem or an invalid command would appear as **failed**, because the session would open and the task would run. A YAML error stops the playbook before any device is contacted, yet lab-r1 returned output. Show commands never report *changed*.

### Q9 · CLI
<sub>Source: 26.7</sub>

An engineer has edited `logging.yml` and wants to check it for YAML errors such as tab indentation before the playbook contacts any device. `ansible.cfg` in the project folder already points to `inventory.ini`, so no inventory option is needed. Enter the `ansible-playbook` command that only checks the syntax of `logging.yml`.

**Prompt:** `$`

**Accepted:** `ansible-playbook --syntax-check logging.yml` · `ansible-playbook logging.yml --syntax-check`

> **Explanation:** `--syntax-check` parses the playbook and reports errors such as `Syntax Error while loading YAML`. YAML allows only spaces for indentation and needs it to be consistent. Because the YAML is parsed before any task runs, a playbook with a syntax error changes no device. `--check --diff` does something else: it is a dry run that shows what would change on the devices.

### Q10 · Multiple choice
<sub>Source: 26.5, 26.7</sub>

What does the output show about lab-sw1?

- [x] Ansible logged in to lab-sw1, but the task returned an error, so the logging lines were not added.
- [ ] Ansible could not open an SSH session to lab-sw1, so no command reached the switch.
- [ ] lab-sw1 already had the logging lines, so `ios_config` had nothing to send.
- [ ] A YAML error in the playbook stopped the run before any device was contacted.

> **Explanation:** **failed** with **unreachable=0** means the SSH session opened and the task ran, but the device returned an error — here `% Invalid input` for `configure terminal`, typed at the `lab-sw1>` user EXEC prompt. A connection or login problem would be reported as **unreachable**. A device that already had the lines would report ok with changed=0, not failed. A YAML error stops the run before any device is contacted, but lab-r1 was changed (changed=1).

### Q11 · Multiple choice
<sub>Source: 26.5, 26.7</sub>

The engineer finds that user ansible on lab-sw1 was created with privilege level 1, and the account must stay at that level. Which change lets the playbook configure lab-sw1?

- [x] Add `ansible_become=yes`, `ansible_become_method=enable` and an `ansible_become_password` to the inventory
- [ ] Replace `cisco.ios.ios_config` with `cisco.ios.ios_command` in the playbook
- [ ] Set `host_key_checking = False` in `ansible.cfg`
- [ ] Run the playbook with `--check --diff`

> **Explanation:** With `ansible_become=yes` and `ansible_become_method=enable`, plus the enable password in `ansible_become_password`, Ansible enters `enable` after it logs in and can then configure the switch. The other fix is to give the user privilege 15. `ios_command` is meant for show commands, not configuration. Host key checking concerns the SSH host key, and the session already opened. `--check --diff` is a dry run, so it changes nothing.

### Q12 · CLI
<sub>Source: 26.6, 26.7</sub>

The team later decides that the account on lab-sw1 must match lab-r1, where user ansible has privilege level 15 and the secret `Ans1ble-Lab-2026`. You are in global configuration mode on lab-sw1. Enter the command that re-creates user ansible with privilege level 15 and that secret.

**Prompt:** `lab-sw1(config)#`

**Accepted:** `username ansible privilege 15 secret Ans1ble-Lab-2026` · `username ansible privilege 15 secret 0 Ans1ble-Lab-2026`

> **Explanation:** Ansible logs in over SSH with this local user, and a privilege-15 user starts in privileged EXEC mode, so `ios_config` can enter configuration mode. As in the Lab 26.1 device preparation, `privilege 15` comes before `secret`. On the next run of `logging.yml`, lab-sw1 reports changed=1, and lab-r1 reports changed=0 because it already has the lines.
