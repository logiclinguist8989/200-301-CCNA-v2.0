## Questions

### Q1 · Drag and drop — order
<sub>Source: 25.2</sub>

R1 is configured with `service sequence-numbers` and `service timestamps log datetime msec`. Drag the parts of an IOS syslog message into the order in which they appear in each message.

1. Sequence number
2. Timestamp
3. Facility
4. Severity
5. Mnemonic
6. Description

> **Explanation:** Every IOS message follows the pattern `seq-no: timestamp: %FACILITY-SEVERITY-MNEMONIC: description`, for example `000234: Oct 15 2026 10:03:05.117 UTC: %SYS-5-CONFIG_I: Configured from console by netadmin on vty0 (10.10.99.21)`. The part between `%` and the second colon (here `SYS-5-CONFIG_I`) is what you search for in documentation and filters.

### Q2 · Multiple choice
<sub>Source: 25.2, 25.3, 25.5</sub>

Refer to the exhibit.

```
SW1# show logging | include MACFLAP
000087: Oct 16 2026 11:42:19.604 UTC: %SW_MATM-4-MACFLAP_NOTIF: Host 0060.2f11.0001 in vlan 10 is flapping between port Fa0/1 and port Gi0/1
```

Which statement correctly interprets the message?

- [x] The IOS facility is SW_MATM and the severity is 4 (warnings); SW1 saw the same MAC address on two ports, which points to a possible loop or a host that moved.
- [ ] The facility is local7 and the severity is 4 (warnings); SW1 learned the MAC address in the wrong VLAN.
- [ ] The facility is SW_MATM and the severity is 4, so the event is less serious than an informational (level 6) message.
- [ ] The facility is MACFLAP_NOTIF and the severity is 4 (errors); SW1 has err-disabled Fa0/1.

> **Explanation:** In `%SW_MATM-4-MACFLAP_NOTIF`, SW_MATM is the facility (the IOS component), 4 is the severity (warnings) and MACFLAP_NOTIF is the mnemonic. The host 0060.2f11.0001 in VLAN 10 appears on both Fa0/1 and Gi0/1: a possible loop or a moved host. local7 is the syslog **transport** facility that the device sends to the server, not the facility in the message text. A lower number is **more** severe, so level 4 is more serious than level 6, and severity 4 is warnings, not errors (3). The message does not say any port was disabled.

### Q3 · Multiple choice
<sub>Source: 25.3, 25.4, 25.7</sub>

Refer to the exhibit.

```
R1# show logging
Syslog logging: enabled (0 messages dropped, 0 flushes, 0 overruns)
    Console logging: level debugging, 58 messages logged
    Monitor logging: level debugging, 0 messages logged
    Buffer logging:  level informational, 58 messages logged
    Trap logging: level errors, 14 message lines logged
        Logging to 10.10.99.40  (udp port 514, link up),
              14 message lines logged
```

The syslog server at 10.10.99.40 receives `%LINK-3-UPDOWN` messages from R1, but never `%LINEPROTO-5-UPDOWN` or `%SYS-5-CONFIG_I` messages. What should the engineer do?

- [x] Configure `logging trap informational` so that the server receives levels 0 to 6
- [ ] Permit UDP 514 from R1 to 10.10.99.40 on the firewalls and ACLs in the path
- [ ] Configure `logging buffered notifications`
- [ ] Enter `terminal monitor` on R1

> **Explanation:** **Trap logging** is the syslog-server destination, and `level errors` sends only levels 0–3. LINK-3 is level 3, so it arrives; LINEPROTO-5 and SYS-5 are level 5 (notifications), so they are filtered out. Raising the trap level to `notifications` or `informational` (the default, 0–6) fixes it. The path itself works: some messages arrive and the output shows UDP port 514 with the link up. The buffer and `terminal monitor` only change what is kept or shown locally on R1.

### Q4 · CLI
<sub>Source: 25.2</sub>

The syslog server at 10.10.99.40 sorts incoming messages into files by their syslog facility code. Every router and switch still uses the Cisco default facility, so all messages land in the same file. The server team asks that R1 send its messages with the facility local5. Enter the command on R1.

**Prompt:** `R1(config)#`

**Accepted:** `logging facility local5`

> **Explanation:** Besides the IOS facility in the message text (LINK, SYS, OSPF …), every syslog message carries a numeric facility code that the server uses to sort it. Network devices normally use local0–local7, and Cisco devices send **local7** by default. `logging facility local5` changes only that transport facility; a message such as `%LINK-3-UPDOWN` still shows LINK as its IOS facility.

### Q5 · CLI
<sub>Source: 25.4, 25.7</sub>

R1's log messages begin with the time since boot, such as `1d02h:`, so they cannot be matched against other devices' logs. NTP is already configured. Enter the global configuration command that stamps log messages with the date and time to the millisecond, with no further options.

**Prompt:** `R1(config)#`

**Accepted:** `service timestamps log datetime msec`

> **Explanation:** A time since boot (`1d02h:`) means `datetime` is not configured; `service timestamps log datetime msec` adds the date and time with milliseconds (the options `localtime show-timezone` can be added). Timestamps are only useful for correlation when the clocks agree, which is why every device should be synchronised with NTP. A `*` in front of the time means the clock is not synchronised.

### Q6 · Drag and drop — match
<sub>Source: 25.4, 25.7</sub>

Drag the command that fixes each logging problem on R1. Not every command is used.

| Symptom | Fix |
| --- | --- |
| An engineer connected to R1 by SSH sees no log messages, although `logging monitor` is at its default level | terminal monitor |
| During an event storm, the console is flooded with level 5, 6 and 7 messages | logging console warnings |
| A log message breaks into a command being typed on the console, and the engineer can no longer see what they had typed | logging synchronous |
| The syslog server cannot tell which device sent R1's messages, because they arrive from different source addresses | logging source-interface GigabitEthernet0/0/0 |
| The syslog server receives nothing from R1, and `show logging` shows no "Logging to" line under Trap logging | logging host 10.10.99.40 |

**Extra targets:** logging facility local5 · clear logging

> **Explanation:** VTY sessions only show messages after `terminal monitor`, entered in each session (`logging monitor` defaults to debugging). `logging console warnings` limits the console to levels 0–4, and `logging synchronous` under `line console 0` reprints the command you were typing after a message interrupts it. `logging source-interface` fixes the source address the server sees, so it can identify the device. Without `logging host` there is no syslog-server destination at all. `logging facility local5` only changes how the server sorts messages, and `clear logging` empties the local buffer.

### Q7 · Multiple choice — choose two
<sub>Source: 25.6</sub>

Which two statements about SNMP versions and notifications are true? (Choose two.)

- [x] An inform is acknowledged by the manager and resent until it is confirmed, whereas a trap is not acknowledged.
- [x] With the authPriv security level, SNMPv3 both authenticates messages (for example with SHA) and encrypts them (for example with AES).
- [ ] SNMPv2c is safe to use across untrusted networks because every request must carry the community string.
- [ ] With the authNoPriv security level, SNMPv3 encrypts messages but does not authenticate them.
- [ ] GetBulk and Inform were first introduced in SNMPv3.

> **Explanation:** Traps and informs are both agent-to-manager notifications; only the inform is acknowledged and resent until confirmed. SNMPv3 offers noAuthNoPriv (username only), authNoPriv (authentication, no encryption) and authPriv (authentication and encryption) — authPriv is the secure choice. The SNMPv1 and v2c community string travels in clear text, so needing one does not make v2c secure. GetBulk and Inform were added in SNMPv2c and remain in v3.

### Q8 · Drag and drop — match
<sub>Source: 25.6</sub>

Drag the SNMP term to the description it matches. Not every term is used.

| Description | Term |
| --- | --- |
| Software on R1 that answers requests from the NMS and sends notifications | Agent |
| The structured collection of values R1 exposes, such as its host name, interface counters and CPU load | MIB |
| The numeric address of one value, such as 1.3.6.1.2.1.1.5.0 for sysName | OID |
| A request that reads the next value in the tree, sent repeatedly to walk a table | GetNext |
| A request that changes a value, and fails when the community is read-only | Set |
| An event notification that R1 resends until the NMS confirms it | Inform |

**Extra targets:** Trap · Manager

> **Explanation:** The **manager** (the NMS) polls the **agent** on each device. The agent exposes its values as a **MIB**, and each value has an **OID** such as `1.3.6.1.2.1.1.5.0` (sysName). **GetNext** reads the next value in the tree and is used to walk tables; **Set** changes a value and needs write access. Both traps and informs are notifications, but only an **inform** is acknowledged and resent until confirmed — a trap is sent once and never acknowledged.

### Q9 · Multiple choice
<sub>Source: 25.6, 25.7</sub>

The NMS at 10.10.99.40 polls R1 with SNMPv2c without any problem, but it never receives traps from R1. `show snmp host` lists 10.10.99.40 as a trap receiver, and `snmp-server enable traps` is configured. A firewall sits between R1 and the NMS. Which traffic must the firewall permit?

- [x] UDP 162 from R1 to 10.10.99.40
- [ ] UDP 161 from 10.10.99.40 to R1
- [ ] UDP 514 from R1 to 10.10.99.40
- [ ] UDP 161 from R1 to 10.10.99.40

> **Explanation:** Get, GetNext, GetBulk and Set requests go to the agent on **UDP 161** — that already works, because polling succeeds. Traps and informs go from the agent to the manager on **UDP 162**, so a blocked UDP 162 explains why no traps arrive when `snmp-server host` and `snmp-server enable traps` are both in place. UDP 514 is syslog, not SNMP.

## Testlet A · A port goes down on SW1

Refer to the scenario. The user of PC2 reports that their network connection has stopped working. PC2 is connected to SW1 Fa0/2, a port protected by port security. SW1 uses `service timestamps log datetime msec` and `service sequence-numbers`, buffers messages at the informational level and sends messages to the syslog server 10.10.99.40. An engineer connects to SW1 by SSH and displays the log buffer.

```
SW1# show logging | begin Log Buffer
Log Buffer (16384 bytes):

000118: Oct 16 2026 09:14:02.517 UTC: %PORT_SECURITY-2-PSECURE_VIOLATION: Security violation occurred, caused by MAC address 0060.2f11.00a7 on port FastEthernet0/2.
000119: Oct 16 2026 09:14:02.521 UTC: %PM-4-ERR_DISABLE: psecure-violation error detected on Fa0/2, putting Fa0/2 in err-disable state
000120: Oct 16 2026 09:14:03.524 UTC: %LINK-3-UPDOWN: Interface FastEthernet0/2, changed state to down
000121: Oct 16 2026 09:14:04.526 UTC: %LINEPROTO-5-UPDOWN: Line protocol on Interface FastEthernet0/2, changed state to down
000122: Oct 16 2026 09:16:45.880 UTC: %SEC_LOGIN-4-LOGIN_FAILED: Login failed [user: admin] [Source: 10.10.30.12] [localport: 22] [Reason: Login Authentication Failed]
000123: Oct 16 2026 09:18:10.006 UTC: %SYS-5-CONFIG_I: Configured from console by netadmin on vty0 (10.10.99.21)
```

### Q10 · Multiple choice
<sub>Source: 25.5</sub>

What caused Fa0/2 to go down?

- [x] A device whose MAC address port security does not allow sent traffic on Fa0/2, so the port was err-disabled.
- [ ] BPDU guard disabled Fa0/2 after another switch was connected to it.
- [ ] The cable to PC2 failed, and port security then reported the loss of PC2's MAC address.
- [ ] The user netadmin shut down Fa0/2 from a VTY session.

> **Explanation:** Messages close together tell one story, and the first event is the cause: `%PORT_SECURITY-2-PSECURE_VIOLATION` (an unknown MAC address on a secured port) and `%PM-4-ERR_DISABLE` (the port is err-disabled) come first; the LINK-3 and LINEPROTO-5 down messages are their consequences. A cable fault would put the LINK-3 message first. BPDU guard would log `%SPANTREE-2-BLOCK_BPDUGUARD`, and netadmin's configuration session ended at 09:18, four minutes after the port went down. The fix is to remove the unknown device, then `shutdown` and `no shutdown` the port.

### Q11 · Multiple choice
<sub>Source: 25.3, 25.4</sub>

From this excerpt, the syslog server at 10.10.99.40 received only messages 000118, 000119, 000120 and 000122. Which command is configured on SW1?

- [x] `logging trap warnings`
- [ ] `logging trap errors`
- [ ] `logging trap notifications`
- [ ] `logging trap critical`

> **Explanation:** The messages that arrived have severities 2 (PORT_SECURITY), 4 (PM), 3 (LINK) and 4 (SEC_LOGIN); the two that did not arrive, 000121 (LINEPROTO) and 000123 (SYS), are level 5. A level sends itself and every more severe level, so `warnings` (0–4) matches. `errors` (0–3) would drop both level 4 messages, `critical` (0–2) would send only 000118, and `notifications` (0–5) would send all six.

### Q12 · Multiple choice — choose two
<sub>Source: 25.5</sub>

Which two conclusions can the engineer draw from messages 000122 and 000123? (Choose two.)

- [x] Someone tried to log in to SW1 over SSH as admin from 10.10.30.12, a host in the wireless VLAN, and the login failed.
- [x] The user netadmin, connected on a VTY line from 10.10.99.21, entered and then left configuration mode on SW1.
- [ ] The user netadmin made the change from SW1's physical console port, as the words "from console" show.
- [ ] The user admin logged in from 10.10.30.12 and then changed SW1's configuration.
- [ ] The failed login is a more serious event than the port-security violation, because its severity number is higher.

> **Explanation:** `%SEC_LOGIN-4-LOGIN_FAILED` records a failed login with the user name (admin), the source (10.10.30.12, VLAN 30 Wireless) and local port 22 (SSH) — possible password guessing that is worth investigating. `%SYS-5-CONFIG_I` is logged when someone leaves configuration mode and shows who (netadmin), how (vty0, a remote session) and from where (10.10.99.21); "from console" does not mean the console port here. The admin login failed, so admin made no change. A **lower** severity number is more serious: the port-security violation (2) outranks the failed login (4).
