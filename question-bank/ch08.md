## Questions

### Q1 · Multiple choice
<sub>Source: 8.3, 8.7</sub>

Refer to the exhibit.

```
SW1# show cdp neighbors
Capability Codes: R - Router, T - Trans Bridge, B - Source Route Bridge
                  S - Switch, H - Host, I - IGMP, r - Repeater, P - Phone,
                  D - Remote, C - CVTA, M - Two-port Mac Relay

Device ID        Local Intrfce     Holdtme    Capability  Platform   Port ID
DSW1             Gig 0/1           164           R S I    WS-C3650-  Gig 1/0/1
DSW1             Gig 0/2           164           R S I    WS-C3650-  Gig 1/0/3
```

SW1's two uplinks are the member ports of EtherChannel Po1. An engineer is updating the port-to-port connection table. Which entry is correct?

- [ ] SW1 Gi1/0/3 connects to DSW1 Gi0/2
- [x] SW1 Gi0/2 connects to DSW1 Gi1/0/3
- [ ] SW1 Gi0/1 connects to DSW1 Gi1/0/3
- [ ] DSW1 Gi0/1 connects to SW1 Gi1/0/1

> **Explanation:** **Local Intrfce** is the port on the device where you typed the command (SW1); **Port ID** is the neighbor's port at the other end of the cable. The second line therefore reads: SW1 Gi0/2 connects to DSW1 Gi1/0/3. Reversing the two columns (SW1 Gi1/0/3 to DSW1 Gi0/2, or DSW1 Gi0/1 to SW1 Gi1/0/1) is the classic mistake, and pairing SW1 Gi0/1 with DSW1 Gi1/0/3 mixes up the two lines. CDP runs on physical links, not on the port-channel, so each EtherChannel member has its own line — two lines for Po1 are normal, and the table should record both members and the port-channel number.

### Q2 · Multiple choice — choose two
<sub>Source: 8.2, 8.4</sub>

Which two statements about LLDP are true? (Choose two.)

- [x] It is defined in IEEE 802.1AB, so it can discover neighbors from other vendors.
- [x] Chassis ID, port ID and time-to-live are mandatory TLVs.
- [ ] Like CDP, it is enabled on every Cisco IOS interface by default.
- [ ] By default it sends an advertisement every 60 seconds, and neighbors keep the entry for 180 seconds.
- [ ] Each interface also needs `lldp transmit` and `lldp receive` after `lldp run`.

> **Explanation:** LLDP is the vendor-neutral IEEE 802.1AB protocol, and it carries its information in TLVs: chassis ID, port ID and time-to-live are mandatory, while system name, description, capabilities and management address are optional. On many Cisco IOS devices LLDP is off by default and must be turned on with `lldp run`; CDP is the one that is on by default. LLDP's defaults are a 30-second timer and a 120-second holdtime — 60 and 180 seconds are CDP's values. Once LLDP runs, every interface both transmits and receives unless you disable a direction with `no lldp transmit` or `no lldp receive`.

### Q3 · Drag and drop — match
<sub>Source: 8.3, 8.4, 8.6</sub>

An engineer is auditing SW2 and the devices around it. Drag each command to the information it gives.

| Command | Information |
| --- | --- |
| `show cdp neighbors` | One line per neighbor connection (local interface), with platform and port ID |
| `show cdp entry DSW1` | One neighbor's management IP address, software version, native VLAN and duplex |
| `show cdp interface` | Which interfaces run CDP |
| `show lldp interface` | Whether each interface transmits and receives LLDP |
| `show mac address-table interface fastethernet0/2` | The MAC address of the printer on a port, although the printer runs neither CDP nor LLDP |

**Extra targets:** Neighbors two or more hops away

> **Explanation:** The summary `show cdp neighbors` gives one line per neighbor link, so each EtherChannel member appears separately; the `detail` form, or `show cdp entry <name>`, adds the management address, full platform, software version, native VLAN and duplex. `show cdp interface` and `show lldp interface` show where each protocol runs (for LLDP, per direction). Printers and PCs usually run neither protocol, so the MAC address table, together with the ARP or DHCP tables, is the evidence for them. No command lists devices two hops away, because CDP and LLDP advertisements are never forwarded — you log in to the next device and continue hop by hop.

### Q4 · Multiple choice
<sub>Source: 8.3, 8.6</sub>

Refer to the exhibit.

```
DSW1# show cdp neighbors detail
...
-------------------------
Device ID: SW2
Entry address(es):
  IP address: 10.10.99.12
Platform: cisco WS-C2960-24TT-L,  Capabilities: Switch IGMP
Interface: GigabitEthernet1/0/2,  Port ID (outgoing port): GigabitEthernet0/1
Holdtime : 157 sec

Version :
Cisco IOS Software, C2960 Software ...

advertisement version: 2
Native VLAN: 999
Duplex: full
...
```

The documentation for this link reads: *DSW1 Gi1/0/2 to SW2 Gi0/1 · WS-C2960-24TT-L · management 10.10.99.12 · trunk native VLAN 1.* The network works and follows the campus design. Which documented value must be corrected?

- [ ] The neighbor port, because SW2's end of the link is Gi1/0/2
- [ ] The management address, because the entry address shown is DSW1's own address
- [x] The native VLAN, which is 999 on this trunk
- [ ] The platform, because SW2 is a WS-C3650

> **Explanation:** CDPv2 (the default) advertises the native VLAN and duplex, and the `detail` view or `show cdp entry` displays them together with the neighbor's management address and full platform. Here SW2's port (Gi0/1), model (WS-C2960-24TT-L, not a WS-C3650) and address 10.10.99.12 all match the record; only the native VLAN differs. The campus design uses native VLAN 999 on its trunks and the network works, so the **documentation** is what you correct. The entry address belongs to the neighbor, not to DSW1, and `Interface` is DSW1's port while `Port ID` is SW2's.

### Q5 · Multiple choice
<sub>Source: 8.4, 8.8</sub>

LLDP has been enabled with `lldp run` on DSW1 and R1 only. R1's `show lldp neighbors` output is empty. Refer to the exhibit.

```
DSW1# show lldp neighbors
Capability codes:
    (R) Router, (B) Bridge, (T) Telephone, (C) DOCSIS Cable Device
    (W) WLAN Access Point, (P) Repeater, (S) Station, (O) Other

Device ID           Local Intf     Hold-time  Capability      Port ID
R1                  Gi1/0/24       120        R               Gi0/0/0

Total entries displayed: 1

DSW1# show lldp interface gigabitethernet1/0/24

GigabitEthernet1/0/24:
    Tx: disabled
    Rx: enabled
    Tx state: IDLE
    Rx state: WAIT FOR FRAME
```

What is the cause?

- [x] DSW1 Gi1/0/24 is configured with `no lldp transmit`, so R1 never receives an advertisement from DSW1.
- [ ] DSW1 Gi1/0/24 is configured with `no lldp receive`, so DSW1 ignores R1's advertisements.
- [ ] LLDP is still disabled globally on R1.
- [ ] R1 G0/0/0 also needs `lldp receive` before it stores LLDP neighbors.

> **Explanation:** DSW1 lists R1, so R1 is sending and DSW1 is receiving (`Rx: enabled`). `Tx: disabled` shows that DSW1 Gi1/0/24 has `no lldp transmit`, so nothing reaches R1 — the neighbor appears only one way. LLDP needs to transmit on one end and receive on the other. If LLDP were off on R1, DSW1 would have no entry for R1. Once `lldp run` is entered, each interface transmits and receives by default, so R1 needs no per-interface command. The fix is `lldp transmit` on DSW1 Gi1/0/24.

### Q6 · Drag and drop — order
<sub>Source: 8.6</sub>

Drag the steps for validating network documentation with CDP and LLDP into the correct order.

1. Collect the topology drawing, port-to-port connection table, IP addressing plan and device inventory
2. Gather `show cdp neighbors detail` or `show lldp neighbors detail`, plus `show interfaces description` and `status`, on every switch and router
3. Compare neighbor hostname, local port, remote port, model and management IP for every link
4. For each mismatch, decide whether the documentation or the network breaks the approved design, and correct that side
5. Verify PCs and printers, which run neither protocol, with the MAC address, ARP and DHCP tables
6. Publish the corrected documentation with the date and the name of who verified it

> **Explanation:** You cannot compare until you have both the documentation and the evidence, and you decide what to correct only after comparing field by field. Hosts that do not run CDP or LLDP are invisible to the neighbor output, so they are checked separately with the MAC address, ARP and DHCP tables before publishing. If the network is what you changed (through change control), gather the evidence again to re-check it. Publishing with a date and the verifier's name — and updating interface `description`s — makes the next audit faster.

### Q7 · Drag and drop — match
<sub>Source: 8.2, 8.8</sub>

Drag the most likely cause to each symptom seen during a documentation audit.

| Symptom | Likely cause |
| --- | --- |
| `show lldp neighbors` on DSW1 has no entries, although all its links are up and CDP lists every neighbor | LLDP is not enabled with `lldp run` on one or both ends |
| A switch that was unplugged from DSW1 a minute ago is still listed in `show cdp neighbors` | The entry has not reached the end of its holdtime |
| R1's `show cdp neighbors` does not list SW1, which is cabled to DSW1 | Advertisements are never forwarded beyond a directly connected neighbor |
| Printer1 never appears in SW2's CDP or LLDP neighbor table | The device does not run CDP or LLDP |
| DSW1 logs `%CDP-4-NATIVE_VLAN_MISMATCH` for Gi1/0/2 | The two ends of the trunk use different native VLANs |

**Extra targets:** CDP runs on the port-channel, not on its members

> **Explanation:** LLDP is often off by default on Cisco IOS, so an empty LLDP table next to a full CDP table points to a missing `lldp run`. Old entries remain until the holdtime expires (180 s for CDP, 120 s for LLDP), or until `clear cdp table` / `clear lldp table`. Each device learns only its direct neighbors, so you follow the network hop by hop, and printers and PCs are verified with the MAC address table. A native VLAN mismatch is a configuration fault on the trunk that CDP reports. The extra target is false: CDP runs on physical links, so each EtherChannel member is listed separately.

### Q8 · Multiple choice
<sub>Source: 8.6, 8.7</sub>

During an audit, DSW1's CDP output shows that one access switch uplink lands on a different DSW1 port from the one in the company's approved cabling plan. The link works. The cabling plan is the approved standard that every site must follow. What should the engineer do?

- [ ] Update the connection table to match the CDP output, because the link is working
- [x] Move the cable to the port in the approved plan through change control, then gather the neighbor output again to confirm
- [ ] Enter `clear cdp table` and check whether the entry moves to the documented port
- [ ] Update the cabling plan for this site only and record the exception

> **Explanation:** A mismatch does not automatically mean that either side is wrong. If the network works and follows the design standard, the documentation is wrong and you update it. When the documented design is the approved standard — as with this cabling plan — the **network** is wrong: fix it through change control, then re-check from the evidence-gathering step. A working link alone does not make the network right, and an exception for one site breaks a plan that every site must follow. `clear cdp table` only removes stale entries; the cable is still where CDP says it is.

### Q9 · Multiple choice — choose two
<sub>Source: 8.5</sub>

A security review asks the network team where CDP and LLDP should stay enabled. On which two interfaces should the protocols stay enabled? (Choose two.)

- [x] DSW1 Gi1/0/21, a member of the Po3 bundle to DSW2
- [x] SW4 Gi1/0/2, where a Cisco IP phone learns voice VLAN 20
- [ ] An edge router interface that connects to the Internet service provider
- [ ] A switch port in the visitor area that guests can plug a laptop into

> **Explanation:** CDP and LLDP advertisements reveal hostnames, models, software versions and management IP addresses, which helps an attacker plan an exploit. Best practice is to disable them on ports facing untrusted networks — the Internet edge, ISP links and guest-facing ports — and to keep them on infrastructure links and on IP phone ports, where the phone learns its voice VLAN through CDP or LLDP-MED.

### Q10 · Multiple choice
<sub>Source: 8.3, 8.5</sub>

Based on the exhibit, on which R1 interface must CDP and LLDP advertisements be stopped?

- [x] G0/0/1, the local interface on the ISP line
- [ ] G0/0/0, the port ID on the ISP line
- [ ] G0/0/0, the local interface on the DSW1 line
- [ ] Gi1/0/24, the port ID on the DSW1 line

> **Explanation:** **Local Intrfce** is R1's own port and **Port ID** is the neighbor's port. The ISP line therefore reads: R1 G0/0/1 connects to the ISP router's G0/0/0, so G0/0/1 is the port that faces the untrusted network. Taking the ISP's port ID instead is the classic column swap; R1 G0/0/0 is the link to DSW1, where both protocols must keep running, and Gi1/0/24 is a port on DSW1, not on R1.

### Q11 · CLI
<sub>Source: 8.3, 8.5</sub>

You are in interface configuration mode for the R1 interface that faces the ISP. Enter the command that disables CDP on this interface only.

**Prompt:** `R1(config-if)#`

**Accepted:** `no cdp enable`

> **Explanation:** `no cdp enable` stops CDP on G0/0/1 while G0/0/0 keeps exchanging advertisements with DSW1. The global command `no cdp run` would not meet the requirement, because it disables CDP on the whole device, including the link to DSW1. The ISP's router keeps its entry for R1 until the holdtime expires — 180 seconds by default — and then drops it. `cdp enable` would restore CDP on the interface.

### Q12 · CLI
<sub>Source: 8.4, 8.5</sub>

You are still in interface configuration mode for the R1 interface that faces the ISP. Enter the command that stops R1 from sending LLDP advertisements out of this interface.

**Prompt:** `R1(config-if)#`

**Accepted:** `no lldp transmit`

> **Explanation:** LLDP is controlled per direction on each interface. `no lldp transmit` stops R1 from advertising its details to the ISP; `no lldp receive` would only stop R1 from listening, so it would keep advertising. `no lldp run` would disable LLDP on the whole router, including the link to DSW1.
