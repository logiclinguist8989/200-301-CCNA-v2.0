# Chapter 23 — Layer 2 security features

CCNA-style practice questions for [Chapter 23](../CCNA%20200-301%20v2.0%20Study%20Guide.md#chapter-23--layer-2-security-features) · Domain 4 · Objectives 4.7 and 4.7.a–e. The format is described in the [question bank README](README.md).

## Questions

### Q1 · Drag and drop — match
<sub>Source: 23.2</sub>

Drag each access-layer attack to the Layer 2 security feature that stops it. Not every feature is used.

| Attack | Feature |
| --- | --- |
| A laptop hands out DHCP leases that name itself as the default gateway | DHCP snooping |
| An attacker sends ARP replies that claim 10.10.10.1 with the attacker's own MAC address | Dynamic ARP inspection |
| A faulty NIC floods VLAN 10 with broadcasts | Storm control |
| A PC sends IPv6 router advertisements and becomes the IPv6 default gateway for the VLAN | RA guard |
| A tool sends frames with thousands of fake source MAC addresses to fill the MAC address table | Port security |

**Extra targets:** BPDU guard · Root guard

> **Explanation:** DHCP snooping drops server messages (OFFER, ACK, NAK) that arrive on untrusted ports, so a rogue DHCP server cannot hand out leases. Dynamic ARP inspection drops ARP messages whose sender IP and MAC do not match a binding, which stops ARP spoofing of the gateway. Storm control limits broadcast, multicast or unknown-unicast traffic arriving on a port. RA guard drops router advertisements on ports where no router should be. Port security limits which and how many MAC addresses may send into a port, which stops MAC flooding. BPDU guard and root guard are STP protection features (Chapter 9); they react to BPDUs, which none of these attacks needs to send.

### Q2 · Multiple choice
<sub>Source: 23.3, 23.8</sub>

An engineer enables DHCP snooping on SW1 with `ip dhcp snooping` and `ip dhcp snooping vlan 10,30`, and configures `ip dhcp snooping trust` on the uplinks Gi0/1 and Gi0/2 to DSW1 and DSW2. DSW1 and DSW2 relay DHCP requests to R1, the DHCP server. Immediately afterwards, no client on SW1 receives an address. Which change on SW1 is most likely to fix the problem?

- [x] Enter `no ip dhcp snooping information option` so that SW1 stops inserting option 82 into client requests
- [ ] Enter `ip dhcp snooping trust` on the access ports so that the clients' DISCOVER messages are accepted
- [ ] Enter `ip arp inspection trust` on Gi0/1 and Gi0/2 so that the replies from R1 are accepted
- [ ] Enter `ip dhcp snooping limit rate 15` on Gi0/1 and Gi0/2 so that the uplinks are protected against starvation

> **Explanation:** The uplinks are already trusted, so the next suspect is option 82. By default a snooping switch inserts option 82 into client requests while leaving the relay address (giaddr) empty. A Cisco relay that receives such a packet on an interface that does not trust relay information drops it, so the clients get no address. Because SW1 is not the relay itself (DSW1 and DSW2 relay to R1), the fix is `no ip dhcp snooping information option`, or configuring the relay to trust the option. Access ports never need to be trusted: untrusted ports already accept client messages, and trusting them would let a rogue server work. Dynamic ARP inspection checks ARP, not DHCP, and a rate limit belongs on untrusted access ports, not on the uplinks.

### Q3 · Multiple choice — choose two
<sub>Source: 23.4</sub>

Which two statements about dynamic ARP inspection (DAI) are true? (Choose two.)

- [x] It checks the sender IP and MAC addresses in ARP messages that arrive on untrusted ports against the DHCP snooping binding table or an ARP ACL.
- [x] By default, an untrusted port that receives more than 15 ARP packets per second is err-disabled.
- [ ] It inspects ARP messages on trusted ports and forwards ARP messages from untrusted ports without checking them.
- [ ] It builds its own binding table from the ARP replies it sees, so DHCP snooping is not needed.
- [ ] Hosts with static IP addresses pass inspection automatically because they do not use DHCP.

> **Explanation:** DAI inspects ARP on **untrusted** ports and drops (and logs) any message whose sender IP and MAC do not match a DHCP snooping binding for that port and VLAN, or an ARP ACL. Untrusted ports are rate-limited to 15 ARP packets per second by default, and exceeding the limit err-disables the port. DAI depends on DHCP snooping for its bindings; it does not learn them itself. Statically addressed hosts such as printers have **no** binding, so their ARP is dropped unless an ARP ACL permits them.

### Q4 · Multiple choice
<sub>Source: 23.5</sub>

Refer to the exhibit.

```
SW1# show running-config interface FastEthernet0/8
Building configuration...

Current configuration : 124 bytes
!
interface FastEthernet0/8
 switchport access vlan 10
 switchport mode access
 storm-control broadcast level 1.00 0.50
end

SW1# show storm-control FastEthernet0/8 broadcast
Interface  Filter State   Upper        Lower        Current
---------  -------------  -----------  -----------  ----------
Fa0/8      Blocking         1.00%        0.50%        23.71%
```

No other storm-control commands are configured on SW1. What is SW1 doing with the traffic that arrives on Fa0/8?

- [x] It drops the excess broadcast traffic until the broadcast level falls below 0.50 % of the port's bandwidth; the port stays up.
- [ ] It has err-disabled Fa0/8, which stays down until an engineer enters `shutdown` and `no shutdown`.
- [ ] It forwards all broadcasts and sends an SNMP trap, because no storm-control action is configured.
- [ ] It drops all traffic on Fa0/8, including unicast, until the broadcast level falls below 1.00 %.

> **Explanation:** Broadcasts (23.71 %) are above the 1.00 % rising threshold, so the filter state is *Blocking*: a storm was detected and the excess is dropped. With no `storm-control action` command, the default action is to drop the excess traffic **of that type** until it falls below the threshold — here the optional falling threshold of 0.50 %. The port would be err-disabled (state *Shutdown*) only with `storm-control action shutdown`, and a trap is sent only with `storm-control action trap`. Unicast traffic is not affected by a broadcast threshold.

### Q5 · CLI
<sub>Source: 23.6, 23.8</sub>

Several PCs in VLAN 10 on SW1 show another PC's link-local address as their IPv6 default gateway. Refer to the exhibit.

```
SW1(config)# ipv6 nd raguard policy HOST-PORTS
SW1(config-nd-raguard)# device-role host
SW1(config-nd-raguard)# exit
SW1(config)# interface range FastEthernet0/1 - 24
```

Enter the command that applies the RA guard policy HOST-PORTS to the selected access ports.

**Prompt:** `SW1(config-if-range)#`

**Accepted:** `ipv6 nd raguard attach-policy HOST-PORTS`

> **Explanation:** A PC's link-local address as the hosts' IPv6 gateway is the signature of a rogue router advertisement. `ipv6 nd raguard attach-policy HOST-PORTS` attaches the policy, and `device-role host` blocks all RAs (and ICMPv6 redirects) entering those ports. The uplinks towards the real routers get a policy with `device-role router` (or none), so legitimate RAs still arrive. RA guard matters even where IPv6 is not deployed, because hosts run IPv6 by default. Verify with `show ipv6 nd raguard policy HOST-PORTS`, which lists the policy and the ports it is attached to.

### Q6 · Multiple choice
<sub>Source: 23.7</sub>

An engineer configures SW1 Fa0/3 with only these commands:

```
interface FastEthernet0/3
 switchport mode access
 switchport access vlan 10
 switchport port-security
```

Later, a user puts a small unmanaged switch between Fa0/3 and their PC and connects a second PC to it. Both PCs send traffic. What happens?

- [x] Fa0/3 is err-disabled, because the default maximum is one MAC address and the default violation mode is shutdown.
- [ ] Both PCs work, because port security does not limit the number of addresses until a maximum is configured.
- [ ] Frames from the second PC are dropped silently and the first PC keeps working, because protect is the default violation mode.
- [ ] Frames from the second PC are dropped and logged while the port stays up, because restrict is the default violation mode.

> **Explanation:** Once `switchport port-security` is enabled, the defaults are a maximum of **1** address, violation mode **shutdown**, no sticky learning and no aging. The second source MAC is a violation, so the port is err-disabled and both PCs lose connectivity. To recover, remove the extra device and enter `shutdown` and `no shutdown`, or configure `errdisable recovery cause psecure-violation` for automatic recovery. Protect and restrict keep the port up, but only when they are configured.

### Q7 · Multiple choice
<sub>Source: 23.7, 23.8</sub>

Refer to the exhibit. Fa0/5 serves one authorised Staff PC, whose MAC address was learned as a sticky address.

```
%PORT_SECURITY-2-PSECURE_VIOLATION: Security violation occurred, caused by MAC address 0090.21aa.0012 on port FastEthernet0/5.

SW1# show port-security interface FastEthernet0/5
Port Security              : Enabled
Port Status                : Secure-up
Violation Mode             : Restrict
Aging Time                 : 0 mins
Aging Type                 : Absolute
SecureStatic Address Aging : Disabled
Maximum MAC Addresses      : 1
Total MAC Addresses        : 1
Configured MAC Addresses   : 0
Sticky MAC Addresses       : 1
Last Source Address:Vlan   : 0090.21aa.0012:10
Security Violation Count   : 37
```

Which statement describes the current situation?

- [x] Frames from 0090.21aa.0012 are dropped and each violation is logged and counted, while the authorised PC keeps working.
- [ ] Fa0/5 is err-disabled and must be recovered with `shutdown` and `no shutdown`.
- [ ] Frames from 0090.21aa.0012 are dropped silently, without log messages or counter increments.
- [ ] 0090.21aa.0012 has been added as a second sticky address, because the port uses sticky learning.

> **Explanation:** In **restrict** mode, frames from the extra MAC address are dropped, a log/SNMP message is sent and the violation counter increments (37 here), but the port stays up — *Secure-up* — so the authorised PC keeps working. An err-disabled port would show *Secure-shutdown*. Silent drops with no log and no count describe **protect** mode. The maximum is 1 and the one allowed address is already learned (Total 1, Sticky 1), so no further address can be learned, sticky or not.

### Q8 · CLI
<sub>Source: 23.7, 23.8</sub>

Refer to the exhibit. Fa0/7 connects a Staff PC.

```
SW1(config)# interface FastEthernet0/7
SW1(config-if)# switchport port-security
Command rejected: FastEthernet0/7 is a dynamic port.
```

Enter the command that must be configured on Fa0/7 before port security can be enabled.

**Prompt:** `SW1(config-if)#`

**Accepted:** `switchport mode access`

> **Explanation:** Port security works only on a **static** access (or trunk) port; on a dynamic (DTP) port the command is rejected. A port for a single PC should be a static access port, so enter `switchport mode access`, then `switchport port-security` again, followed by settings such as `switchport port-security maximum` and `switchport port-security mac-address sticky`.

### Q9 · Drag and drop — match
<sub>Source: 23.8</sub>

Each symptom appeared after Layer 2 security features were enabled on an access switch. Drag each symptom to the change that fixes it.

| Symptom | Fix |
| --- | --- |
| Printer1, which has the static address 10.10.40.11, stops responding after DAI is enabled for VLAN 40 | Create an ARP ACL and apply it with `ip arp inspection filter` |
| Every host in VLAN 10 loses its default gateway after DAI is enabled | `ip arp inspection trust` on the uplinks |
| A rogue DHCP server in VLAN 30 still hands out leases although `ip dhcp snooping` is enabled globally | `ip dhcp snooping vlan` for the missing VLAN |
| Sticky MAC addresses are gone after the switch reloads | `copy running-config startup-config` |
| Users report slow DHCP and ARP because normal broadcasts are dropped on the access ports | Raise the storm-control threshold |

**Extra targets:** Trust the access ports for DHCP snooping

> **Explanation:** A statically addressed printer has no snooping binding, so DAI drops its ARP until an ARP ACL permits its IP and MAC and is applied with `ip arp inspection filter`. When a whole VLAN loses its gateway, the gateway's ARP is being dropped on untrusted uplinks; trust them with `ip arp inspection trust`. Snooping does nothing until it is enabled globally **and** per VLAN. Sticky addresses are written to the running configuration only, so they are lost unless it is saved. A storm-control level set too low drops normal ARP and DHCP broadcasts. Trusting access ports for DHCP snooping fixes none of these and would let a rogue server work.

### Q10 · Multiple choice
<sub>Source: 23.4, 23.8, 23.10</sub>

What is the cause of PC2's problem?

- [x] DHCP snooping is no longer enabled for VLAN 30, so PC2's new lease created no binding, and DAI, still enabled for VLAN 30, drops PC2's ARP requests.
- [ ] The uplinks are not trusted for DHCP snooping, so R1's OFFER and ACK messages are dropped.
- [ ] The uplinks are not trusted for DAI, so the gateway's ARP replies are dropped.
- [ ] Fa0/2 exceeded the DAI rate limit of 15 ARP packets per second and was err-disabled.

> **Explanation:** `show ip dhcp snooping` lists only VLANs 10 and 40, so VLAN 30 was removed from snooping. PC2 still gets an address, but the switch no longer records a binding for it. DAI still inspects VLAN 30, finds no binding for 000a.4122.3002/10.10.30.11 and drops PC2's ARP requests — the *DHCP Drops* counter and the `DHCP_SNOOPING_DENY` message on Fa0/2 show it. The uplinks are trusted (`yes`) and PC2 received its lease, so OFFERs are not being dropped. Untrusted DAI uplinks would break VLANs 10 and 40 as well, and the drops are logged on PC2's access port. A rate-limit violation would err-disable Fa0/2, not log invalid ARPs while PC2 keeps its link.

### Q11 · CLI
<sub>Source: 23.3, 23.10</sub>

Enter the global configuration command that enables DHCP snooping for VLAN 30 again on SW1.

**Prompt:** `SW1(config)#`

**Accepted:** `ip dhcp snooping vlan 30` · `ip dhcp snooping vlan 10,30,40`

> **Explanation:** Snooping must be enabled globally **and** per VLAN. The global `ip dhcp snooping` is still in place (*Switch DHCP snooping is enabled*), so only the VLAN is missing: `ip dhcp snooping vlan 30` adds it back, and `ip dhcp snooping vlan 10,30,40` gives the same result. Afterwards `show ip dhcp snooping` lists 10,30,40 again.

### Q12 · Multiple choice
<sub>Source: 23.3, 23.8, 23.10</sub>

After the fix, `show ip dhcp snooping` lists VLANs 10,30,40, but PC2 still cannot ping 10.10.30.1 and `show ip dhcp snooping binding` has no entry for 10.10.30.11. What should the engineer do next?

- [x] Have PC2 renew its lease, for example with `ipconfig /release` and `ipconfig /renew`, so that SW1 sees the ACK and creates a binding.
- [ ] Reload SW1 so that it rebuilds the binding table from its configuration.
- [ ] Enter `ip arp inspection vlan 30` again so that DAI learns PC2's address from its ARP requests.
- [ ] Wait for errdisable recovery to bring Fa0/2 back up after 300 seconds.

> **Explanation:** The binding table is built from the DHCP ACKs that the switch lets through. PC2 received its lease while VLAN 30 was not snooped, so no binding exists until PC2 renews. A reload does not help — bindings are not in the configuration and are lost after a reload unless `ip dhcp snooping database` keeps them. DAI never learns bindings itself; it only uses the snooping table and ARP ACLs. Fa0/2 is not err-disabled, so errdisable recovery is irrelevant.
