# Chapter 15 — The troubleshooting toolkit

CCNA-style practice questions for [Chapter 15](../CCNA%20200-301%20v2.0%20Study%20Guide.md#chapter-15--the-troubleshooting-toolkit) · Domain 2 · Objective 2.4. The format is described in the [question bank README](README.md).

## Questions

### Q1 · Drag and drop — order
<sub>Source: 15.2</sub>

Drag the steps of a structured troubleshooting method into the correct order.

1. Define the problem: who is affected, what fails, since when and what changed
2. Gather facts with show commands, logs, ping and traceroute
3. Compare the facts with the baseline documentation and saved configurations
4. Form a hypothesis that explains all of the symptoms
5. Change one thing and record the change
6. Verify the fix from the user's point of view
7. Document the cause and the fix

> **Explanation:** Facts come before changes: define the problem precisely, gather facts before touching the configuration, and compare them with the baseline (documentation, saved configurations, how it worked yesterday). Only then form a hypothesis, and it must explain **all** the symptoms. Change one thing at a time and record it, verify from the user's point of view (and undo the change if it did not help), and finally document the cause and the fix. Random changes create new faults and hide the original one.

### Q2 · Multiple choice — choose two
<sub>Source: 15.4, 15.9, 15.10</sub>

Refer to the exhibit. A user reports that the network port in the meeting room, SW1 Fa0/3, stopped working.

```
SW1# show logging
Syslog logging: enabled (0 messages dropped, 0 flushes, 0 overruns)
    Console logging: level debugging, 96 messages logged
    Buffer logging:  level informational, 87 messages logged
Log Buffer (16384 bytes):
*Mar  1 02:14:07.311: %SPANTREE-2-BLOCK_BPDUGUARD: Received BPDU on port Fa0/3 with BPDU Guard enabled. Disabling port.
*Mar  1 02:14:07.315: %PM-4-ERR_DISABLE: bpduguard error detected on Fa0/3, putting Fa0/3 in err-disable state
*Mar  1 02:14:08.319: %LINEPROTO-5-UPDOWN: Line protocol on Interface FastEthernet0/3, changed state to down
*Mar  1 02:14:09.323: %LINK-3-UPDOWN: Interface FastEthernet0/3, changed state to down
```

Which two statements are true? (Choose two.)

- [x] A device that sends BPDUs, such as another switch, was connected to Fa0/3.
- [x] SW1's clock is not synchronised, as the asterisk in front of each timestamp shows.
- [ ] `%LINEPROTO-5-UPDOWN` is the most serious message in the buffer, because it has the highest severity number.
- [ ] Fa0/3 comes back up on its own as soon as the device is unplugged.
- [ ] An engineer connected to SW1 by SSH sees these messages as they happen without entering any extra command.

> **Explanation:** `%SPANTREE-2-BLOCK_BPDUGUARD` shows that BPDU guard received a BPDU on Fa0/3, so something that speaks STP (typically a user's switch) was plugged in, and `%PM-4-ERR_DISABLE` shows the port was err-disabled as a result. A `*` before the timestamp means the clock is not synchronised (NTP). Severity runs from 0 (emergency) to 7 (debugging) and **lower is more serious**, so the severity 2 SPANTREE message is the most serious entry and the severity 5 LINEPROTO message the least serious. An err-disabled port stays down until it is bounced: remove the device, then `shutdown` and `no shutdown` on Fa0/3 (unless errdisable recovery is configured). Log messages appear on the console as they happen, but an SSH session sees them only after `terminal monitor`.

### Q3 · Drag and drop — match
<sub>Source: 15.4</sub>

Drag each IOS log message to what it points to.

| Log message | Points to |
| --- | --- |
| `%SW_MATM-4-MACFLAP_NOTIF` | A MAC address moving between ports, most likely a Layer 2 loop |
| `%IP-4-DUPADDR` | Two devices using the same IP address on the segment |
| `%OSPF-5-ADJCHG` | An OSPF neighbor changing state |
| `%HSRP-5-STATECHANGE` | A change of HSRP role |
| `%SYS-5-CONFIG_I` | A configuration change, and who made it |
| `%CDP-4-NATIVE_VLAN_MISMATCH` | Different native VLANs on the two ends of a trunk |

**Extra targets:** A duplex mismatch with the neighbor · A port disabled by port security

> **Explanation:** Every message reads `%FACILITY-SEVERITY-MNEMONIC: text`, and the facility and mnemonic name the event. MACFLAP means the switch keeps relearning a MAC address on different ports, the classic sign of a loop. DUPADDR is a duplicate IP address, ADJCHG an OSPF neighbor state change, STATECHANGE an HSRP role change and CONFIG\_I a configuration change (with the user and source). NATIVE\_VLAN\_MISMATCH is reported by CDP when the trunk ends disagree. A duplex mismatch would be `%CDP-4-DUPLEX_MISMATCH`, and a port shut down by port security would log `%PM-4-ERR_DISABLE`; neither message is in the list.

### Q4 · Drag and drop — match
<sub>Source: 15.5, 15.6</sub>

Drag each ping result seen on a Cisco router to its most likely cause.

| Ping result | Most likely cause |
| --- | --- |
| `.!!!!` the first time the router pings a host on one of its own subnets | The router was waiting for an ARP reply before it could send the first packet |
| `UUUUU` | A router on the path has no route to the destination, or an ACL rejected the packets |
| `MMMMM` with 1500-byte packets and the DF bit set, while 1400-byte pings succeed | A link on the path with an MTU below 1500 bytes |
| `&&&&&` | A routing loop, so the packets' TTL expired |
| `.....` | No reply within the timeout: a missing return route, a filter dropping silently, or a host that is down |

**Extra targets:** Congestion signalled by source quench messages

> **Explanation:** `!` is an Echo Reply and `.` a timeout. A single `.` at the start is normal: the first packet waited for ARP. `U` means an ICMP Destination Unreachable came back from a router with no route or an ACL that rejected the packet. `M` (could not fragment) appears when a packet is too big for a link and the DF bit forbids fragmentation, which is why large DF pings fail while small ones pass. `&` means the packet lifetime (TTL) was exceeded, the signature of a routing loop. A row of `.` means silence: the problem may be on the way there **or on the way back**. Source quench is shown as `Q`, which is rare today and is not one of the results listed.

### Q5 · Multiple choice
<sub>Source: 15.6, 15.9</sub>

Refer to the exhibit. An engineer at PC1 in VLAN 10 cannot open an SSH session to SW2's management address, 10.10.99.12. DSW1's VLAN 99 address is 10.10.99.2. The engineer runs these tests on DSW1.

```
DSW1# ping 10.10.99.12
Type escape sequence to abort.
Sending 5, 100-byte ICMP Echos to 10.10.99.12, timeout is 2 seconds:
!!!!!
Success rate is 100 percent (5/5), round-trip min/avg/max = 1/1/2 ms
DSW1# ping 10.10.99.12 source vlan 10
Type escape sequence to abort.
Sending 5, 100-byte ICMP Echos to 10.10.99.12, timeout is 2 seconds:
Packet sent with a source address of 10.10.10.2
.....
Success rate is 0 percent (0/5)
```

What is the most likely cause of the problem?

- [ ] VLAN 99 is missing from the trunks between the distribution switches and SW2.
- [ ] DSW1 has no route to 10.10.99.0/24.
- [x] SW2's default gateway is missing or wrong, so it cannot reply to addresses outside 10.10.99.0/24.
- [ ] SW2's VLAN 99 interface is administratively down.

> **Explanation:** A plain ping from a router or Layer 3 switch uses the exit interface's address as its source, here DSW1's VLAN 99 address 10.10.99.2. SW2 can answer that address directly because it is in its own subnet, so the first test proves that VLAN 99 reaches SW2, that DSW1 has the route and that SW2's SVI is up. The extended ping sourced from VLAN 10 (10.10.10.2) forces SW2 to send its replies to another subnet, which needs its default gateway, and that fails. A Layer 2 switch is like a host: the fix is `ip default-gateway 10.10.99.1` on SW2.

### Q6 · CLI
<sub>Source: 15.6</sub>

Staff users report that Internet access drops for a few seconds now and then. On DSW1, enter one command that sends 1000 pings to 192.0.2.8 using DSW1's VLAN 10 interface (10.10.10.2) as the source, so that the test also covers the return route to the Staff subnet.

**Prompt:** `DSW1#`

**Accepted:** `ping 192.0.2.8 source vlan 10 repeat 1000` · `ping 192.0.2.8 repeat 1000 source vlan 10` · `ping 192.0.2.8 source 10.10.10.2 repeat 1000` · `ping 192.0.2.8 repeat 1000 source 10.10.10.2`

> **Explanation:** The one-line form of extended ping takes the options after the destination: `source` (an interface or one of the device's own addresses) and `repeat` (the count). A large repeat count, 100 or 1000, catches intermittent loss that five pings would miss, and the VLAN 10 source makes the replies travel back towards the Staff subnet instead of DSW1's link address. The same test can be run interactively by typing `ping` with no address and answering `y` to `Extended commands`.

### Q7 · Multiple choice
<sub>Source: 15.5, 15.7</sub>

Refer to the exhibit. 192.0.2.8 is a loopback address on the ISP router. PC1's trace to it completes, but the trace from DSW1 never reaches it.

```
C:\> tracert 192.0.2.8

Tracing route to 192.0.2.8 over a maximum of 30 hops

  1    <1 ms    <1 ms    <1 ms  10.10.10.2
  2     1 ms     1 ms     1 ms  10.0.0.1
  3     2 ms     1 ms     1 ms  192.0.2.8

Trace complete.

DSW1# ping 192.0.2.8
Type escape sequence to abort.
Sending 5, 100-byte ICMP Echos to 192.0.2.8, timeout is 2 seconds:
!!!!!
Success rate is 100 percent (5/5), round-trip min/avg/max = 1/1/2 ms
DSW1# traceroute 192.0.2.8
Type escape sequence to abort.
Tracing the route to 192.0.2.8
  1 10.0.0.1 1 msec 0 msec 1 msec
  2  *  *  *
  3  *  *  *
  4  *  *  *
```

What is the most likely explanation?

- [ ] The ISP router has no route back to DSW1's address.
- [ ] There is a routing loop between R1 and the ISP router.
- [ ] The ISP router is down.
- [x] A filter on the path drops the UDP probes that IOS traceroute sends but permits ICMP Echo, which Windows tracert uses.

> **Explanation:** Cisco IOS traceroute sends UDP probes to high ports (starting at 33434), whereas Windows `tracert` sends ICMP Echo Requests. When the final hop is never reached but ping works, the UDP probes are being filtered while ICMP Echo is allowed. DSW1's ping and traceroute leave through the same exit interface and use its address (10.0.0.2) as their source, so the successful ping proves that the ISP router is up and can route replies back to DSW1. A routing loop would show the same addresses repeating, and `* * *` alone never proves that a router is down.

### Q8 · Multiple choice
<sub>Source: 15.8, 15.9</sub>

Refer to the exhibit. PC1 (10.10.10.11) can ping the printer at 10.10.40.11 but cannot print to its raw-print port, TCP 9100. This capture was taken on PC1.

```
No. Time      Source          Destination     Protocol Info
1   0.000000  10.10.10.11     10.10.40.11     ICMP     Echo (ping) request id=0x0001, seq=1, ttl=128
2   0.001120  10.10.40.11     10.10.10.11     ICMP     Echo (ping) reply   id=0x0001, seq=1, ttl=254
3   4.310000  10.10.10.11     10.10.40.11     TCP      49815 → 9100 [SYN] Seq=0
4   5.312000  10.10.10.11     10.10.40.11     TCP      [TCP Retransmission] 49815 → 9100 [SYN] Seq=0
5   7.314000  10.10.10.11     10.10.40.11     TCP      [TCP Retransmission] 49815 → 9100 [SYN] Seq=0
```

What does the capture suggest?

- [ ] The printer is reachable, but no service is listening on TCP port 9100.
- [x] A filter on the path, such as an ACL, is silently dropping TCP port 9100 traffic while ICMP is permitted.
- [ ] PC1 cannot resolve the MAC address of its default gateway.
- [ ] The printer has no route back to PC1's subnet.

> **Explanation:** The Echo Request and Echo Reply prove that the two hosts reach each other in both directions at Layer 3, so ARP, the gateways and the return route all work. A SYN that is repeated with no answer at all means the traffic is filtered (an ACL or a firewall) or has no route back, and the successful ping between the same two addresses rules out the missing route. If the printer were reachable but nothing listened on port 9100, it would answer the SYN with an RST, which points to the application rather than the network.

### Q9 · Drag and drop — match
<sub>Source: 15.3, 15.9, 15.10</sub>

Drag each thing an engineer needs to find out to the command that answers it.

| You need to find out | Command |
| --- | --- |
| Why a switch restarted overnight and how long it has been up | show version |
| Which processes are keeping a switch's CPU busy | show processes cpu sorted |
| Whether VLAN 40 is allowed and forwarding on an uplink | show interfaces trunk |
| Which access VLAN PC3's port, SW2 Fa0/1, is assigned to | show vlan brief |
| Which route and next hop R1 uses for 10.10.10.11 | show ip route 10.10.10.11 |
| Why a port was put in the err-disabled state | show logging |

**Extra targets:** show ip arp · show cdp neighbors

> **Explanation:** `show version` gives the uptime and the last reload reason, along with the IOS version. `show processes cpu sorted` lists the busiest processes first, which helps when a loop or broadcast storm drives the CPU up. `show interfaces trunk` shows the allowed and forwarding VLAN lists of each trunk, and `show vlan brief` shows which VLAN each access port belongs to. `show ip route` followed by an address prints the entry used for that destination. `show logging` holds the messages, such as `%PM-4-ERR_DISABLE` and the event that caused it, that explain why a port was disabled. `show ip arp` maps IP addresses to MAC addresses, and `show cdp neighbors` lists directly connected Cisco devices; neither answers any of these questions.

### Q10 · Multiple choice
<sub>Source: 15.7, 15.10</sub>

Why does PC1's trace stop after hop 1?

- [ ] R1's G0/0/0 interface is down, so the probes never reach R1.
- [ ] R1 filters the UDP probes that `tracert` sends.
- [x] R1's replies to 10.10.10.11 match only its default route, because its static route covers only 10.10.0.0 to 10.10.0.255, so they go to the ISP instead of back to the campus.
- [ ] R1's default route points to the wrong next hop.

> **Explanation:** The probes with TTL 2 do reach R1, which drops them and sends ICMP Time Exceeded to 10.10.10.11. R1's only campus route is 10.10.0.0/24, which covers 10.10.0.0–10.10.0.255, so 10.10.10.11 matches the default route and the reply is sent to the ISP; the ISP's 10.0.0.0/8 route sends it back to R1, and it never reaches PC1. Replies to the later probes are lost the same way, so `* * *` here means "replies cannot get back", not "the next router is down". G0/0/0 is up (its C and L routes are in the table), Windows `tracert` uses ICMP Echo rather than UDP, and 198.51.100.1 is the ISP's correct address.

### Q11 · CLI
<sub>Source: 15.10</sub>

You are in global configuration mode on R1 and have already removed the wrong route with `no ip route 10.10.0.0 255.255.255.0 10.0.0.2`. Enter the command that restores R1's route to every campus subnet: 10.10.0.0/16 through next hop 10.0.0.2 on G0/0/0.

### Q12 · Multiple choice
<sub>Source: 15.2, 15.10</sub>

A good hypothesis explains all the symptoms. Why do newly connected PCs get no address?

- [ ] R1 can lease addresses from the STAFF pool only to clients on a subnet that it is directly connected to.
- [ ] The routing change on R1 stops the new PCs' broadcast Discovers from reaching DSW1.
- [ ] DSW1 and DSW2 stop relaying Discovers to 10.0.0.1 as soon as R1 loses a route.
- [x] R1 still receives the relayed Discovers, but it sends its Offers to the relay's address (giaddr 10.10.10.2), which also matches only its default route.

> **Explanation:** The relays send the Discovers to 10.0.0.1 as unicasts; DSW1 is directly connected to 10.0.0.0/30 and DSW2 reaches it through its default route to DSW1, so R1 receives them. R1 then sends its Offers to the giaddr, the relay's VLAN 10 address (10.10.10.2 for DSW1, 10.10.10.3 for DSW2), and those addresses fall outside 10.10.0.0/24 just like PC1's, so the Offers follow the default route to the ISP. One missing route therefore explains both symptoms. A DHCP server reached through relays does not need to be connected to the clients' subnet, and a Discover is a local broadcast that reaches the relay whatever R1's routing table says.
