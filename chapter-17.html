Chapter 17Client connectivity on Windows, macOS and Linux

🖼️ 2 figures⏱️ ~16 min read📝 Self-check: 13 questions

Objective covered: 1.6 Troubleshoot wired and wireless client connectivity (IP configuration, network reachability, and wireless security parameters on Windows, MacOS, and Linux). Earlier chapters fixed the network side; this chapter starts from the user's computer, because many "network" tickets are solved there.

17.1 Learning objectives

After this chapter you can:

  1. Check a client's link, IP address, mask, gateway and DNS on Windows, macOS and Linux.
  2. Recognise broken configurations from command output: APIPA, wrong mask, wrong gateway, missing DNS, duplicate address, IPv6 without a global address.
  3. Test reachability in a logical order and say what each failure means.
  4. Read a Wi-Fi client's SSID, BSSID, channel, signal and security settings on each operating system.
  5. Match client wireless security settings to the WLAN and fix mismatches.

Lab itThis chapter is hands-on. Once the theory clicks, jump to Lab 17.1 — Client troubleshooting on real systems and in Packet Tracer (Beginner–Intermediate) and build it yourself — reading about a network is good, breaking and fixing one is better.

17.2 A client-side method

Work outward from the client, one question at a time (Figure 17.1):

Read Figure 17.1 left to right. The highlighted last step is where most users start complaining ("the website is down"), but you start at the first box.

  1. Link — is the cable connected or the Wi-Fi associated to the right SSID?
  2. Address — does the client have a valid address and mask for this network (not 169.254.x.x)?
  3. Gateway — is a default gateway set, in the same subnet, and does it answer?
  4. Remote IP — can it reach an address beyond the gateway?
  5. Names — is a DNS server set, and do names resolve (Chapter 22)?
  6. Application — does the service itself answer (port, proxy, firewall on the client)?

Stop at the first "no" — everything after it depends on it.

17.3 Commands on each operating system

All commands below run in a terminal: Command Prompt or PowerShell on Windows, Terminal on macOS and Linux. Commands that change settings need administrator rights (Run as administrator, or sudo). Linux distributions differ; the commands shown use the standard iproute2 tools and NetworkManager (nmcli), present on Ubuntu and most desktops.

DNS servers ipconfig /all scutil --dns resolvectl status (or cat /etc/resolv.conf)

Interface names differ: Windows uses names like Ethernet and Wi-Fi; macOS uses en0 (often Wi-Fi on laptops) and en1; Linux uses names like eth0, enp3s0 and wlan0/wlp2s0. Use the name your system shows. On macOS the old airport command-line tool has been removed in recent releases; use wdutil or the Option-click menu.

17.5 The reachability ladder

Test in this order, one rung at a time:

  1. ping 127.0.0.1 (or ping ::1) — the TCP/IP stack works. A failure means a damaged OS network stack, rare.
  2. ping <own address> — the adapter has that address.
  3. ping <default gateway> — Layer 1–3 to the first hop: link, VLAN, mask, ARP. Failure: back to the link, VLAN or Wi-Fi association.
  4. ping <remote IP>, for example 192.0.2.8 — routing beyond the gateway and back. Failure with step 3 working: a routing, ACL or NAT problem past the gateway (Chapter 15).
  5. ping <name>, for example ping www.campus.example — DNS. A failure here while step 4 works points to DNS (Chapter 22).
  6. Test the application: open the page, curl, or Test-NetConnection server -Port 443 (PowerShell).

Firewalls can lie. Windows Defender Firewall blocks incoming ICMP by default on public networks, so a PC that does not answer ping may still be fine. Test reachability from the PC outward, or use an application-level test.

17.6 Wireless client status and security parameters

A Wi-Fi client connects only when every security setting matches the WLAN (Chapter 16):

Setting Must match Typical mistake
SSID Exact name (case-sensitive) Joining staff-wifi or a look-alike rogue SSID
Security type WPA2/WPA3, Personal or Enterprise Old profile set to WPA2-Personal after the WLAN moved to Enterprise
Cipher AES (CCMP); GCMP for WPA3 192-bit Client forced to TKIP
Passphrase (Personal) Exact Typo, or an old saved password after a change
EAP method and credentials (Enterprise) PEAP or EAP-TLS, correct username/password or certificate Expired certificate; wrong domain in the username
Server certificate trust (Enterprise) Client trusts the RADIUS server's certificate User clicks through warnings — or the client refuses an untrusted server
Capabilities Band and standard the client supports Old laptop cannot see a 6 GHz-only or WPA3-only SSID
Protected management frames Required for WPA3 Old driver without PMF

terminal
$ sudo wdutil info                                  (macOS, excerpt)
    SSID     : Staff-WiFi
    RSSI     : -56 dBm
    Noise    : -92 dBm
    Channel  : 5g36/80
    Security : WPA2 Enterprise

What these tell you: which SSID and AP radio (BSSID) the client chose, the band and channel, signal strength (Windows shows a percentage, Linux and macOS dBm), the security type and cipher actually negotiated, and the data rate. macOS also gives the noise floor, so you can work out SNR directly: −56 − (−92) = 36 dB. Field names and layout differ between OS versions; macOS may hide the SSID unless the terminal has location permission.

Two modern client behaviours that surprise people:

  • Private (random) MAC addresses. Windows, macOS, iOS and Android can use a different random MAC per network. A DHCP reservation or MAC-based rule written for the hardware MAC then fails. Check the address the client actually uses (ipconfig /all, ip link) or turn the feature off for that network.
  • Captive portals. Guest networks often intercept web traffic until the user accepts terms. The client has an address and DNS, but everything else seems blocked until the portal page is completed.

17.7 Troubleshooting client connectivity

Symptom Likely cause Check / fix
Wi-Fi "can't connect to this network" Wrong passphrase or security type, old saved profile Forget the network, reconnect; compare security settings
Enterprise Wi-Fi fails for one user Wrong credentials, expired certificate, untrusted server certificate RADIUS logs (Chapter 18); client certificate store
Connected but 169.254.x.x DHCP not reaching the client (VLAN, relay, pool) Chapter 14; ipconfig /renew
Connected, valid address, nothing off-subnet Wrong or missing gateway, wrong mask ipconfig /all / ip route; Figure 17.2
Pings by IP work, names fail No or wrong DNS server nslookup; DNS settings (Chapter 22)
Slow or dropping Wi-Fi Low SNR, interference, far from the AP, sticky client on a distant BSSID Signal/noise readings; channel plan (Chapter 16)
Works on Wi-Fi, not on cable (or reverse) Different VLAN per access method; static IP on one adapter Compare both adapters' settings
Works at home, not on campus Static address, DNS or proxy left configured Switch back to DHCP/automatic
One device blocked, others fine MAC-based filter or reservation vs private MAC Use the device's current MAC
Remote PC "down" but users work Host firewall blocks ICMP Test with an application port, or allow ICMP

17.9 Chapter 17 summary notes (exam revision)

  • Order: link → address → gateway → remote IP → names → application. Stop at the first failure.
  • IP settings: Windows ipconfig /all; macOS ifconfig en0, networksetup -getinfo; Linux ip address, ip route, resolvectl status. Masks appear as dotted decimal (Windows), hex (macOS 0xffffff00) or prefix (Linux /24).
  • Renew: Windows ipconfig /release + /renew; macOS sudo ipconfig set en0 DHCP; Linux dhclient or nmcli connection down/up.
  • Paths: tracert (Windows, ICMP), traceroute (macOS/Linux, UDP). macOS/Linux ping is continuous unless -c.
  • Wi-Fi status: netsh wlan show interfaces (signal in %), nmcli device wifi list / iw dev <if> link (dBm), macOS Option-click or sudo wdutil info (RSSI and noise).
  • Match: SSID (case-sensitive), security type, cipher, passphrase or EAP credentials, server certificate trust, band/PMF capability.
  • Signs: 169.254 = no DHCP; gateway outside subnet = no off-subnet access; IPv6 only fe80:: = no RAs; private MAC breaks MAC-based rules; captive portal blocks until accepted.

Common conceptual mistakes

Mistake Correct idea
"If I can ping the gateway, DNS must work" DNS is a separate check (step 5)
"0xffffff00 is a strange IP address" It is macOS's hex form of the mask 255.255.255.0
"No reply to ping means the PC is off" Host firewalls often drop ICMP
"The Wi-Fi password is right, so security matches" The security type and cipher must match too
"A wrong mask always breaks connectivity" Proxy ARP can hide it until someone disables proxy ARP
