4.2 Introduction

A college lab server in Kathmandu might run a web server, a database, a DHCP server and a monitoring tool. Twenty years ago each would need its own physical machine, mostly sitting idle. Virtualization lets one physical server run many isolated workloads at once, each believing it has its own computer. The result is fewer servers, less power, faster deployment and easier recovery.

For a network engineer, virtualization changes one thing above all: one switch port may now carry traffic for dozens of machines in several VLANs.

4.3 Key terms

Term Meaning
Host The physical server (or laptop) that provides CPU, memory, storage and NICs
Hypervisor Software that creates and runs VMs and shares the host's hardware among them (also called a virtual machine monitor)
Virtual machine (VM) A complete software computer: virtual CPU (vCPU), memory, disk and NIC, running its own guest operating system
Guest OS The OS inside a VM (Windows Server, Ubuntu, Cisco IOS XE in a virtual router)
Virtual disk A file that acts as the VM's hard disk (.vmdk, .vhdx, .qcow2)
Snapshot A saved point-in-time state you can roll back to
Live migration Moving a running VM to another host without shutting it down (VMware vMotion, Hyper-V Live Migration)
Container An isolated process (or group) that packages an application and its libraries but shares the host's OS kernel
Image A read-only template from which VMs or containers are started
Virtual switch (vSwitch) Software switch inside the host that connects VMs to each other and to the physical NICs

4.4 Type 1 and Type 2 hypervisors

Type 1 (bare-metal) hypervisors run directly on the server hardware, with no general-purpose OS underneath. They are efficient and secure, and they run data centres. Examples: VMware ESXi, Microsoft Hyper-V, KVM (part of the Linux kernel), Xen.

Type 2 (hosted) hypervisors run as an application on top of an ordinary OS. They are convenient for labs and desktops but add a layer of overhead. Examples: Oracle VirtualBox, VMware Workstation, VMware Fusion, Parallels Desktop.

Figure 4.1 compares the three software stacks, including containers.

Read each column of Figure 4.1 from the hardware upward. A Type 1 hypervisor sits directly on the hardware; a Type 2 hypervisor needs a host OS beneath it. Containers drop the guest OS entirely, which is why they start in seconds and use far less memory.

Type 1 (bare-metal) Type 2 (hosted)
Runs on Hardware directly A host OS (Windows, macOS, Linux)
Performance Near native Lower; host OS competes for resources
Typical use Production servers, data centres, cloud Laptops, training labs, testing
Examples ESXi, Hyper-V, KVM, Xen VirtualBox, VMware Workstation, Parallels
Management Central tools (vCenter, SCVMM) or web UI Desktop application

Exam tip"bare-metal" always means Type 1; "runs on top of Windows/macOS" always means Type 2.

Memory trickType 1 sits 1st on the metal (bare-metal). Type 2 is the 2nd layer up — it runs on top of a host OS.

4.5 How VMs connect to the network

A VM has no physical cable. Its traffic travels through three pieces of software and then a physical NIC (Figure 4.2):

  1. vNIC — the VM's virtual network card. It has its own MAC address, so the physical switch learns many MACs behind one port.
  2. Virtual switch (vSwitch) — a Layer 2 switch inside the hypervisor. It forwards frames between VMs on the same host without them ever reaching the physical network, and sends everything else out an uplink. Examples: VMware vSphere Standard and Distributed Switch, Hyper-V Virtual Switch, Linux bridge, Open vSwitch.
  3. Port group — a set of vSwitch ports sharing a policy, most importantly a VLAN ID. Put a VM's vNIC in the "Staff, VLAN 10" port group and its traffic belongs to VLAN 10.
  4. Uplinks (physical NICs) — the host's real NICs, for example vmnic0 and vmnic1. Because VMs in different VLANs share them, the uplinks normally carry an 802.1Q trunk to the physical switch. Two or more uplinks are often bundled (NIC teaming), which on the switch side may be an EtherChannel/LACP port channel.

In Figure 4.2 arrows show outbound traffic. Each VM's vNIC sits in a port group, the vSwitch tags frames with that port group's VLAN, and the two highlighted uplinks carry the tagged frames to SW1 as one LACP bundle. SW1 must allow both VLANs on the trunk, or VMs in a missing VLAN are cut off.

Step by step: VM-Web (VLAN 10) sends a packet to its gateway.

  1. VM-Web's vNIC sends an untagged frame into the Staff port group.
  2. The vSwitch knows the port group is VLAN 10, so it adds an 802.1Q tag with VLAN 10 when sending the frame out vmnic0.
  3. SW1 receives the tagged frame on its trunk and forwards it in VLAN 10 toward the gateway (an SVI or router).
  4. Replies come back tagged VLAN 10; the vSwitch removes the tag and delivers the frame to VM-Web.

Recognising virtual MAC addresses. Hypervisors use their own OUIs, so a MAC table full of them tells you a port connects to a virtualization host:

OUI (first 3 bytes) Usually means
00:50:56 VMware VM
00:15:5D Hyper-V VM
08:00:27 VirtualBox VM
52:54:00 KVM/QEMU VM

4.6 Containers

A container packages one application with exactly the libraries it needs and runs it as an isolated process on a shared OS kernel. The Linux kernel features namespaces (each container sees its own processes, network interfaces and file system) and cgroups (limits on CPU and memory) provide the isolation.

Term Meaning
Image Read-only template: the app, its libraries and settings (for example nginx:latest)
Container A running instance of an image
Registry Where images are stored and downloaded (Docker Hub, a private registry)
Container engine / runtime Software that pulls images and runs containers (Docker, containerd, Podman)
Orchestrator Runs many containers across many hosts, restarts failed ones, scales them (Kubernetes)

How containers are networked (Figure 4.3). By default Docker on Linux:

  1. Creates a Linux bridge called docker0, normally 172.17.0.1/16.
  2. Gives each container a virtual interface on that bridge and an address such as 172.17.0.2.
  3. Uses NAT (masquerading) on the host so containers can reach outside networks using the host's IP.
  4. Makes a container reachable from outside only when a port is published: -p 8080:80 maps the host's port 8080 to the container's port 80.

In Figure 4.3 the highlighted arrows trace a request from a laptop on the home LAN to the web container. Nothing outside the host can reach 172.17.0.2 directly; only the published port is exposed. This is the same NAT idea you will configure on routers in Chapter 21.

Other modes exist: host networking (the container uses the host's interfaces directly), none (no network), and overlay networks that span several hosts in an orchestrated cluster.

4.7 VMs vs containers

Virtual machine Container
Includes Full guest OS + app App + libraries only
Kernel Its own Shares the host's
Size Gigabytes Megabytes
Start time Tens of seconds to minutes About a second
Isolation Strong (separate kernels) Process-level; weaker if the kernel is compromised
Run a different OS? Yes (Windows VM on a Linux host) Must match the host kernel type (Linux containers need a Linux kernel)
Best for Different OSs, legacy apps, strong separation Microservices, fast scaling, CI/CD pipelines

They are not rivals: in practice containers often run inside VMs, especially in the cloud.

4.8 Virtual network appliances (NFV)

Network Functions Virtualization (NFV) runs network devices as software on standard servers instead of dedicated hardware. Examples from Cisco:

  • Catalyst 8000V — a virtual IOS XE router (successor to the CSR 1000v), common in public clouds and data centres.
  • Secure Firewall Threat Defense Virtual (FTDv) and ASAv — virtual firewalls.
  • Virtual wireless controllers — controller software running as a VM (Chapter 7, objective 2.2.b).

Lab tools use the same idea: Cisco Modeling Labs (CML), GNS3 and EVE-NG run real IOS images as VMs or containers. Packet Tracer is different: it simulates device behaviour rather than running real Cisco software, which is why some features are missing (as noted in Part 0.4).

Some Cisco switches and routers can also host containers themselves (Cisco IOx application hosting), but that is beyond the CCNA objectives.

4.9 What virtualization means for the network engineer

You rarely configure the hypervisor, but you configure the switch ports it plugs into, and you get the ticket when a VM "has no network". Three facts drive everything:

  1. One port, many MACs and VLANs. A host port is usually a trunk carrying every VLAN its VMs use.
  2. VMs move. Live migration can move a VM to another host at any moment, so every host in a cluster needs the same VLANs on its uplinks.
  3. The vSwitch and the physical switch must agree on VLAN IDs, the native VLAN, and how uplinks are bundled.

A preview of the switch configuration (taught fully in Chapters 5–7):

SW1
SW1(config)# interface range gigabitethernet1/0/1 - 2
SW1(config-if-range)# description ESXi-01 vmnic0-1
SW1(config-if-range)# switchport mode trunk
SW1(config-if-range)# switchport trunk allowed vlan 10,99
SW1(config-if-range)# switchport nonegotiate
SW1(config-if-range)# spanning-tree portfast trunk
SW1(config-if-range)# channel-group 1 mode active      ! only if the host side uses LACP

Notes: newer IOS releases write the PortFast command as spanning-tree portfast edge trunk. Bundle the ports with LACP only when the hypervisor's teaming is set to LACP (for example a VMware distributed switch with a LAG); many teaming modes expect two independent trunk ports instead.

Troubleshooting virtualized hosts

Symptom Likely cause What to check Fix
VMs in one VLAN have no network; other VMs on the same host are fine VLAN not allowed on the trunk, or not created on the switch show interfaces trunk, show vlan brief Add the VLAN to the switch and the allowed list
A VM sits in the wrong subnet Wrong VLAN ID on its port group Hypervisor port group settings; show mac address-table address <vm-mac> Correct the port group VLAN

4.10 Hands-on Lab 4.1 — VMs and containers on your own laptop (Beginner)

Objective: 1.2. PT note: Packet Tracer cannot run VMs or containers, so this lab uses free tools on your laptop. It is optional for the exam but makes every concept in this chapter concrete.

You need: Oracle VirtualBox (free), an Ubuntu Server ISO, about 20 GB of disk and 2 GB of spare RAM. Your laptop is the host; VirtualBox is a Type 2 hypervisor.

Figure 4.4 shows the three VirtualBox network modes you will test.

In Figure 4.4 the highlighted line is the VM's path. In NAT mode it hides behind the host; in Bridged mode it connects to the home router as if it were a separate PC; in Host-only mode it can reach only the host. The addresses are VirtualBox defaults and a typical home network; yours may differ.

Part A — Build the VM

  1. In VirtualBox create a VM: Linux / Ubuntu (64-bit), 2 vCPU, 2048 MB RAM, 20 GB virtual disk.
  2. Install Ubuntu Server from the ISO, accepting the defaults.
  3. Log in and run ip link show. The interface (usually enp0s3) has a MAC starting 08:00:27 — the VirtualBox OUI from 4.5.

Part B — NAT mode (the default)

terminal
$ ip -4 addr show enp0s3
    inet 10.0.2.15/24 ... dynamic enp0s3
$ ip route
default via 10.0.2.2 dev enp0s3 ...
$ ping -c 2 1.1.1.1          # works if your laptop has Internet

From the laptop, try ping 10.0.2.15: it fails. The VM is hidden behind VirtualBox's NAT, just like a home PC behind a router.

Part C — Bridged mode

  1. Power off the VM. In Settings → Network → Adapter 1 choose Bridged Adapter and select the laptop's Wi-Fi or Ethernet card.
  2. Start the VM and run ip -4 addr show enp0s3. It now has an address from your home router (for example 192.168.1.60).
  3. From the laptop, ping that address: it succeeds. The VM is a full member of your LAN.
  4. If it gets no address, some Wi-Fi and campus networks block extra MAC addresses on one connection; use Ethernet or Host-only mode instead.

Part D — Host-only mode

  1. In File → Tools → Network Manager confirm a host-only network exists (by default 192.168.56.1/24 with DHCP).
  2. Set Adapter 1 to Host-only Adapter and restart the VM. It receives an address such as 192.168.56.101.
  3. The laptop can ping it, but the VM has no Internet. Add a second adapter in NAT mode if it needs updates.

Part E — Containers inside the VM (use Bridged mode so you can browse to it)

terminal
$ sudo apt update && sudo apt install -y docker.io
$ sudo docker run -d --name web -p 8080:80 nginx
$ ip -4 addr show docker0
    inet 172.17.0.1/16 ... docker0
$ sudo docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' web
172.17.0.2
$ sudo docker port web
80/tcp -> 0.0.0.0:8080

Now open http://<VM address>:8080 in your laptop's browser: the nginx welcome page appears. You have just reproduced Figure 4.3 — a container on the docker0 bridge, reachable only through the published port. Your VM is the Docker host.

Troubleshooting

Problem Cause Fix
Bridged VM gets no IP Network blocks extra MACs, or wrong host adapter selected Choose the correct adapter; use Ethernet or Host-only
permission denied on docker commands User is not in the docker group Use sudo, or sudo usermod -aG docker $USER and log in again
Browser cannot reach port 8080 VM in NAT mode, or container not running Use Bridged mode; check sudo docker ps
docker run cannot download nginx VM has no Internet (Host-only mode) Add a NAT adapter or switch to Bridged

Questions to answer

  1. Why could the laptop not ping the VM in NAT mode?
  2. Which mode makes the VM look like a separate physical PC to your home router?
  3. Which address does the outside world use to reach the nginx container: 172.17.0.2 or the VM's address? Why?

4.11 Chapter 4 summary notes (exam revision)

  • Hypervisor = software that runs VMs and shares hardware among them. Type 1 runs on bare metal (ESXi, Hyper-V, KVM, Xen); Type 2 runs on a host OS (VirtualBox, VMware Workstation, Parallels).
  • VM = full computer in software with its own guest OS: strong isolation, gigabytes, slower to start, can run a different OS.
  • Container = app + libraries sharing the host kernel: megabytes, starts in about a second, weaker isolation. Image → container; registry stores images; Docker/containerd run them; Kubernetes orchestrates them.
  • VM networking: vNIC (own MAC) → port group (VLAN ID) → vSwitch (adds 802.1Q tag) → physical NIC uplinks → trunk (often an LACP bundle) to the physical switch.
  • Container networking: docker0 bridge (172.17.0.0/16 by default), NAT outbound, published ports (-p host:container) inbound.
  • NFV: virtual routers and firewalls (Catalyst 8000V, FTDv, ASAv) and virtual WLCs run as VMs.
  • Virtual OUIs: 00:50:56 VMware, 00:15:5D Hyper-V, 08:00:27 VirtualBox, 52:54:00 KVM.
  • Network impact: trunks must allow every VM VLAN on every host in the cluster; teaming and switch bundling must match; clones can duplicate IPs.

Common conceptual mistakes

Mistake Correct idea
"Containers are small VMs" Containers have no guest OS; they share the host's kernel
"Type 2 means a second-generation hypervisor" Type 2 means hosted on an OS; Type 1 means bare metal
"A host port should be an access port in the main server VLAN" It is usually a trunk carrying every VLAN its VMs use
"VMs on the same host always talk through the physical switch" VMs in the same VLAN on one host talk through the vSwitch without leaving the host

9Troubleshootingthink, then reveal

The switch logs %SW_MATM-4-MACFLAP_NOTIF for VM MAC addresses moving between Gi1/0/1 and Gi1/0/2, which connect to the same host. What is the likely cause?

Answer it in your head (or on paper) first.

The host's NIC teaming does not match the switch configuration — for example the host load-balances across two links while the switch treats them as independent ports (or the reverse). Make both sides agree: an LACP bundle on both, or independent links on both.

A network assistant reviewing a ticket says: "VM-Web in VLAN 10 cannot reach its gateway. Change the ESXi uplink port to switchport mode access and switchport access vlan 10." The same host also runs VM-Mgmt in VLAN 99. Is the advice correct?
