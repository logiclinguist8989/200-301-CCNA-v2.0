22.2 How a name is resolved

DNS maps names to data. The client (stub resolver) asks one configured DNS server, its recursive resolver. The resolver either answers from its cache or walks the DNS tree: a root server refers it to the servers of the top-level domain, those refer it to the authoritative servers for the domain, and the authoritative server returns the record (Figure 22.1).

In Figure 22.1 the shaded resolver does all the walking; PC1 sends one query and gets one answer. Every record carries a TTL (time to live, in seconds), so cached answers expire on their own — which is also why a corrected record can take time to "arrive".

DNS uses UDP 53 for normal queries and TCP 53 for large answers and zone transfers. Encrypted variants exist (DNS over TLS on TCP 853, DNS over HTTPS on 443).

22.3 The six record types

Record Holds Question it answers Rules and common faults
A IPv4 address "What is the IPv4 address of web1?" Wrong or old address; missing record
AAAA IPv6 address "What is the IPv6 address of web1?" Clients prefer IPv6: a wrong AAAA (or broken IPv6 path) causes slow or failed access although the A record is fine
CNAME Another name (alias → canonical name) "What is www really called?" The target must exist and resolve; a CNAME cannot share its name with other records, so it cannot be used at the zone apex (campus.example itself)
MX Preference + mail server name "Which server receives mail for campus.example?" Lower preference = tried first; must point to a host name with an A/AAAA record, not to an IP address or a CNAME
NS Name of an authoritative server "Which servers are authoritative for this zone?" Delegation to a server that does not hold the zone ("lame delegation") → SERVFAIL; NS names inside the zone need glue A records at the parent
PTR A name, for an address "What name belongs to 10.10.40.80?" Lives in the reverse zone: 10.10.40.80 → 80.40.10.10.in-addr.arpa; IPv6 uses reversed nibbles under ip6.arpa. Missing PTR → mail rejected, slow SSH logins, logs show only addresses

Two more you will see in outputs: SOA (start of authority: primary server, contact, serial number, timers) and TXT (free text, used for mail policies such as SPF).

Figure 22.2 shows the example zone used in this chapter's lab. Names in the first column are what a user or service asks for; arrows show what each record returns.

In Figure 22.2 three records (CNAME, MX, NS) return names, so the client must make a second lookup for that name's A record; only A, AAAA and PTR end the chain.

Memory trickAAAA has four times the letters of A because IPv6 addresses have four times the bits (128 vs 32). CNAME = a nickname, MX = mail, PTR = points back from IP to name, NS = who answers for the zone.

nslookup output (Windows):

terminal

  • Server / Address = the DNS server that answered. If it shows Server: UnKnown, that server has no PTR record for its own address — harmless for the lookup, but a sign the reverse zone is incomplete.
  • Aliases shows that www is a CNAME for web1.
  • Non-authoritative answer: above the result means the answer came from a resolver (often from its cache), not from the zone's own server.

dig output (macOS/Linux):

terminal
$ dig www.campus.example A

;; flags: qr aa rd ra; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 1

;; ANSWER SECTION:
www.campus.example.    3600  IN  CNAME  web1.campus.example.
web1.campus.example.   3600  IN  A      10.10.40.80

$ dig -x 10.10.40.80 +short
web1.campus.example.

Read status first, then the ANSWER section: each line is name, TTL, class, type, data. The flag aa means the answer is authoritative.

Response Meaning Typical cause
NOERROR with answers Name and record exist — (check the data is right)
NOERROR, empty answer ("NODATA") Name exists, but not that record type Asked for AAAA where only an A exists; missing MX
NXDOMAIN Name does not exist at all Typo, record never created, wrong domain suffix
SERVFAIL Resolver could not get a valid answer Broken delegation, authoritative server down, DNSSEC failure
REFUSED Server will not answer you Resolver does not allow recursion for your subnet
No response / timed out No DNS server reached Wrong server address, routing, UDP 53 blocked by an ACL

22.5 The client side: caches and the hosts file

Operating systems resolve names in this order: hosts file → local cache → configured DNS server. nslookup and dig skip the hosts file and the OS cache and go straight to the server, so ping web1 and nslookup web1 can give different addresses — a classic clue that a hosts-file entry or a cached answer is the problem.

Task Windows macOS Linux (systemd-resolved)
Show configured DNS servers ipconfig /all scutil --dns resolvectl status
Show cache ipconfig /displaydns — resolvectl statistics
Clear cache ipconfig /flushdns sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder resolvectl flush-caches
Hosts file C:\Windows\System32\drivers\etc\hosts /etc/hosts /etc/hosts

22.6 DNS on IOS devices

R1
R1(config)# ip domain name campus.example
R1(config)# ip name-server 10.10.99.53
R1(config)# ip domain lookup
R1(config)# ip host printer1 10.10.40.11
R1(config)# end
R1# ping web1
Translating "web1"...domain server (10.10.99.53) [OK]
R1# show hosts
  • ip domain name is appended to short names (web1 → web1.campus.example) and is also needed for SSH keys (Chapter 18).
  • ip name-server sets up to six DNS servers. ip domain lookup is on by default.
  • ip host creates a static name on the device only, like a hosts file.
  • no ip domain lookup stops IOS from treating a mistyped command as a host name ("Translating …" delay), but then names no longer resolve on that device. In labs it is common; in production, prefer a working name server.
  • On routers handing out addresses, the DHCP pool's dns-server line (Chapter 14) gives clients their DNS server; a wrong value there breaks name resolution for a whole subnet.

22.7 Diagnosing host, web and mail access by name

Always separate DNS from reachability first: if the service works by IP address but not by name, it is a name problem; if it fails by address too, DNS is not the cause (Figure 22.3).

In Figure 22.3 the first question removes most false DNS suspicions. The result of a direct query then points to the kind of fault on the right.

Host access (ping, SSH, file shares by name) depends on A and AAAA records, the client's DNS server setting, and the domain suffix. Watch for: a record with an old address after a server moved; a missing record for a new device; a short name failing because the client has no domain suffix (ipconfig /all shows Primary DNS Suffix and DNS Suffix Search List); and a wrong AAAA: dual-stack clients try IPv6 first, so a wrong or unreachable IPv6 address makes access slow or fail even though the A record is correct.

Web applications usually sit behind a CNAME (www → web1, or to a load balancer or cloud service). Watch for: a CNAME whose target does not exist (the query shows the alias, then NXDOMAIN or an empty answer); a CNAME added at the zone apex, which DNS forbids; a recently changed record still cached until its TTL expires; and the browser warning about a certificate even though DNS is correct — the certificate must contain the name the user typed, so that is a TLS issue, not a DNS one.

Mail depends on several records. A sending server looks up the recipient domain's MX records, tries the lowest preference first, then needs an A/AAAA record for that MX host name. Receiving servers often check that the sender's address has a PTR record whose name resolves back to the same address. Watch for: no MX (senders then fall back to the domain's own A record, which may not be a mail server); an MX that points to an IP address or to a CNAME; an MX host with no A record; missing or mismatched PTR for the mail server's public address, causing rejected or spam-filtered mail.

Delegation (NS) and consistency: if two authoritative servers give different answers, compare them directly (dig @ns1.campus.example web1.campus.example and the same with @ns2). A secondary that was not updated (its SOA serial number is older) serves stale data. NS records that point to a server not holding the zone produce SERVFAIL for everyone using that delegation.

PTR (reverse) problems rarely stop access outright, but cause slow SSH or FTP logins (servers wait for a reverse lookup), logs and traceroute output with only numbers, and mail rejections.

22.9 Lab 22.2 — Name-resolution tickets (Advanced)

Start from: your finished Lab 22.1 file. Introduce one fault at a time, then work the ticket using Figure 22.3.

# Ticket text Fault to introduce
A "The intranet is down for everyone." On DNS1, change web1's A record to 10.10.40.88
B "www stopped working, but web1 works." On DNS1, change the www CNAME target to web01.campus.example
C "Staff PCs can't open anything by name after a restart." On R1, ip dhcp pool STAFF → dns-server 10.10.99.54; renew PC1
D "Only wireless users can't resolve names." Remove line 15 from WIRELESS-IN on the switch that is HSRP Active for VLAN 30

Solutions

  • A — wrong A record. ping 10.10.40.80 works, so it is not routing; nslookup www.campus.example returns 10.10.40.88. Fix the A record. (On a real network, also flush client caches or wait out the TTL.)
  • B — CNAME to a missing name. nslookup web1.campus.example works; nslookup www.campus.example fails because the alias points to a name with no record. Point the CNAME back to web1.campus.example.
  • C — wrong DNS server from DHCP. ipconfig /all on PC1 shows DNS server 10.10.99.54; nslookup times out. Fix the pool and renew. VLAN 30 still works, which shows the fault is specific to the STAFF pool.
  • D — UDP 53 blocked by the ACL. PC2's nslookup times out while PC1's works; show access-lists WIRELESS-IN shows no line 15 and rising matches on line 20 (VLAN 30 to VLAN 99 denied). Re-add 15 permit udp 10.10.30.0 0.0.0.255 host 10.10.99.53 eq domain on both switches.

22.10 Chapter 22 summary notes (exam revision)

  • Resolution: client (stub) → recursive resolver → root → TLD → authoritative; answers are cached for their TTL. UDP 53 (TCP 53 for large answers and zone transfers).
  • A = IPv4, AAAA = IPv6, CNAME = alias → canonical name (not at the apex, no other records beside it), MX = preference + mail host name (lowest first; never an IP or CNAME), NS = authoritative servers (delegation), PTR = address → name in in-addr.arpa (reversed octets) or ip6.arpa (reversed nibbles).
  • Tools: nslookup [-type=x] name [server], dig name type [@server] [+short] [-x addr] [+trace], Resolve-DnsName.
  • Codes: NOERROR (with or without answers), NXDOMAIN (name missing), SERVFAIL (resolution failed), REFUSED; timeout = no server reached.
  • Method: works by IP? → query the name → read the code and data → fix the record, the client's DNS setting, the cache, or the UDP 53 path.
  • Client side: hosts file → OS cache → DNS server; nslookup/dig skip the first two. ipconfig /flushdns, resolvectl flush-caches.
  • IOS: ip domain name, ip name-server, ip domain lookup, ip host, show hosts; DHCP pool dns-server.

Common conceptual mistakes

Mistake Correct idea
"If the site fails, it must be DNS" Test by IP address first
"An MX record holds the mail server's IP address" It holds a host name; that name's A/AAAA gives the address
"A changed record works immediately everywhere" Cached answers live until their TTL expires
"nslookup proves what ping will use" nslookup ignores the hosts file and the OS cache
"NXDOMAIN means the DNS server is down" The server answered: the name does not exist
"PTR records are needed for the internet to work" They are optional for access, but mail, logging and some logins depend on them
